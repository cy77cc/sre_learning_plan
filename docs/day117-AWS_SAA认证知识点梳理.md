#### 2.2 核心服务：EC2

```
┌──────────────────────────────────────────────────────────────┐
│                    EC2 核心知识点                               │
│                                                               │
│  实例类型：                                                    │
│  ├── 通用型（T3, M5）→ 均衡的计算、内存、网络                 │
│  ├── 计算优化（C5, C6）→ 高性能计算、批处理                   │
│  ├── 内存优化（R5, X1）→ 内存数据库、大数据                   │
│  ├── 存储优化（I3, D2）→ 高 IOPS、数据仓库                   │
│  └── 加速计算（P3, G4）→ GPU、机器学习                       │
│                                                               │
│  购买选项：                                                    │
│  ├── 按需（On-Demand）→ 短期、不可预测负载                   │
│  ├── 预留（Reserved）→ 长期稳定负载（1-3 年）                 │
│  ├── 竞价（Spot）→ 可中断、灵活负载（节省 90%）              │
│  ├── Savings Plans → 灵活的承诺使用量                        │
│  └── 专用主机（Dedicated Host）→ 合规要求                     │
│                                                               │
│  存储选项：                                                    │
│  ├── EBS（块存储）                                           │
│  │   ├── gp3/gp2（通用 SSD）→ 大多数工作负载                │
│  │   ├── io2/io1（预配置 IOPS SSD）→ 数据库                │
│  │   ├── st1（吞吐优化 HDD）→ 大数据、日志                  │
│  │   └── sc1（Cold HDD）→ 不常访问的数据                    │
│  ├── 实例存储（Instance Store）→ 临时数据、缓存              │
│  └── EFS（文件存储）→ 共享文件系统                           │
│                                                               │
│  高可用特性：                                                  │
│  ├── 弹性 IP（EIP）→ 静态公网 IP                             │
│  ├── 自动恢复（Auto Recovery）→ 硬件故障自动恢复             │
│  ├── ASG → 自动扩缩容                                        │
│  └── 跨 AZ 部署 → 单 AZ 故障容错                             │
└──────────────────────────────────────────────────────────────┘
```

#### 2.3 核心服务：S3

```
┌──────────────────────────────────────────────────────────────┐
│                    S3 核心知识点                                │
│                                                               │

│  ├── S3 Intelligent-Tiering → 访问模式变化                   │
│  ├── S3 Standard-IA → 不频繁访问（低成本）                   │
│  ├── S3 One Zone-IA → 不频繁访问（单 AZ，更低成本）          │
│  ├── S3 Glacier Instant Retrieval → 归档（毫秒检索）         │
│  ├── S3 Glacier Flexible Retrieval → 归档（分钟到小时）      │
│  └── S3 Glacier Deep Archive → 深度归档（12-48 小时）        │
│                                                               │
│  关键特性：                                                    │
│  ├── 版本控制（Versioning）→ 数据保护                       │
│  ├── 生命周期策略（Lifecycle）→ 自动转换存储类别             │
│  ├── 跨区域复制（CRR）→ 灾难恢复                            │
│  ├── 事件通知（Event Notification）→ 触发 Lambda/SQS        │
│  ├── S3 Select → 查询 CSV/JSON 数据                         │
│  ├── S3 Transfer Acceleration → 加速远距离上传              │
│  └── S3 Object Lock → 合规保留                              │
│                                                               │
│  安全特性：                                                    │
│  ├── 桶策略（Bucket Policy）→ 访问控制                       │
│  ├── ACL（已弃用）→ 细粒度访问控制                           │
│  ├── 加密（SSE-S3, SSE-KMS, SSE-C）→ 数据保护               │
│  ├── VPC Endpoint → 私有网络访问                             │
│  └── 预签名 URL → 临时访问                                   │
│                                                               │
│  SAA 考点：                                                    │
│  - S3 是 11 个 9 的持久性（99.999999999%）                    │
│  - 跨区域复制需要版本控制                                     │
│  - S3 Intelligent-Tiering 无检索费用                         │
│  - Glacier Deep Archive 最低成本                              │
│  - S3 Transfer Acceleration 使用 CloudFront 边缘位置         │
└──────────────────────────────────────────────────────────────┘
```

#### 2.4 核心服务：VPC

```
┌──────────────────────────────────────────────────────────────┐
│                    VPC 核心知识点                               │
│                                                               │
│  VPC 组件：                                                    │
│  ├── 子网（Subnet）→ 公有/私有子网                           │
│  ├── 路由表（Route Table）→ 流量路由                         │
│  ├── Internet Gateway → 公网访问                             │
│  ├── NAT Gateway → 私有子网出站                              │
│  ├── Security Group → 实例级防火墙（有状态）                 │
│  ├── NACL → 子网级防火墙（无状态）                           │
│  ├── VPC Peering → VPC 间连接                                │
│  ├── VPC Endpoint → 私有访问 AWS 服务                        │
│  └── VPC Flow Logs → 流量审计                               │
│                                                               │
│  子网设计：                                                    │
│  ┌─────────────────────────────────────────────────────┐    │
│  │  公有子网（Public Subnet）                            │    │
│  │  ├── 路由到 Internet Gateway                         │    │
│  │  ├── 适用于：ALB, NAT Gateway, Bastion Host          │    │
│  │  └── 需要分配公网 IP                                 │    │
│  └─────────────────────────────────────────────────────┘    │
│                                                               │
│  ┌─────────────────────────────────────────────────────┐    │
│  │  私有子网（Private Subnet）                           │    │
│  │  ├── 路由到 NAT Gateway（出站）                      │    │
│  │  ├── 适用于：应用服务器、数据库                       │    │
│  │  └── 无直接公网访问                                  │    │
│  └─────────────────────────────────────────────────────┘    │
│                                                               │
│  VPC Endpoint 类型：                                          │
│  ├── Gateway Endpoint → S3, DynamoDB（免费）                 │
│  └── Interface Endpoint → 其他 AWS 服务（收费）              │
│                                                               │
│  SAA 考点：                                                    │
│  - Security Group 是有状态的（自动允许响应流量）              │
│  - NACL 是无状态的（需要明确允许入站和出站）                  │
│  - NAT Gateway 不支持安全组                                   │
│  - VPC Peering 不支持传递路由                                 │
│  - Transit Gateway 支持多 VPC 连接                            │
└──────────────────────────────────────────────────────────────┘
```

#### 2.8 核心服务：SQS 和 SNS

```
┌──────────────────────────────────────────────────────────────┐
│                    SQS 和 SNS 核心知识点                       │
│                                                               │
│  SQS（Simple Queue Service）：                                │
│  ├── 标准队列 → 最大吞吐量，不保证顺序                       │
│  ├── FIFO 队列 → 保证顺序，去重                              │
│  ├── 消息保留：1-14 天（默认 4 天）                          │
│  ├── 可见性超时：0-12 小时（默认 30 秒）                     │
│  ├── 消息大小：最大 256KB                                    │
│  ├── 长轮询 vs 短轮询                                        │
│  └── 死信队列（DLQ）→ 处理失败消息                           │
│                                                               │
│  SNS（Simple Notification Service）：                         │
│  ├── 发布/订阅模式                                           │
│  ├── 支持协议：HTTP/HTTPS, Email, SMS, SQS, Lambda           │
│  ├── 主题（Topic）→ 消息发布目标                             │
│  ├── 订阅（Subscription）→ 消息接收端                        │
│  ├── 消息过滤（Message Filtering）                           │
│  └── FIFO 主题 → 保证顺序                                    │
│                                                               │
│  SQS vs SNS：                                                 │
│  ┌──────────┬──────────────┬──────────────┐                  │
│  │ 特性     │ SQS          │ SNS          │                  │
│  ├──────────┼──────────────┼──────────────┤                  │
│  │ 模式     │ 消息队列      │ 发布/订阅    │                  │
│  │ 消费者   │ 单个消费者    │ 多个订阅者   │                  │
│  │ 消息     │ 持久化存储    │ 推送分发     │                  │
│  │ 顺序     │ FIFO 支持    │ FIFO 支持    │                  │
│  │ 用途     │ 解耦、削峰   │ 通知、扇出   │                  │
│  └──────────┴──────────────┴──────────────┘                  │
│                                                               │
│  SAA 考点：                                                    │
│  - SQS Standard 最大吞吐量无限制                              │
│  - SQS FIFO 每秒 300 条消息（批处理 3000）                    │
│  - SNS + SQS = 扇出模式                                      │
│  - SQS 消息至少传递一次（Standard）                           │
```

### 6. 30 道 SAA 练习题

#### 题目 1-10：设计弹性架构

**Q1**: 一家公司需要将静态网站托管在 S3 上，并通过自定义域名访问。应该使用哪种配置？

A. S3 静态网站托管 + Route 53 A 记录
B. CloudFront + S3 + Route 53 Alias 记录
C. ALB + EC2 + S3
D. API Gateway + Lambda + S3

**答案**：B
**解析**：CloudFront + S3 是静态网站的最佳实践。CloudFront 提供 CDN 加速，S3 提供存储，Route 53 Alias 记录支持根域名解析。A 选项不支持 HTTPS，C 和 D 选项过于复杂。

---

**Q2**: 一个应用需要处理突发流量，消息可以延迟处理，且需要保证消息至少传递一次。应该使用哪种服务？

A. SQS Standard
B. SQS FIFO
C. SNS
D. Kinesis

**答案**：A
**解析**：SQS Standard 提供最大吞吐量和至少一次传递保证，适合突发流量处理。SQS FIFO 保证顺序但吞吐量较低，SNS 是推送模式，Kinesis 用于实时流处理。

---

**Q3**: 一个数据库需要跨区域灾难恢复，RPO < 1 秒，RTO < 1 分钟。应该选择哪种方案？

A. RDS Multi-AZ
B. RDS Read Replicas
C. Aurora Global Database
D. DynamoDB Global Tables

**答案**：C
**解析**：Aurora Global Database 提供跨区域复制（< 1 秒延迟）和快速故障转移（< 1 分钟）。RDS Multi-AZ 只在同一区域，Read Replicas 是异步复制，DynamoDB Global Tables 适用于 NoSQL 场景。

---

**Q4**: 一个应用需要在私有子网中访问 S3，但不能通过公网。应该使用什么？

A. NAT Gateway
B. VPC Endpoint (Gateway)
C. VPC Endpoint (Interface)
D. Internet Gateway

**答案**：B
**解析**：S3 Gateway Endpoint 免费且提供私有访问。NAT Gateway 需要收费且通过公网，Interface Endpoint 也收费，Internet Gateway 提供公网访问。

---

**Q5**: 一个电商网站在促销期间流量增加 10 倍，促销结束后流量恢复正常。最经济的 EC2 购买选项是什么？

A. On-Demand Instances
B. Reserved Instances
C. Spot Instances
D. Savings Plans

**答案**：C
**解析**：Spot Instances 可以节省高达 90%，适合可中断的批处理工作负载。促销期间的流量可以使用 ASG + Spot Instances，基础负载使用 On-Demand 或 Reserved Instances。

### 练习 1：基础操作 — 创建高可用 Web 应用

**目标**：使用 ALB + ASG + RDS Multi-AZ 创建高可用 Web 应用

```bash
# 步骤 1：创建 VPC 和子网
VPC_ID=$(aws ec2 create-vpc --cidr-block 10.0.0.0/16 \
  --query 'Vpc.VpcId' --output text)

# 创建公有子网（2 个 AZ）
PUB_SUBNET1=$(aws ec2 create-subnet \
  --vpc-id $VPC_ID \
  --cidr-block 10.0.1.0/24 \
  --availability-zone us-east-1a \
  --query 'Subnet.SubnetId' --output text)

PUB_SUBNET2=$(aws ec2 create-subnet \
  --vpc-id $VPC_ID \
  --cidr-block 10.0.2.0/24 \
  --availability-zone us-east-1b \
  --query 'Subnet.SubnetId' --output text)

# 创建私有子网（2 个 AZ）
PRIV_SUBNET1=$(aws ec2 create-subnet \
  --vpc-id $VPC_ID \
  --cidr-block 10.0.3.0/24 \
  --availability-zone us-east-1a \
  --query 'Subnet.SubnetId' --output text)

PRIV_SUBNET2=$(aws ec2 create-subnet \
  --vpc-id $VPC_ID \
  --cidr-block 10.0.4.0/24 \
  --availability-zone us-east-1b \
  --query 'Subnet.SubnetId' --output text)

# 步骤 2：创建安全组
ALB_SG=$(aws ec2 create-security-group \
  --group-name alb-sg \
  --description "ALB Security Group" \
  --vpc-id $VPC_ID \
  --query 'GroupId' --output text)

aws ec2 authorize-security-group-ingress \
  --group-id $ALB_SG \
  --protocol tcp --port 80 --cidr 0.0.0.0/0

APP_SG=$(aws ec2 create-security-group \
  --group-name app-sg \
  --description "App Security Group" \
  --vpc-id $VPC_ID \
  --query 'GroupId' --output text)

aws ec2 authorize-security-group-ingress \
  --group-id $APP_SG \
  --protocol tcp --port 80 --source-group $ALB_SG

DB_SG=$(aws ec2 create-security-group \
  --group-name db-sg \
  --description "DB Security Group" \
  --vpc-id $VPC_ID \
  --query 'GroupId' --output text)

aws ec2 authorize-security-group-ingress \
  --group-id $DB_SG \
  --protocol tcp --port 3306 --source-group $APP_SG

# 步骤 3：创建 ALB
ALB_ARN=$(aws elbv2 create-load-balancer \
  --name web-app-alb \
  --type application \
  --scheme internet-facing \
  --subnets $PUB_SUBNET1 $PUB_SUBNET2 \
  --security-groups $ALB_SG \
  --query 'LoadBalancers[0].LoadBalancerArn' --output text)

# 创建 Target Group
TG_ARN=$(aws elbv2 create-target-group \
  --name web-app-tg \
  --protocol HTTP \
  --port 80 \
  --vpc-id $VPC_ID \
  --health-check-path /health \
  --query 'TargetGroups[0].TargetGroupArn' --output text)

# 创建监听器
aws elbv2 create-listener \
  --load-balancer-arn $ALB_ARN \
  --protocol HTTP \
  --port 80 \
  --default-actions '[{"Type":"forward","TargetGroupArn":"'$TG_ARN'"}]'

# 步骤 4：创建 Launch Template
aws ec2 create-launch-template \
  --launch-template-name web-app-lt \
  --launch-template-data '{
    "ImageId": "ami-0abcdef1234567890",
    "InstanceType": "t3.medium",
    "SecurityGroupIds": ["'$APP_SG'"],
    "UserData": "'$(base64 -w0 <<'USERDATA'
#!/bin/bash
yum update -y
yum install -y httpd php php-mysqlnd
systemctl start httpd
systemctl enable httpd
USERDATA
)'"
  }'

# 步骤 5：创建 Auto Scaling Group
aws autoscaling create-auto-scaling-group \
  --auto-scaling-group-name web-app-asg \
  --launch-template "LaunchTemplateName=web-app-lt,Version=1" \
  --min-size 2 \
  --max-size 6 \
  --desired-capacity 2 \
  --vpc-zone-identifier "$PRIV_SUBNET1,$PRIV_SUBNET2" \

# 步骤 6：创建 RDS Multi-AZ
aws rds create-db-subnet-group \

aws rds create-db-instance \

# 步骤 7：验证并清理
```

### 练习 2：进阶场景 — 无服务器架构

**目标**：使用 Lambda + API Gateway + DynamoDB 创建无服务器 API

```bash
# 步骤 1：创建 DynamoDB 表
aws dynamodb create-table \
  --table-name Users \
  --attribute-definitions '[
    {"AttributeName": "userId", "AttributeType": "S"}
  ]' \
  --key-schema '[
    {"AttributeName": "userId", "KeyType": "HASH"}
  ]' \
  --billing-mode PAY_PER_REQUEST

# 步骤 2：创建 Lambda 执行角色
aws iam create-role \
  --role-name lambda-dynamodb-role \
  --assume-role-policy-document '{
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Principal": {"Service": "lambda.amazonaws.com"},
      "Action": "sts:AssumeRole"
    }]
  }'

aws iam attach-role-policy \
  --role-name lambda-dynamodb-role \
  --policy-arn arn:aws:iam::aws:policy/AmazonDynamoDBFullAccess

aws iam attach-role-policy \
  --role-name lambda-dynamodb-role \
  --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole

# 步骤 3：创建 Lambda 函数
cat > lambda_function.py << 'EOF'
import json
import boto3
import uuid

dynamodb = boto3.resource('dynamodb')
table = dynamodb.Table('Users')

def lambda_handler(event, context):
    method = event['httpMethod']

    if method == 'GET':
        response = table.scan()
        return {
            'statusCode': 200,
            'body': json.dumps(response['Items'])
        }
    elif method == 'POST':
        body = json.loads(event['body'])
        body['userId'] = str(uuid.uuid4())
        table.put_item(Item=body)
        return {
            'statusCode': 201,
            'body': json.dumps(body)
        }
EOF

zip function.zip lambda_function.py

aws lambda create-function \
  --function-name user-api \
  --runtime python3.12 \
  --role arn:aws:iam::123456789012:role/lambda-dynamodb-role \
  --handler lambda_function.lambda_handler \
  --zip-file fileb://function.zip \
  --timeout 30

# 步骤 4：创建 API Gateway
API_ID=$(aws apigatewayv2 create-api \
  --name user-api \
  --protocol-type HTTP \
  --query 'ApiId' --output text)

# 创建集成
INTEGRATION_ID=$(aws apigatewayv2 create-integration \
  --api-id $API_ID \
  --integration-type AWS_PROXY \
  --integration-uri arn:aws:lambda:us-east-1:123456789012:function:user-api \
  --payload-format-version 2.0 \
  --query 'IntegrationId' --output text)

# 创建路由
aws apigatewayv2 create-route \
  --api-id $API_ID \
  --route-key 'ANY /users' \
  --target "integrations/$INTEGRATION_ID"

# 创建阶段
aws apigatewayv2 create-stage \
  --api-id $API_ID \
  --stage-name prod \
  --auto-deploy

# 步骤 5：授权 API Gateway 调用 Lambda
aws lambda add-permission \
  --function-name user-api \
  --statement-id apigateway-invoke \
  --action lambda:InvokeFunction \
  --principal apigateway.amazonaws.com \
  --source-arn "arn:aws:execute-api:us-east-1:123456789012:$API_ID/*/*/users"

# 步骤 6：测试
curl https://$API_ID.execute-api.us-east-1.amazonaws.com/prod/users
```

### 练习 3：故障排查挑战 — 成本优化分析

```bash

# 步骤 6：生成成本优化建议
# 1. 未使用的 EBS 卷 → 删除或创建快照后删除
# 2. 未关联的弹性 IP → 释放或关联到实例
# 3. 低利用率的 EC2 实例 → Right Size 或使用 Spot
# 4. S3 存储 → 启用生命周期策略，转换到低成本存储类别
# 5. RDS 实例 → 评估是否可以使用 Reserved Instances

# 挑战：使用 AWS Cost Explorer API 和 Trusted Advisor 自动生成成本优化报告
```

## 🎯 面试题精选

### Q1: 如何选择合适的 EC2 实例类型？

**参考答案**：
选择 EC2 实例类型需要考虑：工作负载类型（通用型 T3/M5、计算优化 C5/C6、内存优化 R5/X1、存储优化 I3/D2、加速计算 P3/G4）、性能需求（CPU、内存、网络、存储 IOPS）、成本考虑（按需 vs 预留 vs 竞价，Savings Plans 灵活性，Right Sizing 避免过度配置）。

### Q2: SQS Standard 和 SQS FIFO 有什么区别？

**参考答案**：
SQS Standard：最大吞吐量无限制，至少一次传递（可能重复），不保证顺序，适合日志处理和后台任务。SQS FIFO：每秒 300 条消息（批处理 3000），恰好一次传递（去重），保证顺序，适合订单处理和金融交易。需要高吞吐量选 Standard，需要顺序和去重选 FIFO。

### Q3: 如何设计一个无服务器架构？

**参考答案**：
无服务器架构设计：前端使用 S3 + CloudFront（静态资源），API 层使用 API Gateway + Lambda（业务逻辑），数据层使用 DynamoDB + ElastiCache，异步处理使用 SQS + Lambda，事件驱动使用 EventBridge + Lambda。优势：按需付费、自动扩缩容、无需管理服务器。挑战：冷启动延迟、执行时间限制、调试复杂性。

### Q4: 如何优化 S3 存储成本？

**参考答案**：
S3 存储成本优化：生命周期策略自动转换存储类别（30 天后 S3 Standard-IA，90 天后 Glacier，365 天后 Deep Archive）、S3 Intelligent-Tiering 自动分层（无检索费用）、删除不完整分段上传、压缩数据、S3 Select 查询部分数据、版本控制设置过期策略。

### Q5: VPC Peering 和 Transit Gateway 有什么区别？

**参考答案**：
- **VPC Peering**：点对点连接（1:1），不支持传递路由，免费（数据传输收费），适合少量 VPC 互联。
- **Transit Gateway**：中心辐射连接（1:N），支持传递路由，按连接和数据传输收费，适合大量 VPC 互联。

选择建议：2-5 个 VPC 使用 VPC Peering，5+ 个 VPC 或跨账户/跨区域使用 Transit Gateway。

### Q6: 如何确保 DynamoDB 的高可用性？

**参考答案**：
DynamoDB 高可用性设计：多 AZ 部署（自动跨 3 AZ 复制）、Global Tables（多区域复制）、Auto Scaling（自动调整读写容量）、DAX 缓存（减少数据库压力）、备份策略（按需备份、时间点恢复、跨区域备份）。单区域 RPO 0 / RTO < 1 秒，多区域 RPO < 1 秒 / RTO < 1 分钟。

### Q7: Lambda 冷启动是什么？如何优化？

**参考答案**：
Lambda 冷启动是函数首次调用或长时间未调用后的初始化过程。优化策略：Provisioned Concurrency（预分配并发实例）、SnapStart（Java 加速启动）、减少包大小（精简依赖）、使用轻量运行时（Python/Node.js 比 Java 更快）、VPC 优化（使用 VPC Endpoint 替代 NAT Gateway）、初始化代码在函数外部（全局变量）。
