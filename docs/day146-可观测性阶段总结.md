### 1. 三大支柱整合

### 2. 信号关联机制

#### 2.1 Trace ID 关联

```
┌─────────────────────────────────────────────────────────────────────┐
│                    信号关联机制 (Trace ID)                            │
│                                                                     │
│  请求流程:                                                          │
│  用户请求 → API Gateway → Service A → Service B → Database         │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │                    Trace (追踪)                               │   │
│  │                                                             │   │
│  │  TraceID: abc123def456                                       │   │
│  │  ├── Span 1: API Gateway (100ms)                            │   │
│  │  │   ├── Span 2: Service A (80ms)                           │   │
│  │  │   │   ├── Span 3: Service B (50ms)                       │   │
│  │  │   │   │   └── Span 4: Database Query (30ms)              │   │
│  │  │   │   └── Span 5: Redis Cache (5ms)                      │   │
│  │  │   └── Span 6: Response Serialization (10ms)              │   │
│  │                                                             │   │
│  │  关键: 每个 Span 都携带 TraceID 和 SpanID                    │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │                    Metrics (指标)                              │   │
│  │                                                             │   │
│  │  http_requests_total{service="A", trace_id="abc123"} = 1    │   │
│  │  http_request_duration_seconds{service="A"} = 0.08          │   │
│  │                                                             │   │
│  │  通过 trace_id 标签关联到具体请求                            │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │                    Logs (日志)                                │   │
│  │                                                             │   │
│  │  {                                                          │   │
│  │    "timestamp": "2026-05-03T10:00:00Z",                     │   │
│  │    "level": "ERROR",                                        │   │
│  │    "service": "service-b",                                  │   │
│  │    "traceID": "abc123def456",    ← 关联 TraceID            │   │
│  │    "spanID": "span3",                                       │   │
│  │    "message": "Database query timeout",                     │   │
│  │    "error": "connection timeout after 30s"                  │   │
│  │  }                                                          │   │
│  │                                                             │   │
│  │  通过 traceID 字段关联到 Trace                               │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  关联路径:                                                          │
│  Metrics (发现异常) → Traces (定位链路) → Logs (查看详情)          │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 2.2 Grafana 关联配置

```yaml
# Grafana 数据源关联配置
# provisioning/datasources/correlated.yml
apiVersion: 1

datasources:
  # Prometheus 数据源
  - name: Prometheus
    type: prometheus
    url: http://prometheus:9090
    isDefault: true
    jsonData:
      httpMethod: POST
      exemplarTraceIdDestinations:
        - name: trace_id
          datasourceUid: Tempo

  # Loki 数据源（关联到 Tempo）
  - name: Loki
    type: loki
    url: http://loki:3100
    jsonData:
      derivedFields:
        # 从日志中提取 TraceID 并关联到 Tempo
        - datasourceUid: Tempo
          matcherRegex: "traceID=(\\w+)"
          name: TraceID
          url: "$${__value.raw}"

  # Tempo 数据源（关联到 Prometheus 和 Loki）
  - name: Tempo
    type: tempo
    url: http://tempo:3200
    jsonData:
      tracesToLogsV2:
        datasourceUid: Loki
        filterByTraceID: true
        filterBySpanID: false
        tags: ['service']
      tracesToMetrics:
        datasourceUid: Prometheus
        tags:
          - key: service
            value: service
        queries:
          - name: 'Request rate'
            query: 'sum(rate(http_requests_total{service="${__tags.service}"}[5m]))'
          - name: 'Error rate'
            query: 'sum(rate(http_errors_total{service="${__tags.service}"}[5m]))'
      serviceMap:
        datasourceUid: Prometheus
      nodeGraph:
        enabled: true
```

### 3. 系统性故障排查方法论

#### 3.1 故障排查流程

```
┌─────────────────────────────────────────────────────────────────────┐
│                    系统性故障排查方法论                                │
│                                                                     │
│  阶段 1: 检测 (Detection)                                           │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  来源: 告警通知 / 用户反馈 / 监控仪表盘                      │   │
│  │                                                             │   │
│  │  关键问题:                                                   │   │
│  │  - 什么指标触发了告警？                                      │   │
│  │  - 影响范围有多大？（单服务/多服务/全局）                     │   │
│  │  - 什么时候开始的？（时间线）                                │   │
│  │  - 是否有相关变更？（部署/配置变更）                         │   │
│  └────────────────────────────┬────────────────────────────────┘   │
│                               │                                     │
│                               ▼                                     │
│  阶段 2: 定位 (Localization)                                        │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  方法: 逐步缩小范围                                         │   │
│  │                                                             │   │
│  │  1. 查看全局仪表盘 → 确定影响的集群/命名空间/服务            │   │
│  │  2. 查看服务级别 RED 指标 → 确定是哪个服务                   │   │
│  │  3. 查看实例级别指标 → 确定是哪个实例                        │   │
│  │  4. 查看追踪 → 确定是哪个操作/依赖                           │   │
│  │  5. 查看日志 → 确定具体错误原因                              │   │
│  └────────────────────────────┬────────────────────────────────┘   │
│                               │                                     │
│                               ▼                                     │
│  阶段 3: 诊断 (Diagnosis)                                           │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  工具: 三大支柱协作                                         │   │
│  │                                                             │   │
│  │  Metrics: CPU/Memory/Disk 使用率是否异常？                   │   │
│  │  Traces: 哪个 Span 耗时最长？是否有错误？                    │   │
│  │  Logs: 错误日志内容是什么？堆栈信息？                        │   │
│  │  Events: K8s 事件是否有 OOM/Eviction/Pending？              │   │
│  └────────────────────────────┬────────────────────────────────┘   │
│                               │                                     │
│                               ▼                                     │
│  阶段 4: 修复 (Resolution)                                          │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  短期修复:                                                   │   │
│  │  - 回滚部署                                                  │   │
│  │  - 扩容资源                                                  │   │
│  │  - 重启服务                                                  │   │
│  │  - 限流/降级                                                 │   │
│  │                                                             │   │
│  │  长期修复:                                                   │   │
│  │  - 修复代码 Bug                                              │   │
│  │  - 优化性能                                                  │   │
│  │  - 调整资源配置                                              │   │
│  │  - 完善监控告警                                              │   │
│  └────────────────────────────┬────────────────────────────────┘   │
│                               │                                     │
│                               ▼                                     │
│  阶段 5: 复盘 (Postmortem)                                          │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  - 时间线回顾                                                │   │
│  │  - 根因分析（5 Whys）                                       │   │
│  │  - 行动项（预防措施）                                        │   │
│  │  - 更新 Runbook                                              │   │
│  │  - 完善监控覆盖                                              │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 3.2 常见故障排查模式

```
┌─────────────────────────────────────────────────────────────────────┐
│                    常见故障排查模式                                    │
│                                                                     │
│  模式 1: 延迟升高                                                    │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  Metrics: P99 延迟上升                                       │   │
│  │  → Traces: 找到慢请求，查看哪个 Span 耗时最长                │   │
│  │  → Logs: 查看该 Span 对应的日志，是否有超时/错误             │   │
│  │  → 确认: 是数据库慢？网络延迟？还是代码逻辑？                │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  模式 2: 错误率上升                                                  │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  Metrics: 5xx 错误率上升                                     │   │
│  │  → Logs: 搜索 ERROR 级别日志，查看错误类型                   │   │
│  │  → Traces: 找到失败请求，查看调用链路                        │   │
│  │  → 确认: 是依赖服务故障？输入校验失败？还是内部错误？        │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  模式 3: 服务不可用                                                  │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  Metrics: 健康检查失败，Pod 重启                             │   │
│  │  → K8s Events: OOMKilled / CrashLoopBackOff                 │   │
│  │  → Logs: 启动日志，是否有初始化错误                          │   │
│  │  → Metrics: 资源使用率，是否超出 Limit                       │   │
│  │  → 确认: 是内存不足？启动失败？还是依赖不可用？              │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  模式 4: 流量异常                                                    │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  Metrics: QPS 突增/突降                                      │   │
│  │  → 上游检查: 是真实流量？还是爬虫/攻击？                     │   │
│  │  → 资源检查: CPU/Memory 是否跟上？                           │   │
│  │  → 依赖检查: 下游服务是否能承受？                            │   │
│  │  → 确认: 需要限流？扩容？还是等待恢复？                      │   │
│  └─────────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────┘
```

### 4. 容量规划

#### 4.1 基于可观测性数据的容量规划

```
┌─────────────────────────────────────────────────────────────────────┐
│                    容量规划方法                                       │
│                                                                     │
│  步骤 1: 收集基线数据                                               │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  历史指标分析（过去 30 天）:                                  │   │
│  │  - CPU 使用率: P50=30%, P95=60%, P99=80%                    │   │
│  │  - Memory 使用率: P50=40%, P95=65%, P99=75%                 │   │
│  │  - QPS: 平均=1000, 峰值=3000, 增长率=15%/月                 │   │
│  │  - Pod 数量: 当前=10, 最大=20                               │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  步骤 2: 预测未来需求                                               │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  线性预测:                                                   │   │
│  │  当前 QPS: 1000, 月增长率: 15%                               │   │
│  │  3 个月后: 1000 × (1.15)^3 ≈ 1521                           │   │
│  │  6 个月后: 1000 × (1.15)^6 ≈ 2313                           │   │
│  │                                                             │   │
│  │  资源需求预测:                                               │   │
│  │  当前 CPU: 4 cores (使用率 60%)                              │   │
│  │  3 个月后: 4 × 1.52 ≈ 6 cores                               │   │
│  │  6 个月后: 4 × 2.31 ≈ 10 cores                              │   │
```

### 5. SLO 驱动告警

#### 5.1 SLO/SLI/SLA 关系

```
┌─────────────────────────────────────────────────────────────────────┐
│                    SLO/SLI/SLA 关系                                  │
│                                                                     │
│  SLA (Service Level Agreement)                                      │
│  ├── 与客户的正式协议                                               │
│  ├── 包含承诺的可用性和性能                                         │
│  └── 违反有商业后果（赔偿等）                                       │
│                                                                     │
│  SLO (Service Level Objective)                                      │
│  ├── 内部目标，比 SLA 更严格                                        │
│  ├── 定义服务的可靠性目标                                           │
│  └── 例: 99.9% 可用性 = 每月允许 43.2 分钟不可用                   │
│                                                                     │
│  SLI (Service Level Indicator)                                      │
│  ├── 衡量 SLO 的具体指标                                           │
│  ├── 例: 请求成功率、延迟 P99、吞吐量                              │
│  └── 通过 Prometheus 指标计算                                      │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  示例:                                                       │   │
│  │  SLA: 承诺 99.9% 可用性                                      │   │
│  │  SLO: 目标 99.95% 可用性（内部更严格）                       │   │
│  │  SLI: 成功率 = 成功请求数 / 总请求数                         │   │
│  │                                                             │   │
│  │  Error Budget: 1 - 0.9995 = 0.05% = 每月 21.6 分钟          │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 5.2 Burn Rate 告警

```
┌─────────────────────────────────────────────────────────────────────┐
│                    Burn Rate (燃烧速率) 告警                          │
│                                                                     │
│  概念: Burn Rate 表示消耗 Error Budget 的速率                        │
│                                                                     │
│  Burn Rate = 实际错误率 / 允许错误率                                 │
│                                                                     │
│  例: SLO = 99.9% (允许错误率 = 0.1%)                                │
│      实际错误率 = 1%                                                 │
│      Burn Rate = 1% / 0.1% = 10x                                    │
│      含义: 以 10 倍速率消耗 Error Budget                             │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  多窗口方法 (Multi-Window, Multi-Burn-Rate)                  │   │
│  │                                                             │   │
│  │  ┌──────────┬────────────┬────────────┬──────────────────┐ │   │
│  │  │ 级别      │ Burn Rate │ 长窗口     │ 短窗口           │ │   │
│  │  ├──────────┼────────────┼────────────┼──────────────────┤ │   │
│  │  │ P1 Critical│ 14.4x    │ 1 小时     │ 5 分钟           │ │   │
│  │  │ P2 Warning │ 6x       │ 6 小时     │ 30 分钟          │ │   │
│  │  │ P3 Info    │ 3x       │ 1 天       │ 2 小时           │ │   │
│  │  │ P4 Low     │ 1x       │ 3 天       │ 6 小时           │ │   │
│  │  └──────────┴────────────┴────────────┴──────────────────┘ │   │
│  │                                                             │   │
│  │  触发条件: 长窗口 AND 短窗口同时满足                         │   │
│  │  长窗口: 检测慢速燃烧（减少噪音）                            │   │
│  │  短窗口: 确认问题仍在持续（快速响应）                        │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  优势:                                                              │
│  ├── 基于用户影响而非任意阈值                                       │
│  ├── 自动平衡灵敏度和噪音                                           │
│  ├── Error Budget 耗尽前触发告警                                    │
│  └── 支持分级响应                                                   │
└─────────────────────────────────────────────────────────────────────┘
```

#### 5.3 SLO 告警 PromQL

```promql
# ===== SLI 定义 =====

# 成功率 SLI
sli:success_rate:ratio_rate5m = 
  sum(rate(http_requests_total{code!~"5.."}[5m]))
  / sum(rate(http_requests_total[5m]))

# 延迟 SLI (P99 < 500ms)
sli:latency_p99:ratio_rate5m = 
  sum(rate(http_request_duration_seconds_bucket{le="0.5"}[5m]))
  / sum(rate(http_request_duration_seconds_bucket{le="+Inf"}[5m]))

# ===== Burn Rate 计算 =====

# SLO 目标: 99.9% (允许错误率 = 0.001)
# 错误率
error_rate = 1 - sli:success_rate:ratio_rate5m

# Burn Rate
burn_rate_5m = error_rate / 0.001
burn_rate_1h = (1 - sli:success_rate:ratio_rate1h) / 0.001
burn_rate_6h = (1 - sli:success_rate:ratio_rate6h) / 0.001

# ===== 多窗口 Burn Rate 告警规则 =====

groups:
  - name: slo_alerts
    rules:
      # 记录规则 - 预计算 SLI
      - record: sli:success_rate:ratio_rate5m
        expr: |
          sum(rate(http_requests_total{code!~"5.."}[5m]))
          / sum(rate(http_requests_total[5m]))

      - record: sli:success_rate:ratio_rate1h
        expr: |
          sum(rate(http_requests_total{code!~"5.."}[1h]))
          / sum(rate(http_requests_total[1h]))

      - record: sli:success_rate:ratio_rate6h
        expr: |
          sum(rate(http_requests_total{code!~"5.."}[6h]))
          / sum(rate(http_requests_total[6h]))

      - record: sli:success_rate:ratio_rate1d
        expr: |
          sum(rate(http_requests_total{code!~"5.."}[1d]))
          / sum(rate(http_requests_total[1d]))

      # P1 Critical: 14.4x Burn Rate, 1h 窗口, 5m 快速确认
      - alert: SLOBurnRateCritical
        expr: |
          (
            1 - sli:success_rate:ratio_rate1h > 14.4 * 0.001
          ) and (
            1 - sli:success_rate:ratio_rate5m > 14.4 * 0.001
          )
        for: 2m
        labels:
          severity: critical
          slo: availability
        annotations:
          summary: "SLO 燃烧速率 Critical: {{ $value | humanizePercentage }} 错误率"
          description: "以 14.4x 速率消耗 Error Budget，1 小时内将耗尽 2% 预算"
          runbook_url: "https://wiki.runbook/slo-critical"

      # P2 Warning: 6x Burn Rate, 6h 窗口, 30m 快速确认
      - alert: SLOBurnRateWarning
        expr: |
          (
            1 - sli:success_rate:ratio_rate6h > 6 * 0.001
          ) and (
            1 - sli:success_rate:ratio_rate30m > 6 * 0.001
          )
        for: 5m
        labels:
          severity: warning
          slo: availability
        annotations:
          summary: "SLO 燃烧速率 Warning: {{ $value | humanizePercentage }} 错误率"
          description: "以 6x 速率消耗 Error Budget，6 小时内将耗尽 5% 预算"

      # Error Budget 剩余量
      - alert: SLOErrorBudgetLow
        expr: |
          (
            1 - avg_over_time(sli:success_rate:ratio_rate5m[30d])
          ) / 0.001 > 0.9
        for: 5m
        labels:
          severity: warning
          slo: availability
        annotations:
          summary: "SLO Error Budget 剩余不足 10%"
          description: "本月 Error Budget 已消耗 90%，请减少变更或提高稳定性"
```

### 练习 2: 配置 SLO 告警

**目标:** 使用 Burn Rate 方法配置 SLO 驱动的告警规则。

```bash
# 步骤 1: 定义 SLI 记录规则
cat <<EOF | kubectl apply -f -
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: slo-recording-rules
  namespace: monitoring
spec:
  groups:
    - name: slo.rules
      interval: 30s
      rules:
        - record: sli:success_rate:ratio_rate5m
          expr: |
            sum(rate(http_requests_total{code!~"5.."}[5m]))
            / sum(rate(http_requests_total[5m]))

        - record: sli:success_rate:ratio_rate30m
          expr: |
            sum(rate(http_requests_total{code!~"5.."}[30m]))
            / sum(rate(http_requests_total[30m]))

        - record: sli:success_rate:ratio_rate1h
          expr: |
            sum(rate(http_requests_total{code!~"5.."}[1h]))
            / sum(rate(http_requests_total[1h]))

        - record: sli:success_rate:ratio_rate6h
          expr: |
            sum(rate(http_requests_total{code!~"6.."}[6h]))
            / sum(rate(http_requests_total[6h]))
EOF

# 步骤 2: 定义 Burn Rate 告警规则
cat <<EOF | kubectl apply -f -
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: slo-burn-rate-alerts
  namespace: monitoring
spec:
  groups:
    - name: slo.burn_rate.alerts
      rules:
        - alert: SLOBurnRateCritical
          expr: |
            (
              1 - sli:success_rate:ratio_rate1h > 14.4 * 0.001
            ) and (
              1 - sli:success_rate:ratio_rate5m > 14.4 * 0.001
            )
          for: 2m
          labels:
            severity: critical
          annotations:
            summary: "SLO 燃烧速率 Critical"

        - alert: SLOBurnRateWarning
          expr: |
            (
              1 - sli:success_rate:ratio_rate6h > 6 * 0.001
            ) and (
              1 - sli:success_rate:ratio_rate30m > 6 * 0.001
            )
          for: 5m
          labels:
            severity: warning
          annotations:
            summary: "SLO 燃烧速率 Warning"
EOF

# 步骤 3: 验证规则
kubectl get prometheusrule -n monitoring
```

## 面试题精选

### 1. 可观测性的三大支柱是什么？它们各自解决什么问题？

**参考答案：**

三大支柱是 Metrics（指标）、Logs（日志）、Traces（链路追踪）。

- **Metrics**：回答"发生了什么"。聚合的数值型时间序列数据，适合趋势分析和告警。如 QPS、错误率、延迟。
- **Logs**：回答"为什么发生"。详细的文本记录，包含上下文和错误堆栈，适合调试和审计。
- **Traces**：回答"在哪里发生"。请求的完整调用链路，跨越多个服务，适合定位分布式系统瓶颈。

三者通过 Trace ID 关联：Metrics 发现异常 → Traces 定位链路 → Logs 查看详情。

### 2. 什么是 Trace ID 关联？如何实现三大支柱的关联？

**参考答案：**

Trace ID 关联是通过在三大支柱中共享相同的 Trace ID 来实现信号间的关联查询。

实现方式：
1. 应用使用 OpenTelemetry SDK，在请求入口生成 Trace ID
2. Trace ID 通过 HTTP Header（如 traceparent）在服务间传播
3. Metrics 指标中添加 trace_id 标签（通过 Exemplar 机制）
4. Logs 日志中记录 traceID 字段
5. Grafana 配置数据源关联，支持从 Metrics → Traces → Logs 下钻

### 3. 什么是 SLO 驱动告警？相比传统阈值告警有什么优势？

**参考答案：**

SLO 驱动告警基于 Error Budget（错误预算）和 Burn Rate（燃烧速率）触发告警，而非任意阈值。

优势：
1. **基于用户影响**：告警反映的是 SLO 违约风险，而非技术指标波动
2. **自动平衡灵敏度**：高 Burn Rate 快速告警，低 Burn Rate 延迟告警
3. **减少噪音**：多窗口方法过滤短暂抖动
4. **分级响应**：不同 Burn Rate 对应不同严重程度
5. **Error Budget 可视化**：团队可以清楚看到可靠性剩余预算

### 4. 什么是 Burn Rate？多窗口方法如何工作？

**参考答案：**

Burn Rate = 实际错误率 / 允许错误率。表示消耗 Error Budget 的速率。

多窗口方法使用长窗口 + 短窗口组合：
- **长窗口**：检测慢速燃烧（减少噪音），如 6 小时
- **短窗口**：确认问题仍在持续（快速响应），如 30 分钟
- **触发条件**：长窗口 AND 短窗口同时满足

例如：6x Burn Rate 告警需要 6 小时窗口内平均 Burn Rate > 6 且 30 分钟窗口内 Burn Rate > 6。

### 5. 如何使用可观测性数据进行容量规划？

**参考答案：**

容量规划步骤：
1. **收集基线**：分析过去 30 天的 CPU/Memory/QPS 等指标的 P50/P95/P99
2. **趋势预测**：使用 `predict_linear()` 预测未来资源需求
3. **设定阈值**：CPU > 70% (P95) 触发扩容告警
4. **制定计划**：水平扩容（HPA）、垂直扩容（VPA）、集群扩容（Cluster Autoscaler）
5. **持续优化**：定期评审资源使用率，调整 Request/Limit

### 6. 可观测性成熟度模型有哪些等级？

**参考答案：**

四个等级：
- **Level 0**：无监控，依赖用户反馈
- **Level 1**：基础监控，有 CPU/内存指标和简单告警
- **Level 2**：标准化监控，统一 Prometheus + Grafana + Alertmanager
- **Level 3**：完整可观测性，三大支柱集成，SLO 驱动告警
- **Level 4**：智能可观测性（AIOps），ML 异常检测，自动修复

评估维度：指标覆盖度、日志集中化、链路追踪率、告警有效性、MTTD/MTTR。

### 7. 故障排查的系统性方法是什么？

**参考答案：**

五个阶段：
1. **检测**：通过告警或监控发现问题，确定影响范围和时间线
2. **定位**：从全局仪表盘逐步缩小到具体服务、实例、操作
3. **诊断**：使用三大支柱协作，Metrics 看趋势，Traces 看链路，Logs 看详情
4. **修复**：短期修复（回滚/扩容）和长期修复（代码/配置优化）
5. **复盘**：时间线回顾、根因分析（5 Whys）、行动项、更新 Runbook

### 8. 如何评估告警的有效性？

**参考答案：**

评估指标：
1. **信噪比**：有效告警 / 总告警 > 80%
2. **MTTD**（Mean Time To Detect）：从问题发生到告警触发的时间
3. **告警疲劳**：团队是否开始忽略告警
4. **覆盖率**：关键场景是否都有告警覆盖
5. **误报率**：告警触发但实际无问题的比例

优化方法：SLO 驱动告警、多窗口 Burn Rate、告警抑制、定期评审删除无用告警。

### 9. 什么是 Error Budget？如何使用它指导运维决策？

**参考答案：**

Error Budget = 1 - SLO 目标。例如 SLO 99.9% 的 Error Budget = 0.1% = 每月 43.2 分钟。

使用方式：
1. **剩余多**：可以积极变更（频繁部署、实验新功能）
2. **剩余少**：保守策略（减少变更、增加 Review、冻结非必要部署）
3. **耗尽**：停止变更，专注稳定性改进
4. **超支**：复盘根因，制定改进计划

Error Budget 将可靠性目标转化为团队可理解的"预算"概念。

### 10. OpenTelemetry 在可观测性中的角色是什么？

**参考答案：**

OpenTelemetry 是 CNCF 的可观测性标准项目，提供：

1. **统一 API**：Metrics、Logs、Traces 的统一采集 API
2. **SDK**：多语言 SDK（Go、Python、Java、Node.js 等）
3. **Collector**：统一的采集、处理、导出管道
4. **协议**：OTLP 协议，厂商中立
5. **自动注入**：支持自动注入 Trace 和 Metrics

角色：作为可观测性的"标准层"，解耦应用代码和后端存储，实现"一次插桩，多处使用"。
