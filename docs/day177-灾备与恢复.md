### 1. RPO 与 RTO

#### 1.1 核心概念

```
┌─────────────────────────────────────────────────────────┐
│                    RPO 与 RTO                            │
│                                                         │
│  RPO (Recovery Point Objective)                         │
│  恢复点目标 - 可以容忍丢失多少数据                        │
│                                                         │
│  ├──── 数据丢失区间 ────┤                                │
│  │                      │                               │
│  最后备份点            故障点            恢复点           │
│  │                      │               │               │
│  ▼                      ▼               ▼               │
│  ───────────────────────────────────────────────→ 时间   │
│                                                         │
│  例：RPO = 1 小时 → 最多丢失 1 小时的数据                │
│                                                         │
│                                                         │
│  RTO (Recovery Time Objective)                          │
│  恢复时间目标 - 恢复服务需要多长时间                      │
│                                                         │
│                        ├──── 恢复区间 ────┤              │
│                        │                 │              │
│                       故障点           恢复完成          │
│                        │                 │              │
│                        ▼                 ▼              │
│  ───────────────────────────────────────────────→ 时间   │
│                                                         │
│  例：RTO = 30 分钟 → 必须在 30 分钟内恢复服务            │
│                                                         │
│                                                         │
│  RPO vs RTO 对比：                                      │
│  ┌────────────────┬────────────────────────────────┐    │
│  │ 指标            │ 含义                          │    │
│  ├────────────────┼────────────────────────────────┤    │
│  │ RPO            │ 能容忍丢失多少数据（向后看）    │    │
│  │ RTO            │ 能容忍停机多久（向前看）        │    │
│  └────────────────┴────────────────────────────────┘    │
└─────────────────────────────────────────────────────────┘
```

#### 1.2 RPO/RTO 与业务的关系

```
┌─────────────────────────────────────────────────────────┐
│              RPO/RTO 与业务影响                           │
│                                                         │
│  ┌────────────┬──────────┬──────────┬─────────────────┐ │
│  │ 业务类型    │ RPO      │ RTO      │ 灾备策略         │ │
│  ├────────────┼──────────┼──────────┼─────────────────┤ │
│  │ 核心交易    │ 0（零丢失）│ < 1 分钟 │ 多活/热备       │ │
│  │ （支付）    │          │          │                  │ │
│  ├────────────┼──────────┼──────────┼─────────────────┤ │
│  │ 核心业务    │ < 5 分钟  │ < 15 分钟│ 热备/温备       │ │
│  │ （订单）    │          │          │                  │ │
│  ├────────────┼──────────┼──────────┼─────────────────┤ │
│  │ 一般业务    │ < 1 小时  │ < 1 小时 │ 温备            │ │
│  │ （用户中心）│          │          │                  │ │
│  ├────────────┼──────────┼──────────┼─────────────────┤ │
│  │ 非核心业务  │ < 24 小时 │ < 4 小时 │ 冷备            │ │
│  │ （报表）    │          │          │                  │ │
│  └────────────┴──────────┴──────────┴─────────────────┘ │
│                                                         │
│  成本关系：                                              │
│  RPO 越小 + RTO 越小 → 成本越高                          │
│                                                         │
│  成本                                                    │
│   ▲                                                     │
│   │  ★ 多活                                             │
│   │     ★ 热备                                          │
│   │        ★ 温备                                       │
│   │           ★ 冷备                                    │
│   └────────────────────────→ 可靠性                     │
│       (RPO/RTO 越小 = 可靠性越高)                        │
└─────────────────────────────────────────────────────────┘
```

### 2. 灾备策略

#### 2.1 灾备策略层次

```
┌─────────────────────────────────────────────────────────┐
│                    灾备策略层次                           │
│                                                         │
│  Level 1: 冷备（Cold Standby）                          │
│  ┌───────────────────────────────────────┐              │
│  │ • 备份站点只有基础设施                  │              │
│  │ • 需要手动启动和部署                   │              │
│  │ • RPO: 小时级  RTO: 小时-天            │              │
│  │ • 成本: 最低（约为主站 10-20%）        │              │
│  │ • 适用: 非核心业务                     │              │
│  └───────────────────────────────────────┘              │
│                                                         │
│  Level 2: 温备（Warm Standby）                          │
│  ┌───────────────────────────────────────┐              │
│  │ • 备份站点有缩减版环境                  │              │
│  │ • 数据实时/准实时同步                   │              │
│  │ • 需要手动切换流量                      │              │
│  │ • RPO: 分钟级  RTO: 分钟-小时           │              │
│  │ • 成本: 中等（约为主站 30-50%）        │              │
│  │ • 适用: 一般业务                       │              │
│  └───────────────────────────────────────┘              │
│                                                         │
│  Level 3: 热备（Hot Standby）                           │
│  ┌───────────────────────────────────────┐              │
│  │ • 备份站点有完整环境，随时可切换        │              │
│  │ • 数据实时同步                         │              │
│  │ • 自动或半自动切换                      │              │
│  │ • RPO: 秒级  RTO: 分钟级               │              │
│  │ • 成本: 较高（约为主站 60-80%）        │              │
│  │ • 适用: 核心业务                       │              │
│  └───────────────────────────────────────┘              │
│                                                         │
│  Level 4: 多活（Active-Active）                         │
│  ┌───────────────────────────────────────┐              │
│  │ • 多个站点同时提供服务                  │              │
│  │ • 数据实时双向同步                      │              │
│  │ • 流量自动分配和切换                    │              │
│  │ • RPO: ~0  RTO: 秒级                   │              │
│  │ • 成本: 最高（约为主站 150-200%）      │              │
│  │ • 适用: 关键业务、金融交易              │              │
│  └───────────────────────────────────────┘              │
└─────────────────────────────────────────────────────────┘
```

### 3. 数据备份策略

#### 3.1 备份类型

```
┌─────────────────────────────────────────────────────────┐
│                    备份类型                               │
│                                                         │
│  全量备份（Full Backup）                                 │
│  ┌───────────────────────────────────────┐              │
│  │ • 备份所有数据                         │              │
│  │ • 恢复最简单                           │              │
│  │ • 耗时最长，占用空间最大               │              │
│  │ • 建议频率：每周一次                   │              │
│  │                                       │              │
│  │ Day1: [████████████████] 全量          │              │
│  └───────────────────────────────────────┘              │
│                                                         │
│  增量备份（Incremental Backup）                          │
│  ┌───────────────────────────────────────┐              │
│  │ • 只备份上次备份后变化的数据           │              │
│  │ • 备份速度快，占用空间小               │              │
│  │ • 恢复需要全量 + 所有增量              │              │
│  │ • 建议频率：每天一次                   │              │
│  │                                       │              │
│  │ Day2: [████] 增量                      │              │
│  │ Day3: [██] 增量                        │              │
│  │ Day4: [██████] 增量                    │              │
│  └───────────────────────────────────────┘              │
│                                                         │
│  差异备份（Differential Backup）                         │
│  ┌───────────────────────────────────────┐              │
│  │ • 备份上次全量备份后所有变化的数据      │              │
│  │ • 备份速度介于全量和增量之间            │              │
│  │ • 恢复只需全量 + 最新差异              │              │
│  │                                       │              │
│  │ Day2: [████] 差异                      │              │
│  │ Day3: [██████] 差异                    │              │
│  │ Day4: [██████████] 差异                │              │
│  └───────────────────────────────────────┘              │
│                                                         │
│  推荐策略：                                              │
│  全量（周日）+ 增量（周一-周六）                          │
│  保留策略：7天日备，4周周备，12月月备                     │
└─────────────────────────────────────────────────────────┘
```

### 4. 恢复演练（GameDay）

```

│  │ • 准备回滚方案                         │              │

#### 4.2 GameDay 演练剧本示例

```markdown
# GameDay 演练剧本：数据库灾难恢复

## 演练信息
| 字段 | 内容 |
|------|------|
| 演练日期 | 2026-05-15 |
| 演练时间 | 14:00-18:00 |
| 演练目标 | 验证 MySQL 主库故障后的恢复能力 |
| RPO 目标 | < 5 分钟 |
| RTO 目标 | < 30 分钟 |
| 指挥官 | Alice |
| 参与人员 | SRE Team, DBA Team |

## 演练场景
模拟华东-1 区域 MySQL 主库故障，需要从备份恢复并切换到华南-1 备用库。

## 演练步骤

### Step 1: 故障注入 (14:00)
```bash
# 模拟主库故障（停止 MySQL 服务）
# 注意：在演练环境中执行
systemctl stop mysql
```

### Step 2: 检测和确认 (14:01-14:05)
```bash
# 确认主库不可用
mysql -h master-db -u root -e "SELECT 1"
# 预期：连接失败

# 检查监控告警
# 确认告警触发
```

### Step 3: 启动恢复流程 (14:05)
```bash
# 切换到备用库
aws rds failover-db-cluster --db-cluster-identifier prod-cluster

# 或者从备份恢复
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier prod-db-restored \
  --db-snapshot-identifier prod-db-snapshot-latest
```

### Step 4: 验证恢复 (14:30)
```bash
# 验证数据库连接
mysql -h restored-db -u root -e "SELECT 1"

# 验证数据完整性
mysql -h restored-db -u root -e "
  SELECT COUNT(*) FROM orders 
  WHERE created_at > DATE_SUB(NOW(), INTERVAL 1 HOUR)
"

# 验证应用连接
curl -s https://api.example.com/health
```

### Step 5: 流量切换 (14:35)
```bash
# 更新 DNS 指向
aws route53 change-resource-record-sets \
  --hosted-zone-id Z1234567890 \
  --change-batch file://dns-change.json

# 验证流量切换
curl -s https://api.example.com/health
```

## 成功标准
- [ ] RPO < 5 分钟（数据丢失 < 5 分钟）
- [ ] RTO < 30 分钟（恢复时间 < 30 分钟）
- [ ] 数据完整性验证通过
- [ ] 服务功能验证通过
- [ ] 监控和告警正常工作
```

### 5. 混沌工程

#### 5.1 混沌工程原理

```
┌─────────────────────────────────────────────────────────┐
│                  混沌工程原理                             │
│                                                         │
│  混沌工程是一种通过实验来发现系统弱点的方法               │
│                                                         │
│  核心理念：                                              │
│  ┌───────────────────────────────────────┐              │
│  │ "在生产环境中注入故障，                  │              │
│  │  验证系统是否如预期般 resilient"        │              │
│  │                                       │              │
│  │ - Netflix Chaos Engineering Principles │              │
│  └───────────────────────────────────────┘              │
│                                                         │
│  实验流程：                                              │
│  ┌───────────────────────────────────────┐              │
│  │ 1. 定义稳态（Steady State）            │              │
│  │    • 系统正常运行时的指标基线          │              │
│  │                                       │              │
│  │ 2. 提出假设                            │              │
│  │    • "注入 X 故障后，系统仍能保持      │              │
│  │      稳态"                             │              │
│  │                                       │              │
│  │ 3. 注入故障                            │              │
│  │    • 模拟真实世界可能发生的故障        │              │
│  │                                       │              │
│  │ 4. 观察结果                            │              │
│  │    • 对比稳态，验证假设                │              │
│  │                                       │              │
│  │ 5. 修复或改进                          │              │
│  │    • 如果假设不成立，改进系统          │              │
│  └───────────────────────────────────────┘              │
└─────────────────────────────────────────────────────────┘
```

#### 5.2 常见混沌实验场景

```yaml
# Chaos Monkey 风格实验配置
chaos_experiments:
  # 实例故障
  - name: "随机终止实例"
    description: "随机终止一个 Pod，验证自愈能力"
    target: "kubernetes"

### 练习 1：设计灾备方案

**场景**：为一个电商系统设计灾备方案。

**已知信息**：
- 日均订单量：10 万
- 峰值 QPS：5000
- 数据库大小：500GB
- 预算：有限

**任务**：
1. 确定各系统的 RPO/RTO
2. 选择合适的灾备策略
3. 设计数据备份方案
4. 制定恢复流程

```python
# disaster_recovery_plan.py

class DisasterRecoveryPlan:
    def __init__(self):
        self.systems = {}
    
    def add_system(self, name, config):
        self.systems[name] = config
    
    def design_plan(self):
        plan = {}
        for name, config in self.systems.items():
            rpo = config['rpo']
            rto = config['rto']
            
            # 根据 RPO/RTO 选择策略
            if rpo <= 0 and rto <= 60:
                strategy = "多活架构"
                cost = "高"
            elif rpo <= 300 and rto <= 900:
                strategy = "热备"
                cost = "中高"
            elif rpo <= 3600 and rto <= 3600:
                strategy = "温备"
                cost = "中"
            else:
                strategy = "冷备"
                cost = "低"
            
            plan[name] = {
                'rpo': rpo,
                'rto': rto,
                'strategy': strategy,
                'cost': cost,
                'backup': self._design_backup(config)
            }
        
        return plan
    
    def _design_backup(self, config):
        data_size = config.get('data_size_gb', 100)
        daily_growth = config.get('daily_growth_gb', 1)
        
        return {
            'full_backup': '每周日全量备份',
            'incremental_backup': '每天增量备份',
            'retention': '7天日备，4周周备，12月月备',
            'storage': f'预计1年存储: {data_size + daily_growth * 365:.0f} GB',
            '异地备份': '跨区域复制'
        }

# 使用示例
plan = DisasterRecoveryPlan()

plan.add_system('支付系统', {
    'rpo': 0,      # 零数据丢失
    'rto': 60,     # 1 分钟恢复
    'data_size_gb': 100,
    'daily_growth_gb': 0.5
})

plan.add_system('订单系统', {
    'rpo': 300,    # 5 分钟
    'rto': 900,    # 15 分钟
    'data_size_gb': 500,
    'daily_growth_gb': 2
})

plan.add_system('用户中心', {
    'rpo': 3600,   # 1 小时
    'rto': 3600,   # 1 小时
    'data_size_gb': 200,
    'daily_growth_gb': 1
})

result = plan.design_plan()

print("=== 灾备方案设计 ===\n")
for system, details in result.items():
    print(f"系统: {system}")
    print(f"  RPO: {details['rpo']}秒")
    print(f"  RTO: {details['rto']}秒")
    print(f"  策略: {details['strategy']}")
    print(f"  成本: {details['cost']}")
    print(f"  备份: {details['backup']['full_backup']}, {details['backup']['incremental_backup']}")
    print()
```

## 🎯 面试题精选

### 面试题 1：什么是 RPO 和 RTO？

**考察点**：对灾备核心概念的理解。

**参考答案要点**：
1. RPO（Recovery Point Objective）：可容忍的最大数据丢失量
2. RTO（Recovery Time Objective）：可容忍的最大恢复时间
3. RPO 向后看（数据丢失），RTO 向前看（恢复时间）
4. RPO/RTO 越小，成本越高

### 面试题 2：冷备、温备、热备、多活有什么区别？

**考察点**：对灾备策略的理解。

**参考答案要点**：
1. 冷备：只有基础设施，RPO/RTO 小时级，成本最低
2. 温备：缩减版环境，RPO/RTO 分钟-小时级，成本中等
3. 热备：完整环境，RPO/RTO 秒-分钟级，成本较高
4. 多活：多站点同时服务，RPO ~0，RTO 秒级，成本最高

### 面试题 3：什么是混沌工程？

**考察点**：对混沌工程的理解。

**参考答案要点**：
1. 通过注入故障来发现系统弱点的方法
2. 核心流程：定义稳态 → 提出假设 → 注入故障 → 观察结果
3. 工具：Chaos Mesh、Litmus、AWS FIS
4. 目标：提高系统的韧性（Resilience）

### 面试题 4：如何设计数据备份策略？

**考察点**：对备份策略的掌握。

**参考答案要点**：
1. 3-2-1 原则：3 份副本、2 种介质、1 份异地
2. 备份类型：全量、增量、差异
3. 保留策略：7天日备、4周周备、12月月备
4. 定期验证备份可恢复性

### 面试题 5：什么是 GameDay？

**考察点**：对恢复演练的理解。

**参考答案要点**：
1. GameDay 是有组织的灾难恢复演练
2. 流程：计划 → 准备 → 执行 → 验证 → 复盘
3. 目的：验证恢复流程、测量实际 RTO/RPO
4. 应定期进行，至少每季度一次

### 面试题 6：多活架构的主要挑战是什么？

**考察点**：对多活架构的深入理解。

**参考答案要点**：
1. 数据一致性（CAP 定理约束）
2. 流量路由（就近访问 + 故障切换）
3. 冲突处理（写入冲突、数据合并）
4. 状态管理（Session、缓存同步）
5. 成本高（需要多套完整环境）
