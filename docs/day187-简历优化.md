### 2. STAR 法则详解

#### 2.1 什么是 STAR 法则

STAR 法则是描述工作经验和项目经历的结构化方法：

```
S - Situation（情境）：当时的背景是什么？面临什么挑战？
T - Task（任务）：你的职责是什么？需要完成什么目标？
A - Action（行动）：你具体做了什么？用了什么技术方案？
R - Result（结果）：最终成果如何？用数据量化！
```

#### 2.2 STAR 法则写作公式

```
在 [S: 什么场景/背景] 下，负责 [T: 什么任务/目标]，
通过 [A: 使用了什么技术/方法/工具]，实现了 [R: 量化成果]。
```

#### 2.3 SRE 场景 STAR 示例

**示例 1：监控体系建设**

```
❌ 错误写法：
"负责公司监控系统的搭建和维护"

✅ STAR 写法：
"S：公司原有监控体系分散（Zabbix + 各业务自建），告警风暴频发，日均告警 500+，
   有效告警率不足 30%，MTTR 平均 60 分钟。
T：需要统一监控平台，消除告警噪音，提升故障发现和定位效率。
A：主导设计并实施统一可观测性平台：
   - 部署 Prometheus + Thanos 集群实现多集群指标采集
   - 搭建 Grafana 统一仪表盘，按业务域划分 20+ 看板
   - 实施告警分级策略（P0-P3）和告警聚合规则
   - 编写 Runbook 自动关联告警与处置手册
   - 接入 PagerDuty 实现 On-Call 轮值自动派单
R：告警数量从日均 500+ 降至 80（有效告警率提升至 92%），
   MTTR 从 60 分钟缩短至 15 分钟，团队加班时长减少 40%。"
```

**示例 2：Kubernetes 集群运维**

```
✅ STAR 写法：
"S：公司核心业务从虚拟机迁移至 Kubernetes，初期集群规模 50 节点，
   频繁出现 Pod OOM、节点 NotReady 等问题，月均故障 8 次。
T：优化集群稳定性，建立标准化运维体系，支撑业务 3 倍增长。
A：
   - 实施资源配额（ResourceQuota）和限制范围（LimitRange）策略
   - 配置 HPA 和 VPA 实现自动弹性伸缩
   - 建立节点健康检查和自动修复机制（Node Problem Detector）
   - 编写 Helm Chart 标准化应用部署流程
   - 搭建 Chaos Engineering 平台定期故障注入测试
R：集群规模扩展至 200 节点，月均故障降至 1 次，Pod 调度成功率 99.8%，
   应用部署时间从 2 小时缩短至 15 分钟。"
```

**示例 3：故障演练与容灾**

```
✅ STAR 写法：
"S：公司缺乏系统性的故障演练机制，多次因上游依赖故障导致全站不可用，
   年度重大事故 5 起，累计影响时长 12 小时。
T：建立故障演练体系，验证系统容灾能力，将年度事故控制在 1 起以内。
A：
   - 引入 ChaosBlade 工具，设计 20+ 故障场景库
   - 建立"演练-发现-修复-验证"闭环流程
   - 推动研发完成核心链路的熔断、降级改造
   - 每月执行一次全链路故障演练
   - 编写应急预案手册并定期更新
R：年度重大事故降至 1 起，平均故障恢复时间从 2.4 小时缩短至 35 分钟，
   系统整体可用性从 99.9% 提升至 99.95%。"
```

### 3. 量化成果的技巧

#### 3.1 SRE 核心量化指标

SRE 面试官最看重的量化指标：

| 指标类别 | 具体指标 | 示例 |
|---------|---------|------|
| 可用性 | SLA/SLO 提升 | 可用性从 99.9% 提升至 99.99% |
| 效率 | MTTR/MTTD 缩短 | MTTR 从 60 分钟降至 15 分钟 |
| 规模 | 管理的节点/服务数 | 管理 500+ 节点 Kubernetes 集群 |
| 成本 | 成本节省比例 | 基础设施成本降低 35% |
| 自动化 | 手动操作减少 | 自动化率从 30% 提升至 85% |
| 部署 | 部署频率/时间 | 部署频率从周级别提升至日级别 |
| 告警 | 告警准确率 | 有效告警率从 30% 提升至 92% |

#### 3.2 如何挖掘量化数据

很多人觉得自己做的事情"没什么好量化的"，以下是挖掘技巧：

```
1. 前后对比法：
   "之前是 XXX，之后变成了 YYY"
   - 之前手动部署需要 2 小时 → 自动化后只需 10 分钟

2. 规模数据法：
   "管理/处理了多少"
   - 管理 200+ 台服务器、50+ 个微服务

3. 频率数据法：
   "做了多少次/多频繁"
   - 日均处理 1000+ 条告警、每月执行 4 次发布

4. 百分比法：
   "提升了/降低了多少百分比"
   - 故障率降低 60%、部署效率提升 80%

5. 时间维度法：
   "节省了多少时间"
   - 每周节省运维工时 20+ 小时

6. 影响范围法：
   "影响了多少用户/业务"
   - 支撑日活 500 万用户的系统稳定运行
```

#### 3.3 量化成果万能句式

```
• 通过 [技术手段]，将 [指标] 从 [X] 提升/降低至 [Y]，提升/降低 [Z]%
• 负责 [规模] 的 [系统/平台]，实现 [SLA/SLO 目标]
• 主导完成 [项目]，[时间范围] 内 [量化成果]
• 独立设计并实施 [方案]，覆盖 [规模]，[量化效果]
• 建立 [体系/流程]，[团队/业务] 的 [指标] 提升 [百分比]
```

### 4. ATS 优化策略

#### 4.1 什么是 ATS

ATS（Applicant Tracking System）是企业用来筛选简历的软件系统。据统计，超过 75% 的简历在到达 HR 之前就被 ATS 过滤掉了。

#### 4.2 ATS 工作原理

```
简历投递 → ATS 解析 → 关键词匹配 → 评分排名 → HR 查看高分简历

ATS 主要检查：
├── 关键词匹配度（最重要）
├── 工作经验年限
├── 学历要求
├── 技能关键词
└── 格式是否可解析
```

#### 4.3 关键词提取技巧

**步骤 1：分析目标 JD**

以一个典型的 SRE 岗位 JD 为例：

```
职位：Senior Site Reliability Engineer
要求：
- 5 年以上 Linux 系统运维或 SRE 工作经验
- 精通 Kubernetes 集群管理和运维
- 熟悉 Prometheus/Grafana 监控体系
- 具备 Terraform/Ansible 等 IaC 工具使用经验
- 熟悉至少一种编程语言（Python/Go 优先）
- 了解 SRE 理论（SLO/SLI/错误预算）
- 有大规模分布式系统运维经验优先
```

**步骤 2：提取关键词**

```
核心关键词（必须出现在简历中）：
Linux, Kubernetes, SRE, Prometheus, Grafana, Terraform, Ansible,
Python, Go, SLO, SLI, 错误预算, 分布式系统

扩展关键词（尽量覆盖）：
Docker, Helm, CI/CD, Jenkins, GitLab CI, AWS, 高可用,
故障排查, 容量规划, 自动化运维, On-Call, 监控告警
```

**步骤 3：将关键词融入简历**

```
❌ 错误做法：在简历末尾堆砌关键词
"关键词：Linux, Kubernetes, Docker, Prometheus..."

✅ 正确做法：在工作经历和技能清单中自然融入
"使用 Terraform 管理 AWS 基础设施，通过 Ansible 实现 200+ 台
 Linux 服务器的自动化配置管理，部署 Prometheus + Grafana 监控体系
 覆盖 50+ Kubernetes 集群..."
```

#### 4.4 ATS 友好格式规范

```
DO（推荐）：
✓ 使用标准字体（宋体/微软雅黑/Arial/Calibri）
✓ 使用标准章节标题（工作经历、教育背景、技能清单）
✓ 使用简单的项目符号（• 或 -）
✓ 保存为 PDF 格式（确保文字可选中）
✓ 文件名格式：姓名_SRE简历_日期.pdf

DON'T（避免）：
✗ 使用表格排版（ATS 可能无法解析）
✗ 使用图片/图标代替文字
✗ 使用页眉页脚放重要信息
✗ 使用特殊字符和 Unicode 符号
✗ 使用简历模板网站的复杂样式
✗ 在 PDF 中嵌入图片导致文字不可选中
```

### 9. 简历常见错误

#### 9.1 十大简历致命错误

```
1. ❌ 没有量化数据
   "负责服务器运维" → 改为 "管理 200+ 台 Linux 服务器，SLA 99.9%"

2. ❌ 技术栈罗列但没有实际经验
   写了 Kubernetes 但面试时说不清楚 Pod 生命周期

3. ❌ 只写职责不写成果
   "负责监控系统的搭建" → 改为 "搭建 Prometheus 监控体系，覆盖 50+ 服务"

4. ❌ 简历太长（超过 3 页）
   精简至 1-2 页，只保留与目标岗位相关的经历

5. ❌ 简历太短（不到 1 页）
   补充项目经历、技术细节、量化成果

6. ❌ 格式混乱
   统一字体、字号、间距、对齐方式

7. ❌ 拼写和语法错误
   至少找 2 个人帮忙检查

8. ❌ 使用通用简历投所有公司
   针对每个 JD 定制简历关键词

9. ❌ 隐私信息泄露
   不要写身份证号、家庭住址等敏感信息

10. ❌ 照片不专业
    如果要放照片，请使用专业证件照
```

### 10. 简历投递策略

#### 10.1 投递时间

```
最佳投递时间：
• 周二至周四（HR 工作日精力最充沛）
• 上午 9:00 - 11:00（HR 开始处理简历）
• 避免周一（积压邮件多）和周五（准备周末）

特殊时间点：
• 金三银四（3-4 月）：跳槽高峰期
• 金九银十（9-10 月）：秋招 + 跳槽
• 年后（2-3 月）：年终奖发完后的跳槽潮
```

#### 10.2 投递数量与质量

```
建议策略：
• 每天投递 5-10 份精选简历（质量 > 数量）
• 每份简历根据 JD 做微调（10-15 分钟/份）
• 记录投递进度表（公司、职位、投递时间、状态）
• 7 天无回复可尝试主动联系 HR
```

## 💻 实战练习

### 练习 1：撰写 SRE 简历

**目标**：根据本日所学，撰写一份完整的 SRE 简历。

**步骤**：

```
1. 选择目标岗位：在招聘网站上选 3 个你感兴趣的 SRE 职位
2. 提取关键词：从每个 JD 中提取核心关键词
3. 撰写简历：
   - 个人简介（3-4 行）
   - 技能清单（按技术域分类）
   - 工作经历（每段 3-5 个 STAR bullet point）
   - 项目经历（2-3 个重点项目）
   - 教育背景和认证
4. 检查清单：
   □ 是否包含目标 JD 的核心关键词？
   □ 每个 bullet point 是否有量化数据？
   □ 是否使用了 STAR 法则？
   □ 格式是否整洁统一？
   □ 是否控制在 2 页以内？
   □ 是否有拼写错误？
```

### 练习 2：STAR 法则改写练习

**目标**：将以下"普通"描述改写为 STAR 格式。

```
原始描述（改写以下 5 条）：
1. "负责公司 Kubernetes 集群的运维工作"
2. "参与了监控系统的建设"
3. "编写了一些自动化脚本"
4. "处理过多次线上故障"
5. "负责服务器的日常管理"

改写要求：
• 每条包含 S、T、A、R 四个要素
• R 部分必须包含量化数据
• 每条控制在 3-4 行
```

### 练习 3：ATS 优化模拟

**目标**：测试简历的 ATS 兼容性。

**步骤**：

```
1. 将简历粘贴到纯文本编辑器，检查是否丢失格式
2. 使用在线 ATS 检测工具（如 jobscan.co）扫描简历
3. 对比 JD 关键词覆盖率，确保 > 70%
4. 检查以下 ATS 友好清单：
   □ 使用标准字体
   □ 无表格嵌套
   □ 无图片/图标
   □ 章节标题使用标准名称
   □ 文件名规范（姓名_职位_日期.pdf）
   □ PDF 文字可选中（非图片格式）
```

### 1. 面试官问："请简单介绍一下你自己"

**回答思路**：这是自我介绍题，控制在 1-2 分钟。

