### 2. 滚动更新（Rolling Update）

#### 2.1 K8s 原生滚动更新

```
┌─────────────────────────────────────────────────────────────────────┐
│                    滚动更新 (Rolling Update)                          │
│                                                                     │
│  时间线:                                                            │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  T0: 初始状态 (3 个旧版本 Pod)                               │   │
│  │  ┌─────┐ ┌─────┐ ┌─────┐                                   │   │
│  │  │ v1  │ │ v1  │ │ v1  │                                   │   │
│  │  └─────┘ └─────┘ └─────┘                                   │   │
│  │  副本数: 3 (全部 v1)                                         │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  T1: 开始更新 (maxSurge=1, maxUnavailable=0)                 │   │
│  │  ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐                           │   │
│  │  │ v1  │ │ v1  │ │ v1  │ │ v2  │ ← 新 Pod 启动              │   │
│  │  └─────┘ └─────┘ └─────┘ └─────┘                           │   │
│  │  副本数: 4 (3 v1 + 1 v2)                                    │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  T2: 新 Pod 就绪，开始替换                                    │   │
│  │  ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐                           │   │
│  │  │ v1  │ │ v1  │ │ v1  │ │ v2  │                           │   │
│  │  └─────┘ └─────┘ └─────┘ └─────┘                           │   │
│  │       ↓                                                     │   │
│  │  ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐                           │   │
│  │  │ v1  │ │ v1  │ │ v2  │ │ v2  │                           │   │
│  │  └─────┘ └─────┘ └─────┘ └─────┘                           │   │
│  │  副本数: 4 (2 v1 + 2 v2) → 逐步替换                         │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  T3: 更新完成                                                │   │
│  │  ┌─────┐ ┌─────┐ ┌─────┐                                   │   │
│  │  │ v2  │ │ v2  │ │ v2  │                                   │   │
│  │  └─────┘ └─────┘ └─────┘                                   │   │
│  │  副本数: 3 (全部 v2)                                         │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  关键参数:                                                          │
│  - maxSurge: 最大超出副本数 (默认 25%)                              │
│  - maxUnavailable: 最大不可用副本数 (默认 25%)                      │
│  - minReadySeconds: Pod 就绪后等待时间                              │
│  - progressDeadlineSeconds: 更新超时时间                            │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 2.2 滚动更新配置

```yaml
# deployment-rolling-update.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  namespace: production
spec:
  replicas: 4
  # 更新策略
  strategy:
    type: RollingUpdate
    rollingUpdate:
      # 最大超出副本数: 允许临时多创建 1 个 Pod
      maxSurge: 1
      # 最大不可用数: 更新过程中始终保证 3 个 Pod 可用
      maxUnavailable: 0
  # 最小就绪时间: Pod 就绪后等待 30s 才认为可用
  minReadySeconds: 30
  # 更新超时: 超过 600s 未完成则判定失败
  progressDeadlineSeconds: 600
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
        version: v2.0.0
    spec:
      containers:
        - name: myapp
          image: myapp:v2.0.0
          ports:
            - containerPort: 8080
          # 健康检查
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 15
            periodSeconds: 10
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /readyz
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 5
            failureThreshold: 3
          # 启动探针（慢启动应用）
          startupProbe:
            httpGet:
              path: /healthz
              port: 8080
            failureThreshold: 30
            periodSeconds: 10
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 256Mi
```

#### 2.3 滚动更新监控

```bash
# 查看部署状态
kubectl rollout status deployment/myapp -n production

# 查看部署历史
kubectl rollout history deployment/myapp -n production

# 暂停部署（发现问题时）
kubectl rollout pause deployment/myapp -n production

# 恢复部署
kubectl rollout resume deployment/myapp -n production

# 回滚到上一版本
kubectl rollout undo deployment/myapp -n production

# 回滚到指定版本
kubectl rollout undo deployment/myapp --to-revision=3 -n production
```

### 3. 蓝绿部署（Blue-Green Deployment）

#### 3.1 蓝绿部署原理

```
┌─────────────────────────────────────────────────────────────────────┐
│                    蓝绿部署 (Blue-Green)                              │
│                                                                     │
│  阶段 1: 蓝色环境运行 (当前生产)                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │                                                             │   │
│  │  用户流量 ──→ Service (selector: version=blue)              │   │
│  │                    │                                        │   │
│  │                    ▼                                        │   │
│  │              ┌──────────┐                                   │   │
│  │              │  Blue    │  ← 当前生产                       │   │
│  │              │  v1.0    │                                    │   │
│  │              │  Pod x3  │                                    │   │
│  │              └──────────┘                                   │   │
│  │                                                             │   │
│  │              ┌──────────┐                                   │   │
│  │              │  Green   │  ← 新版本准备                     │   │
│  │              │  v2.0    │                                    │   │
│  │              │  Pod x3  │                                    │   │
│  │              └──────────┘                                   │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  阶段 2: 测试绿色环境                                               │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  内部测试流量 ──→ Green Service                              │   │
│  │  验证: 健康检查、功能测试、性能测试                          │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  阶段 3: 切换流量到绿色                                             │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │                                                             │   │
│  │  用户流量 ──→ Service (selector: version=green)             │   │
│  │                    │                                        │   │
│  │                    ▼                                        │   │
│  │              ┌──────────┐                                   │   │
│  │              │  Blue    │  ← 旧版本保留（可快速回滚）       │   │
│  │              │  v1.0    │                                    │   │
│  │              │  Pod x3  │                                    │   │
│  │              └──────────┘                                   │   │
│  │                                                             │   │
│  │              ┌──────────┐                                   │   │
│  │              │  Green   │  ← 新生产环境                     │   │
│  │              │  v2.0    │                                    │   │
│  │              │  Pod x3  │                                    │   │
│  │              └──────────┘                                   │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  回滚: 切换 Service selector 回到 version=blue (秒级)              │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 3.2 蓝绿部署实现

```yaml
# blue-deployment.yaml
apiVersion: apps/v1

# green-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-green
  namespace: production
  labels:
    app: myapp
    version: green
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp
      version: green
  template:
    metadata:
      labels:
        app: myapp
        version: green
    spec:
      containers:
        - name: myapp
          image: myapp:v2.0.0
          ports:
            - containerPort: 8080

---
# service.yaml - 切换 selector 实现蓝绿切换
apiVersion: v1
kind: Service
metadata:
  name: myapp
  namespace: production
spec:
  selector:
    app: myapp
    # 切换此行实现蓝绿切换
    version: blue  # 改为 green 即切换到绿色环境
  ports:
    - port: 80
      targetPort: 8080
```

```bash
# 蓝绿切换脚本
#!/bin/bash
# switch-blue-green.sh

NAMESPACE="production"
SERVICE="myapp"
TARGET_VERSION="${1:-green}"

echo "切换 Service ${SERVICE} 到 ${TARGET_VERSION} 版本..."

# 方式 1: 使用 kubectl patch
kubectl patch service ${SERVICE} -n ${NAMESPACE} \
  -p "{\"spec\":{\"selector\":{\"version\":\"${TARGET_VERSION}\"}}}"

# 方式 2: 使用 kubectl apply
kubectl apply -f - <<EOF
apiVersion: v1
kind: Service
metadata:
  name: ${SERVICE}
  namespace: ${NAMESPACE}
spec:
  selector:
    app: myapp
    version: ${TARGET_VERSION}
  ports:
    - port: 80
      targetPort: 8080
EOF

echo "切换完成！当前指向: ${TARGET_VERSION}"

# 验证
kubectl get service ${SERVICE} -n ${NAMESPACE} -o jsonpath='{.spec.selector}'
```

### 4. 金丝雀部署（Canary Deployment）

#### 4.1 金丝雀部署原理

```
┌─────────────────────────────────────────────────────────────────────┐
│                    金丝雀部署 (Canary)                                │
│                                                                     │
│  阶段 1: 部署金丝雀版本 (5% 流量)                                    │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │                                                             │   │
│  │  用户流量 (100%)                                            │   │
│  │       │                                                     │   │
│  │       ▼                                                     │   │
│  │  ┌──────────────┐                                          │   │
│  │  │  Ingress /   │                                          │   │
│  │  │  Gateway     │                                          │   │
│  │  └──────┬───────┘                                          │   │
│  │         │                                                   │   │
│  │    ┌────┴────┐                                              │   │
│  │    │         │                                              │   │
│  │    ▼         ▼                                              │   │
│  │  95%        5%                                              │   │
│  │  ┌─────┐   ┌─────┐                                         │   │
│  │  │v1.0 │   │v2.0 │ ← 金丝雀                               │   │
│  │  │x10  │   │x1   │                                         │   │
│  │  └─────┘   └─────┘                                         │   │
│  │  (稳定版)   (新版本)                                        │   │
│  │                                                             │   │
│  │  监控指标:                                                  │   │
│  │  - 错误率 < 1%                                              │   │
│  │  - P99 延迟 < 500ms                                         │   │
│  │  - CPU/Memory 正常                                          │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  阶段 2: 逐步扩大流量                                               │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  5% → 25% → 50% → 75% → 100%                               │   │
│  │                                                             │   │
│  │  每个阶段:                                                   │   │
│  │  - 等待一段时间（如 5 分钟）                                 │   │
│  │  - 检查指标是否正常                                          │   │
│  │  - 正常 → 扩大流量                                          │   │
│  │  - 异常 → 自动回滚                                          │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  阶段 3: 完成或回滚                                                 │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  成功: v2.0 接管 100% 流量，v1.0 下线                       │   │
│  │  失败: 自动回滚到 v1.0，v2.0 下线                           │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 4.2 Flagger 金丝雀部署

```yaml
# flagger-canary.yaml
apiVersion: flagger.app/v1beta1
kind: Canary
metadata:
  name: myapp
  namespace: production
spec:
  # 目标 Deployment
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp

  # Ingress 配置
  ingressRef:
    apiVersion: networking.k8s.io/v1
    kind: Ingress
    name: myapp

  # HPA 配置
  autoscalerRef:
    apiVersion: autoscaling/v2
    kind: HorizontalPodAutoscaler
    name: myapp

  # 金丝雀分析配置
  analysis:
    # 分析间隔
    interval: 1m
    # 最大流量百分比
    maxWeight: 50
    # 流量步长
    stepWeight: 10
    # 最大失败次数
    threshold: 3
    # 分析次数
    iterations: 5

    # 指标分析
    metrics:
      # 请求成功率
      - name: request-success-rate
        thresholdRange:
          min: 99
        interval: 1m

      # 请求延迟 P99
      - name: request-duration
        thresholdRange:
          max: 500
        interval: 30s

    # Webhook 测试
    webhooks:
      # 负载测试
      - name: load-test
        type: rollout
        url: http://flagger-loadtester.test/
        timeout: 5s
        metadata:
          cmd: "hey -z 1m -q 10 -c 2 http://myapp.production.svc.cluster.local/"
```

#### 4.3 Argo Rollouts 金丝雀部署

```yaml
# argo-rollouts-canary.yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: myapp
  namespace: production
spec:
  replicas: 5
  revisionHistoryLimit: 5
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
        - name: myapp
          image: myapp:v2.0.0
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 256Mi

  strategy:
    canary:
      # 金丝雀步骤
      steps:
        # 步骤 1: 设置权重为 5%
        - setWeight: 5
        # 步骤 2: 等待 5 分钟
        - pause: {duration: 5m}
```

### 6. 健康检查与 Readiness Gates

#### 6.1 三种探针

```
┌─────────────────────────────────────────────────────────────────────┐
│                    Kubernetes 三种探针                                │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  Startup Probe (启动探针)                                    │   │
│  │                                                             │   │
│  │  作用: 检查应用是否启动完成                                  │   │
│  │  时机: 容器启动时，替代 liveness/readiness 直到成功         │   │
│  │  失败: 超过 failureThreshold 后重启容器                     │   │
│  │  场景: 慢启动应用（如 Java、大型应用）                      │   │
│  │                                                             │   │
│  │  优点: 避免慢启动应用被误判为不健康                         │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  Liveness Probe (存活探针)                                   │   │
│  │                                                             │   │
│  │  作用: 检查应用是否还在运行                                  │   │
│  │  时机: 启动探针成功后持续检查                               │   │
│  │  失败: 重启容器                                              │   │
│  │  场景: 死锁检测、内存泄漏检测                               │   │
│  │                                                             │   │
│  │  注意: 不要检查依赖（数据库、外部服务）                     │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  Readiness Probe (就绪探针)                                  │   │
│  │                                                             │   │
│  │  作用: 检查应用是否准备好接收流量                            │   │
│  │  时机: 启动探针成功后持续检查                               │   │
│  │  失败: 从 Service Endpoint 中移除（不接收流量）             │   │
│  │  场景: 预热、依赖检查、负载过高                             │   │
│  │                                                             │   │
│  │  可以检查依赖（数据库连接、缓存预热等）                     │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  执行顺序:                                                          │
│  1. Startup Probe → 成功后不再检查                                 │
│  2. Liveness Probe + Readiness Probe 并行检查                      │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 6.2 探针配置

```yaml
# 完整探针配置示例
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  template:
    spec:
      containers:
        - name: myapp
          image: myapp:v1.0.0

          # 启动探针: 慢启动应用
          startupProbe:
            httpGet:
              path: /healthz
              port: 8080
            # 最多等待 300s (30 * 10s)
            failureThreshold: 30
            periodSeconds: 10

          # 存活探针: 检测死锁
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 0
            periodSeconds: 10
            timeoutSeconds: 5
            failureThreshold: 3
            successThreshold: 1

          # 就绪探针: 检查是否可接收流量
          readinessProbe:
            httpGet:
              path: /readyz
              port: 8080
            initialDelaySeconds: 0
            periodSeconds: 5
            timeoutSeconds: 3
            failureThreshold: 3
            successThreshold: 1

          # 探针类型选择:
          # httpGet: HTTP 端点检查
          # tcpSocket: TCP 端口检查
          # exec: 执行命令检查
          # grpc: gRPC 健康检查

          # TCP 探针示例
          # livenessProbe:
          #   tcpSocket:
          #     port: 3306

          # 命令探针示例
          # livenessProbe:
          #   exec:
          #     command:
          #       - cat
          #       - /tmp/healthy

          # gRPC 探针示例
          # livenessProbe:
          #   grpc:
          #     port: 50051
```

```bash
# 步骤 3: 创建 Service (初始指向蓝色)
kubectl apply -f - <<EOF
apiVersion: v1
kind: Service
metadata:
  name: myapp
spec:
  selector:
    app: myapp
    version: blue
  ports:
    - port: 80
      targetPort: 80

# 步骤 4: 验证当前版本
curl http://myapp | grep nginx

# 步骤 5: 切换到绿色环境

# 步骤 6: 验证切换

# 步骤 7: 回滚到蓝色环境
```

### 练习 3: 金丝雀部署 (Argo Rollouts)

**目标:** 使用 Argo Rollouts 实现金丝雀部署。

```bash
# 步骤 1: 安装 Argo Rollouts
kubectl create namespace argo-rollouts
kubectl apply -n argo-rollouts -f https://github.com/argoproj/argo-rollouts/releases/latest/download/install.yaml

# 步骤 2: 创建 Rollout
cat <<EOF | kubectl apply -f -
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: myapp
spec:
  replicas: 5
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
        - name: myapp
          image: nginx:1.25
          ports:
            - containerPort: 80
  strategy:
    canary:
      steps:
        - setWeight: 20
        - pause: {duration: 1m}
        - setWeight: 40
        - pause: {duration: 1m}
        - setWeight: 60
        - pause: {duration: 1m}
        - setWeight: 80
        - pause: {duration: 1m}
EOF

# 步骤 3: 创建 Service
kubectl apply -f - <<EOF
apiVersion: v1
kind: Service
metadata:
  name: myapp
spec:
  selector:
    app: myapp
  ports:
    - port: 80
      targetPort: 80
EOF

# 步骤 4: 更新镜像触发金丝雀
kubectl argo rollouts set image myapp myapp=nginx:1.26

# 步骤 5: 观察金丝雀过程
kubectl argo rollouts get rollout myapp --watch

# 步骤 6: 手动推进
kubectl argo rollouts promote myapp

# 步骤 7: 回滚
kubectl argo rollouts undo myapp
```

## 面试题精选

### 1. 滚动更新、蓝绿部署和金丝雀部署有什么区别？各适用于什么场景？

**参考答案：**

| 策略 | 原理 | 适用场景 | 优缺点 |
|------|------|----------|--------|
| 滚动更新 | 逐步替换旧 Pod | 常规更新 | 简单但有混合版本期 |
| 蓝绿部署 | 全量切换环境 | 关键服务 | 回滚快但资源翻倍 |
| 金丝雀部署 | 小流量验证后扩大 | 高风险变更 | 风险最低但最复杂 |

选择依据：变更风险、资源预算、回滚速度要求、团队技术能力。

### 2. K8s 滚动更新的 maxSurge 和 maxUnavailable 参数如何影响更新行为？

**参考答案：**

- **maxSurge**：更新过程中允许超出期望副本数的最大值。设为 1 表示更新时最多多创建 1 个 Pod。值越大更新越快，但资源消耗越高。

- **maxUnavailable**：更新过程中允许不可用的最大副本数。设为 0 表示更新过程中始终保证所有副本可用。值越小越安全，但更新越慢。

最佳实践：maxSurge=1, maxUnavailable=0 保证零停机更新。

### 3. 蓝绿部署的优缺点是什么？

**参考答案：**

优点：
- 回滚极快（秒级，仅修改 Service selector）
- 零停机时间
- 新版本可以完整测试后再切换

缺点：
- 资源消耗翻倍（需要同时运行两套环境）
- 数据库迁移复杂（两套环境共享数据库）
- 成本高

### 4. 什么是渐进式交付？与传统部署有什么区别？

**参考答案：**

渐进式交付是将"部署"和"发布"分离的理念：

传统部署：代码部署即发布，所有用户立即看到新版本。
渐进式交付：代码先部署到生产环境，然后逐步向用户发布。

核心特点：
1. 流量百分比控制
2. 指标驱动的自动推进/回滚
3. 最小化爆炸半径
4. 自动化分析

工具：Flagger、Argo Rollouts。

### 5. 如何在金丝雀部署中实现自动回滚？

**参考答案：**

自动回滚通过 AnalysisTemplate 定义指标检查：

1. 定义成功条件：成功率 > 99%、P99 延迟 < 500ms
2. 配置检查间隔和次数
3. 设置 failureLimit（允许失败次数）
4. 工具自动检查指标，不满足条件则回滚

```yaml
analysis:
  metrics:
    - name: success-rate
      successCondition: result[0] >= 0.99
      failureLimit: 2
```

### 6. Kubernetes 的三种探针分别是什么？如何选择？

**参考答案：**

- **Startup Probe**：启动探针，检查应用是否启动完成。适用于慢启动应用（Java、大型应用）。
- **Liveness Probe**：存活探针，检查应用是否还在运行。失败会重启容器。适用于检测死锁。
- **Readiness Probe**：就绪探针，检查应用是否准备好接收流量。失败会从 Endpoint 移除。适用于依赖检查。

选择原则：
- 慢启动应用必须配置 Startup Probe
- Liveness Probe 不要检查外部依赖
- Readiness Probe 可以检查依赖（数据库、缓存）

### 7. 如何选择合适的部署策略？

**参考答案：**

选择矩阵：

| 场景 | 推荐策略 | 原因 |
|------|----------|------|
| 日常更新 | 滚动更新 | 简单、原生支持 |
| 关键服务 | 蓝绿部署 | 快速回滚 |
| 高风险变更 | 金丝雀 | 最小化影响 |
| 性能测试 | 影子部署 | 不影响生产 |
| 用户群体测试 | A/B 测试 | 按条件分流 |

考虑因素：风险级别、资源预算、回滚速度、团队能力、用户影响。

### 8. Readiness Gates 的作用是什么？什么场景需要使用？

**参考答案：**

Readiness Gates 允许自定义 Pod 就绪条件。K8s 原生 Readiness Probe 只检查应用本身，但有些场景需要外部条件：

1. **外部服务依赖**：等待外部 API 就绪
2. **数据库迁移**：等待迁移完成
3. **证书注入**：等待 Sidecar 注入证书
4. **服务网格准备**：等待 Istio/Envoy 配置同步

通过 Readiness Gates，可以确保 Pod 在所有依赖都准备好后才接收流量。

### 9. Argo Rollouts 和 Flagger 有什么区别？

**参考答案：**

| 特性 | Argo Rollouts | Flagger |
|------|---------------|---------|
| CRD | Rollout | Canary |
| 流量管理 | Nginx/Istio/ALB | Nginx/Istio/Linkerd |
| 分析 | AnalysisTemplate | 内置指标分析 |
| 回滚 | 手动/自动 | 自动 |
| 集成 | ArgoCD 生态 | Flux/ArgoCD |
| 学习曲线 | 中等 | 简单 |

选择：如果已用 ArgoCD 生态，选 Argo Rollouts；如果需要简单配置，选 Flagger。

### 10. 如何监控金丝雀部署过程？

**参考答案：**

监控维度：
1. **应用指标**：成功率、延迟、错误率（Prometheus）
2. **资源指标**：CPU、内存、网络（cAdvisor）
3. **业务指标**：订单量、转化率（自定义指标）
4. **部署状态**：Argo Rollouts/Flagger 状态（kubectl argo rollouts get rollout）

Dashboard 设计：
- 对比金丝雀版本和稳定版本的指标差异
- 实时显示流量百分比
- 告警阈值可视化
