## 📖 核心知识点

### 1. 什么是大语言模型（LLM）

#### 1.1 LLM 的本质

大语言模型是基于深度学习的自然语言处理模型，通过在海量文本数据上训练，学习语言的统计规律。其核心能力是：给定一段文本（prompt），预测下一个 token（词或子词）。

```
┌─────────────────────────────────────────────────────────────┐
│                    LLM 工作原理示意                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  输入: "SRE 的核心目标是"                                     │
│         │                                                   │
│         ▼                                                   │
│  ┌─────────────────────────────────────────┐               │
│  │           Transformer 模型               │               │
│  │  ┌───────┐ ┌───────┐ ┌───────┐         │               │
│  │  │Embedding│▶│Attention│▶│ FFN   │         │               │
│  │  └───────┘ └───────┘ └───────┘         │               │
│  │      × N layers (32-128层)               │               │
│  └─────────────────────────────────────────┘               │
│         │                                                   │
│         ▼                                                   │
│  输出概率分布: {"保障": 0.35, "确保": 0.28, "维护": 0.15, ...}│
│         │                                                   │
│         ▼                                                   │
│  采样/贪心 → "保障" → 拼接到输入 → 继续预测                    │
└─────────────────────────────────────────────────────────────┘
```

#### 1.2 关键概念

| 概念 | 说明 | SRE 视角 |
|------|------|----------|
| Token | 模型处理的最小单位，英文约 4 字符，中文约 1-2 字 | 影响计费和延迟 |
| Context Window | 模型一次能处理的最大 token 数 | 决定显存需求 |
| Parameters | 模型权重数量（7B, 13B, 70B） | 决定 GPU 需求 |
| Batch Size | 同时处理的请求数 | 影响吞吐量和延迟 |
| Temperature | 控制输出随机性的参数 | 影响输出质量和一致性 |

### 2. Transformer 架构详解

#### 2.1 整体架构

```
┌─────────────────────────────────────────────────────────────┐
│              Transformer Decoder-Only 架构                    │
│                 (GPT/Llama/Qwen 等)                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  输入 Token IDs: [101, 2003, 1037, 3231, ...]               │
│         │                                                   │
│         ▼                                                   │
│  ┌─────────────────────────────────────────┐               │
│  │        Token Embedding + Position        │               │
│  │     将 token ID 转换为向量 + 位置编码      │               │
│  └─────────────────────────────────────────┘               │
│         │                                                   │
│         ▼                                                   │
│  ┌─────────────────────────────────────────┐               │
│  │          Transformer Block × N           │               │
│  │  ┌───────────────────────────────────┐  │               │
│  │  │  Layer Norm                        │  │               │
│  │  │       │                            │  │               │
│  │  │       ▼                            │  │               │
│  │  │  Multi-Head Self-Attention         │  │               │
│  │  │  (Q, K, V 矩阵运算)                │  │               │
│  │  │       │                            │  │               │
│  │  │       ▼  + 残差连接                 │  │               │
│  │  │  Layer Norm                        │  │               │
│  │  │       │                            │  │               │
│  │  │       ▼                            │  │               │
│  │  │  Feed-Forward Network              │  │               │
│  │  │  (两层全连接 + 激活函数)              │  │               │
│  │  │       │                            │  │               │
│  │  │       ▼  + 残差连接                 │  │               │
│  │  └───────────────────────────────────┘  │               │
│  └─────────────────────────────────────────┘               │
│         │                                                   │
│         ▼                                                   │
│  ┌─────────────────────────────────────────┐               │
│  │        Final Layer Norm + LM Head        │               │
│  │     映射到词表大小的 logits 向量           │               │
│  └─────────────────────────────────────────┘               │
│         │                                                   │
│         ▼                                                   │
│  Softmax → 下一个 token 的概率分布                            │
└─────────────────────────────────────────────────────────────┘
```

#### 2.2 Self-Attention 机制

Self-Attention 是 Transformer 的核心，它让模型能够理解 token 之间的关系。

```
┌─────────────────────────────────────────────────────────┐
│              Self-Attention 计算过程                       │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  输入 X ──┬──▶ Wq ──▶ Q (Query: "我在找什么")             │
│           ├──▶ Wk ──▶ K (Key:   "我能提供什么")           │
│           └──▶ Wv ──▶ V (Value: "我的实际内容")           │
│                                                         │
│  Attention(Q,K,V) = softmax(Q·K^T / √dk) · V           │
│                                                         │
│  步骤:                                                   │
│  1. Q·K^T 计算每对 token 的相关性分数                      │
│  2. 除以 √dk 防止分数过大                                 │
│  3. Softmax 归一化为概率分布                               │
│  4. 用概率对 V 加权求和，得到输出                           │
│                                                         │
│  Multi-Head: 将 Q/K/V 分成多个 head 并行计算               │
│  例: Llama-3-8B 使用 32 个 head，每个 head 维度 128       │
└─────────────────────────────────────────────────────────┘
```

#### 2.3 为什么 SRE 需要理解这些

| 架构特点 | 运维影响 |
|----------|----------|
| 自回归生成（逐 token） | 延迟随输出长度线性增长，需要流式输出 |
| Attention 矩阵大小 O(n²) | 长上下文需要更多显存，KV Cache 是瓶颈 |
| FFN 层参数量大 | 模型体积大，加载时间长 |
| 多头并行计算 | 天然适合 GPU 并行，但需要正确的并行策略 |

#### 3.2 各阶段工程对比

| 维度 | 预训练 | 微调 | 推理 |
|------|--------|------|------|
| **GPU 需求** | 数百-数千张 | 1-8 张 | 1-多张（按需） |
| **数据量** | TB-PB 级 | MB-GB 级 | 实时流式 |
| **耗时** | 周-月 | 小时-天 | 毫秒-秒 |
| **成本** | $100K-$10M+ | $100-$10K | 按 token 计费 |
| **SRE 参与度** | 低（ML 团队主导） | 中（协助部署） | **高（核心职责）** |
| **关键指标** | Loss, Perplexity | Loss, 任务准确率 | TTFT, TPS, 延迟 |
| **扩缩容** | 静态大集群 | 小规模固定 | 动态弹性伸缩 |

### 4. MLOps vs LLMOps

#### 4.1 核心区别

```
┌───────────────────────────────────────────────────────────────┐
│                    MLOps vs LLMOps 对比                        │
├───────────────┬───────────────────┬───────────────────────────┤
│ 维度           │ MLOps             │ LLMOps                    │
├───────────────┼───────────────────┼───────────────────────────┤
│ 模型来源       │ 自己训练           │ 预训练模型 + 微调           │
│ 数据管理       │ 特征工程 + 标注    │ Prompt 工程 + 指令数据      │
│ 训练方式       │ 从头训练           │ 微调 / RLHF / DPO         │
│ 部署目标       │ 模型服务           │ 推理引擎 (vLLM/TGI)       │
│ 资源需求       │ CPU/GPU 混合       │ GPU 密集型                 │
│ 延迟要求       │ 毫秒级             │ 秒级 (流式输出)            │
│ 评估方式       │ 离线指标 (AUC/F1)  │ 在线评估 + 人工评测         │
│ 成本结构       │ 训练成本为主        │ 推理成本为主 (80%+)        │
│ 监控重点       │ 数据漂移, 模型衰减  │ TTFT, TPS, GPU 利用率      │
│ 版本管理       │ 模型版本 + 数据版本  │ 模型 + Prompt + RAG 知识库 │
└───────────────┴───────────────────┴───────────────────────────┘
```

#### 4.2 LLMOps 独有挑战

| 挑战 | 说明 | 传统运维类比 |
|------|------|-------------|
| GPU 显存管理 | 一个 70B 模型需要 140GB+ 显存 | 类似数据库内存管理 |
| KV Cache 爆炸 | 长上下文请求消耗大量显存 | 类似连接池耗尽 |
| 冷启动慢 | 模型加载需要数分钟 | 类似 Java 应用启动 |
| 输出不可控 | 同一输入可能产生不同输出 | 无直接类比 |
| 成本高昂 | 一张 A100 月租 $2000+ | 类似数据库服务器成本 |
| 请求特征差异大 | 短请求 vs 长上下文差异巨大 | 类似大小文件混合 IO |

### 练习 2：LLM 请求生命周期分析

**目标**：编写一个脚本，测量 LLM 推理的关键性能指标。

```python
#!/usr/bin/env python3
"""llm_benchmark.py - LLM 推理性能基准测试"""
import requests
import time
import json
import statistics

OLLAMA_URL = "http://localhost:11434/api/generate"

def benchmark_request(prompt: str, model: str = "llama3:8b") -> dict:
    """发送一个请求并测量性能指标"""
    payload = {
        "model": model,
        "prompt": prompt,
        "stream": True,
    }

    start_time = time.time()
    first_token_time = None
    token_count = 0
    full_response = ""

    response = requests.post(OLLAMA_URL, json=payload, stream=True)
    for line in response.iter_lines():
        if line:
            data = json.loads(line)
            if first_token_time is None:
                first_token_time = time.time()
            token_count += 1
            full_response += data.get("response", "")
            if data.get("done", False):
                break

    end_time = time.time()

    ttft = (first_token_time - start_time) * 1000  # ms
    total_time = (end_time - start_time) * 1000     # ms
    decode_time = (end_time - first_token_time) * 1000 if first_token_time else 0
    tps = (token_count / (decode_time / 1000)) if decode_time > 0 else 0

    return {
        "ttft_ms": round(ttft, 1),
        "total_time_ms": round(total_time, 1),
        "token_count": token_count,
        "tps": round(tps, 1),
        "response_length": len(full_response),
    }

def run_benchmark():
    """运行多轮基准测试"""
    prompts = [
        "What is SRE?",
        "Explain Kubernetes in 3 sentences.",
        "Write a haiku about monitoring.",
        "What are the golden signals in SRE?",
        "Explain the CAP theorem simply.",
    ]

    results = []
    for i, prompt in enumerate(prompts):
        print(f"Running test {i+1}/{len(prompts)}...")
        result = benchmark_request(prompt)
        results.append(result)
        print(f"  TTFT: {result['ttft_ms']}ms, "
              f"Tokens: {result['token_count']}, "
              f"TPS: {result['tps']}")

    # 汇总统计
    ttfts = [r["ttft_ms"] for r in results]
    tps_list = [r["tps"] for r in results]

    print("\n===== Benchmark Summary =====")
    print(f"TTFT  - Avg: {statistics.mean(ttfts):.1f}ms, "
          f"P50: {statistics.median(ttfts):.1f}ms, "
          f"Max: {max(ttfts):.1f}ms")
    print(f"TPS   - Avg: {statistics.mean(tps_list):.1f}, "
          f"Min: {min(tps_list):.1f}, "
          f"Max: {max(tps_list):.1f}")

if __name__ == "__main__":
    run_benchmark()
```

## 🎯 面试题精选

### 1. 什么是 LLM？它与传统 NLP 模型有什么区别？

**参考答案**：
LLM（大语言模型）是参数量通常在数十亿以上的深度学习模型，基于 Transformer 架构，在海量文本上预训练。与传统 NLP 模型的区别：
- **规模**：参数量从百万级跃升到数十亿-数万亿
- **泛化能力**：一个模型可以处理多种 NLP 任务，无需为每个任务训练专门模型
- **涌现能力**：当模型规模超过一定阈值时，出现推理、代码生成等新能力
- **交互方式**：通过自然语言 prompt 交互，而非特征工程 + 分类器
- **资源需求**：需要 GPU 集群，而非单机 CPU

### 2. 解释 Transformer 的 Self-Attention 机制，以及它为什么重要？

**参考答案**：
Self-Attention 让模型在处理每个 token 时，能够"关注"输入序列中的所有其他 token，计算它们之间的相关性。计算过程：Q（查询）和 K（键）的点积得到注意力分数，经 softmax 归一化后与 V（值）加权求和。

重要性：
- 解决了 RNN 的长距离依赖问题，可以并行计算
- 捕捉 token 间的复杂关系（语法、语义、指代等）
- Multi-Head Attention 允许模型同时关注不同类型的关系
- 是 LLM 能理解和生成自然语言的核心机制

### 3. 预训练、微调、推理三个阶段，SRE 最应该关注哪个？为什么？

**参考答案**：
SRE 应最关注**推理**阶段。原因：
- 推理是面向用户的服务，直接影响用户体验和 SLA
- 推理成本占总成本的 80% 以上，是成本优化的重点
- 推理需要 7x24 运维保障，而训练/微调是阶段性的
- 推理的扩缩容、监控、故障排查是 SRE 的核心技能
- SRE 在推理阶段的优化（量化、批处理、缓存）能直接降低业务成本

### 4. LLMOps 与传统 MLOps 有什么区别？请列举至少 5 个方面。

**参考答案**：
1. **资源类型**：LLMOps 几乎完全依赖 GPU，MLOps 可以 CPU/GPU 混合
2. **成本结构**：LLMOps 推理成本占主导（80%+），MLOps 训练成本占主导
3. **延迟特征**：LLM 推理延迟在秒级（流式输出），传统 ML 在毫秒级
4. **评估方式**：LLM 输出难以用传统指标评估，需要人工评测或 LLM-as-judge
5. **扩缩容**：LLM 冷启动慢（分钟级），传统 ML 模型可以秒级启动
6. **数据管理**：LLMOps 关注 Prompt 和 RAG 知识库，MLOps 关注特征工程
7. **版本管理**：LLMOps 需要管理模型 + Prompt + 知识库三个维度

### 5. 为什么 LLM 推理的扩缩容比传统 Web 服务困难得多？

**参考答案**：
- **冷启动时间长**：加载 70B 模型需要 2-5 分钟，而 Web 服务容器启动只需秒级
- **GPU 资源稀缺**：云厂商 GPU 实例启动需要 5-15 分钟，且可能没有库存
- **资源粒度粗**：最小单位是一张 GPU（价值数千美元），不像 CPU 可以细粒度分配
- **显存绑定**：模型必须完整加载到显存中，无法像磁盘 IO 那样灵活
- **请求特征差异大**：一个长上下文请求可能消耗比 100 个短请求更多的资源
- **无法快速释放**：卸载模型再加载的成本极高，不能频繁伸缩

### 6. 什么是 KV Cache？为什么它是 LLM 推理的瓶颈？

**参考答案**：
KV Cache 是 LLM 推理时缓存已计算的 Key 和 Value 矩阵，避免在自回归生成每个新 token 时重新计算所有先前 token 的 K/V。

瓶颈原因：
- 显存占用随序列长度线性增长：对于 70B 模型，128K 上下文的 KV Cache 可达数十 GB
- 不同请求的 KV Cache 大小不同，导致显存碎片化
- 批处理时需要管理多个请求的 KV Cache，调度复杂
- 是限制并发请求数和上下文长度的主要因素

### 7. 作为 SRE，你如何评估一个 LLM 推理服务的健康状态？

**参考答案**：
我会关注以下维度：
- **功能性指标**：TTFT（首 token 延迟）、TPS（每秒 token 数）、端到端延迟
- **资源指标**：GPU 利用率、显存使用率、GPU 温度、功耗
- **可靠性指标**：请求成功率、超时率、OOM 错误率、CUDA 错误率
- **队列指标**：排队请求数、队列等待时间、丢弃请求数
- **业务指标**：QPS、并发用户数、token 消耗量
- **成本指标**：每千 token 成本、GPU 利用效率、$/request

### 8. 描述一下 LLM 推理的 Prefill 和 Decode 两个阶段的区别。

**参考答案**：
- **Prefill 阶段**：处理所有输入 token，计算初始 KV Cache。特点是计算密集，可以高度并行（所有输入 token 同时处理）。延迟与输入长度成正比。决定 TTFT（Time to First Token）。
- **Decode 阶段**：逐个生成输出 token，每步读取完整 KV Cache。特点是内存带宽密集（受显存带宽限制），难以并行。延迟与输出长度成正比。决定 TPS（Tokens Per Second）。

优化方向不同：Prefill 优化关注计算吞吐，Decode 优化关注显存带宽。
