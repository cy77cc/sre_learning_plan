## 📖 核心知识点

### 1. 沟通技巧

#### 1.1 为什么沟通对 SRE 如此重要

```
SRE 的工作本质上是"连接器"：
- 连接开发团队和运维团队
- 连接技术问题和业务影响
- 连接日常操作和战略目标
- 连接个人贡献和团队成果

SRE 沟通场景：
1. 故障沟通：向管理层和用户解释故障影响
2. 技术方案：向非技术人员解释技术决策
3. 跨团队协作：与开发、产品、安全团队协作
4. 事后复盘：主持无指责的复盘会议
5. 向上汇报：向领导汇报工作成果和风险
```

#### 1.2 结构化沟通：金字塔原理

```
金字塔原理（Minto Pyramid）：
- 结论先行：先说结论，再说原因
- 以上统下：上层是下层的总结
- 归类分组：同一层级的内容属于同一范畴
- 逻辑递进：按照逻辑顺序排列

示例：向上汇报

❌ 错误方式（流水账）：
"我们这周处理了 5 个告警，其中 2 个是磁盘空间问题，
1 个是 CPU 使用率高，还有 2 个是网络问题。磁盘问题
是因为日志太多，我们清理了一下。CPU 问题是某个 bug
导致的，已经修复了..."

✅ 正确方式（金字塔结构）：
"本周系统稳定性良好，SLA 达到 99.97%。

主要做了三件事：
1. 处理了 5 个告警，均已解决，无重大影响
2. 优化了日志清理策略，预计每月节省 50GB 存储
3. 修复了一个 CPU 使用率异常的 bug

下一步计划：
- 完善告警规则，减少误报
- 推进自动化日志清理"
```

#### 1.3 故障沟通模板

```
故障沟通模板（面向不同受众）：

面向用户（简短、安抚）：
"我们正在经历服务中断，技术团队正在紧急处理。
预计 XX 分钟内恢复。我们会在状态页面实时更新进展。"

面向管理层（影响、措施）：
"故障概要：
- 时间：2026-05-02 14:30-15:00
- 影响：核心下单功能不可用，影响约 2 万用户
- 根因：数据库连接池耗尽
- 恢复措施：重启应用 + 扩容连接池

改进计划：
- 增加连接池监控告警
- 实现自动扩容机制"

面向技术团队（详细、可操作）：
"故障时间线：
14:30 告警触发：数据库连接数超过阈值
14:35 确认故障：下单接口返回 500
14:40 排查发现：连接池配置不当 + 慢查询
14:50 执行修复：重启应用 + 调整连接池大小
15:00 服务恢复

根因：连接池 max_connections 设置过小（50），
大促期间并发超过连接池上限。

Action Items：
- 张三：调整连接池配置为 200（今天完成）
- 李四：增加连接池使用率监控（本周完成）
- 王五：优化慢查询 SQL（下周完成）"
```

#### 1.4 倾听技巧

```
主动倾听的 SOFTEN 原则：
S - Smile（微笑）
O - Open Posture（开放姿态）
F - Forward Lean（前倾）
T - Touch（适当点头）
E - Eye Contact（眼神交流）
N - Nod（点头回应）

技术沟通中的倾听技巧：
1. 不要急于打断：让对方说完
2. 复述确认："你的意思是...对吗？"
3. 提问澄清："能具体说说...吗？"
4. 记录要点：用笔记本或工具记录
5. 共情回应："我理解你的感受"

避免的沟通陷阱：
❌ "这个很简单，不应该有问题"
❌ "这不是我的责任"
❌ "我早就说过了"
❌ "你不懂技术"
```

#### 1.5 向上管理

```
向上管理的核心：
1. 主动汇报：不要等领导来问
2. 管理预期：提前沟通风险和困难
3. 提供选项：给领导做选择题而非问答题
4. 展示价值：用数据说话

汇报频率建议：
- 日报：关键事项（可选）
- 周报：本周工作 + 下周计划
- 月报：月度总结 + 数据分析
- 季度：OKR 回顾 + 职业发展

向上汇报的 SCR 框架：
S - Situation：当前情况
C - Complication：遇到的挑战
R - Resolution：解决方案和建议

示例：
"S：本周完成了监控系统的升级。
C：升级过程中发现旧版本的告警规则与新版本不兼容。
R：建议投入 2 天时间重新整理告警规则，
   预计可以减少 30% 的误报。需要您审批额外的时间。"
```

### 2. 跨团队协作

#### 2.1 SRE 与开发团队的协作

```
协作模式：

1. 嵌入式（Embedded SRE）
   - SRE 工程师加入开发团队
   - 深度参与开发流程
   - 优点：深度理解业务
   - 缺点：可能失去 SRE 视角

2. 咨询式（Consulting SRE）
   - SRE 作为独立团队
   - 提供技术支持和咨询
   - 优点：保持独立视角
   - 缺点：可能不够深入

3. 工具型（Tooling SRE）
   - SRE 开发内部工具和平台
   - 为开发团队提供自助服务
   - 优点：规模化赋能
   - 缺点：可能脱离实际需求

与开发团队协作的最佳实践：
1. 参与开发团队的 Sprint Planning
2. 共同定义 SLO
3. 提供可观测性工具和最佳实践
4. 参与 Code Review（关注可靠性）
5. 共同处理故障和事后复盘
6. 定期举办可靠性培训
```

#### 2.2 SRE 与产品团队的协作

```
协作要点：

1. SLO 对齐
   - 与产品团队共同定义 SLO
   - 理解业务优先级
   - 用错误预算指导发布决策

2. 发布管理
   - 参与发布计划制定
   - 评估发布风险
   - 制定回滚方案

3. 容量规划
   - 了解业务增长预期
   - 提前规划资源
   - 大促活动保障

沟通话术：
❌ "技术上做不到"
✅ "目前的技术方案需要 XX 资源，预计 XX 时间完成。
   如果时间紧张，我们可以先实现核心功能。"

❌ "这个需求不合理"
✅ "这个需求涉及 XX 风险，我建议我们讨论一下优先级。"
```

#### 2.3 SRE 与安全团队的协作

```
协作领域：

1. 安全合规
   - 安全基线配置
   - 漏洞管理
   - 审计日志

2. 事件响应
   - 安全事件联合响应
   - 安全演练
   - 应急预案

3. 安全左移
   - CI/CD 中集成安全扫描
   - 镜像安全
   - 依赖安全

协作原则：
- 安全不是阻碍，而是保障
- 自动化安全检查
- 平衡安全和效率
```

#### 2.4 跨团队协作工具

```
1. 文档协作
   - Confluence / Notion / 飞书文档
   - 版本控制的文档

2. 项目管理
   - Jira / Linear / 飞书项目
   - 透明的任务看板

3. 即时通讯
   - Slack / 钉钉 / 飞书
   - 频道分组，减少噪音

4. 会议协作
   - 会议纪要
   - Action Items 跟踪
   - 定期同步会议

5. 知识共享
   - 内部 Wiki
   - 技术分享会
   - 跨团队培训
```

### 3. 技术写作

#### 3.1 为什么技术写作很重要

```
技术写作的价值：
1. 知识沉淀：避免知识随人员流失
2. 效率提升：减少重复解答相同问题
3. 质量保障：标准化操作流程
4. 团队协作：统一理解和认知
5. 职业发展：展示技术深度

SRE 常见的写作场景：
- 架构设计文档
- 运维手册 / Runbook
- 故障复盘报告（Postmortem）
- 技术方案文档
- 操作手册 / SOP
- 周报 / 月报
- 技术博客
```

#### 3.2 技术文档的结构

```
标准技术文档结构：

1. 标题和摘要
   - 简洁明了的标题
   - 一段话概述文档内容

2. 背景和目标
   - 为什么写这个文档
   - 要解决什么问题
   - 目标受众是谁

3. 方案设计
   - 整体架构
   - 详细设计
   - 技术选型
   - 流程图 / 架构图

4. 实施计划
   - 时间线
   - 里程碑
   - 资源需求

5. 风险评估
   - 潜在风险
   - 应对措施

6. 附录
   - 参考资料
   - 术语表
   - 配置示例

文档模板示例：

# [项目名称] 技术方案

## 1. 摘要
[一段话概述]

## 2. 背景
### 2.1 现状
[当前系统的问题]

### 2.2 目标
[要达到的效果]

## 3. 方案设计
### 3.1 整体架构
[架构图]

### 3.2 详细设计
[详细说明]

### 3.3 技术选型
[选型对比]

## 4. 实施计划
[时间线和里程碑]

## 5. 风险评估
[风险和应对]

## 6. 附录
[参考资料]
```

#### 3.3 Runbook 写作规范

```
Runbook 是故障处理的操作手册。

Runbook 结构：
1. 告警名称和描述
2. 影响范围
3. 严重等级
4. 排查步骤（编号列表）
5. 修复步骤（编号列表）
6. 验证方法
7. 升级流程
8. 相关链接

示例 Runbook：

# 告警：Pod CrashLoopBackOff

## 描述
Pod 反复崩溃重启，无法正常提供服务。

## 影响
- 该服务的请求会失败
- 可能影响依赖该服务的其他服务

## 严重等级
P1

## 排查步骤
1. 查看 Pod 状态
   $ kubectl describe pod <pod-name>

2. 查看容器日志
   $ kubectl logs <pod-name> --previous

3. 检查资源限制
   $ kubectl top pod <pod-name>

4. 检查事件
   $ kubectl get events --field-selector involvedObject.name=<pod-name>

## 修复步骤
1. 如果是 OOMKilled
   - 增加 memory limits
   - 或优化应用内存使用

2. 如果是应用错误
   - 查看日志定位错误
   - 修复代码或配置

3. 如果是配置错误
   - 检查 ConfigMap/Secret
   - 修正配置

4. 临时缓解
   $ kubectl rollout undo deployment/<deployment-name>

## 验证方法
$ kubectl get pod <pod-name>
$ kubectl logs <pod-name>
$ curl http://<service>/health

## 升级流程
如果 15 分钟内无法解决，升级给团队 Lead。
```

#### 3.4 Postmortem 写作规范

```
Postmortem 的核心原则：
1. 无指责文化（Blameless）
2. 关注系统改进，而非个人责任
3. 事实驱动，数据说话
4. 可执行的改进措施

Postmortem 模板：

# [事故名称] 事后复盘

## 事故概要
| 项目 | 内容 |
|------|------|
| 日期 | YYYY-MM-DD |

| 影响范围 | [受影响的服务/用户] |
| 严重等级 | P0/P1/P2 |
| IC | [Incident Commander] |

## 影响评估
- 受影响用户数：X 万
- 请求失败数：X 万
- 收入影响：约 X 万元

## 时间线
| 时间 | 事件 |
|------|------|
| HH:MM | [事件描述] |
| HH:MM | [事件描述] |

## 根本原因
[详细的技术原因分析]

## 做得好的地方
- [列出做得好的方面]

## 需要改进的地方
- [列出需要改进的方面]

## 改进措施
| 措施 | 负责人 | 截止日期 | 优先级 |
|------|--------|---------|--------|

[总结性的经验教训]

### 4. 演示技巧

#### 4.1 技术演示的准备

```
演示准备清单：

1. 内容准备
   - 明确目标：听众听完后要做什么
   - 了解听众：技术水平、关注点
   - 结构清晰：开头、主体、结尾
   - 准备 Demo：可运行的演示

2. 技术准备
   - 测试 Demo：确保演示时能正常运行
   - 准备备份：录屏或截图
   - 检查网络：确保网络稳定
   - 准备环境：提前登录、准备命令

3. 表达准备
   - 练习演讲：至少练习 3 遍
   - 控制时间：留出提问时间
   - 准备 Q&A：预想可能的问题

演示结构：
1. 开场（2 分钟）
   - 自我介绍
   - 演示背景
   - 核心观点

2. 主体（15-20 分钟）
   - 问题定义
   - 解决方案
   - Demo 演示
   - 关键要点

3. 总结（3 分钟）
   - 核心要点回顾
   - 下一步行动
   - Q&A

演示技巧：
- 控制语速，不要过快
- 使用停顿强调重点
- 与听众保持眼神交流
- 用故事和案例说明
- 准备"救场"方案
```

#### 4.2 Demo 演示技巧

```
Demo 演示的常见问题：
1. 网络问题
2. 环境问题
3. 时间超长
4. 操作失误

避免问题的方法：

1. 准备备份方案
   - 录屏视频
   - 截图
   - 本地环境

2. 简化 Demo
   - 只演示核心功能
   - 避免复杂操作
   - 提前准备好命令

3. 脚本化
   # 准备演示脚本
   #!/bin/bash
   echo "=== Demo 1: 创建 Pod ==="
   kubectl run nginx --image=nginx
   sleep 3
   kubectl get pods
   echo "=== Demo 2: 查看日志 ==="
   kubectl logs nginx

4. 控制节奏
   - 每个步骤后暂停解释
   - 观察听众反应
   - 调整演示速度

5. 处理失败
   - 不要慌张
   - 简单说明问题
   - 切换到备份方案
   - 继续演示
```

### 5. 领导力

#### 5.1 技术领导力的定义

```
技术领导力不是管理职位，而是影响力。

技术领导力的五个维度：

1. 技术深度
   - 深入理解技术原理
   - 能够解决复杂技术问题
   - 持续学习和探索

2. 技术广度
   - 了解相关技术领域
   - 能够做技术选型
   - 理解业务需求

3. 影响力
   - 推动技术决策
   - 帮助他人成长
   - 建立技术标准

4. 沟通能力
   - 清晰表达技术观点
   - 跨团队协作
   - 向上管理

5. 执行力
   - 将想法落地
   - 交付高质量成果
   - 持续改进
```

#### 5.3 如何影响技术决策

```
影响技术决策的方法：

1. 用数据说话
   "根据压测结果，方案 A 的性能比方案 B 高 30%，
    但成本高 20%。建议选择方案 A。"

2. 提供选项
   "有三个方案：
    A. 使用 Kubernetes（推荐，高可用，可扩展）
    B. 使用 Docker Compose（简单，但扩展性差）
    C. 使用虚拟机（传统，但运维成本高）"

3. 评估风险
   "这个方案的主要风险是 XX，我们可以采取以下措施：
    1. XX
    2. XX"

4. 引用最佳实践
   "根据 Google SRE 的最佳实践，建议采用 XX 方案。"

5. 展示成功案例
   "XX 公司采用了类似的方案，效果是 XX。"

6. 小范围验证
   "建议先在测试环境验证，确认效果后再推广。"
```

SRE 职业发展路径：

├── 职责：技术决策、团队指导

├── 职责：技术战略、行业影响

#### 6.2 技术深度 vs 广度

```
T 型人才模型：

广度（了解相关领域）
├── 云计算（AWS/GCP/Azure）
├── 容器编排（K8s/Docker）
├── 监控（Prometheus/Grafana）
├── CI/CD（Jenkins/GitLab CI）
├── 编程（Go/Python/Shell）
└── 网络（TCP/IP/HTTP/DNS）

深度（精通一个领域）
├── 选择一个领域深入
│   ├── Kubernetes 内核
│   ├── 可观测性
│   ├── 混沌工程
│   └── 平台工程
│
├── 学习路径
│   ├── 阅读源码
│   ├── 参与开源
│   ├── 撰写博客
│   └── 技术分享
│
└── 衡量标准
    ├── 能够解决复杂问题
    ├── 能够指导他人
    ├── 能够做技术决策
    └── 能够推动创新

建议：
- 前 3 年：建立广度

## 🎯 面试题精选

### 1. "你如何与开发团队协作确保系统可靠性？"

```
回答框架：
1. 建立协作机制
   "我会与开发团队建立定期沟通机制，比如每周的技术同步会。"

2. 共同定义 SLO
   "我们会一起定义服务的 SLO，确保双方对可靠性目标达成一致。"

3. 提供工具和培训
   "我会为开发团队提供可观测性工具和培训，帮助他们理解系统行为。"

4. 参与 Code Review
   "我会参与代码审查，关注可靠性相关的实践。"

5. 共同处理故障
   "故障发生时，我会与开发团队共同排查和修复。"
```

### 2. "你如何处理与开发团队的意见分歧？"

```
回答框架：
1. 理解对方立场
   "首先，我会认真倾听对方的观点，理解他们的考虑。"

2. 用数据说话
   "我会用数据和事实来支持我的观点，而不是主观判断。"

3. 提供选项
   "我会提供多个方案，列出各自的优缺点。"

4. 小范围验证
   "如果分歧较大，我会建议先在小范围验证。"

5. 达成共识
   "最终目标是达成双方都能接受的共识。"
```

### 3. "你如何向上级汇报技术风险？"

```
回答框架：
1. 明确风险
   "首先，我会明确风险是什么，影响范围有多大。"

2. 量化影响
   "我会用数据量化风险的影响，比如可能的损失。"

3. 提供方案
   "我会提供应对方案，包括短期和长期措施。"

4. 评估成本
   "我会评估不同方案的成本和收益。"

5. 寻求决策
   "最后，我会寻求上级的决策支持。"
```
