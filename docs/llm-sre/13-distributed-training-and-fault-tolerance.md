# LLM SRE 13：分布式训练与容错

## 这篇文档解决什么问题

这篇文档解释分布式训练为什么难以稳定运行，以及平台团队该如何设计编排、checkpoint 和容错策略。重点不在算法原理，而在工程影响：不同并行方式会如何改变网络压力、显存占用、故障半径和恢复路径。

## 系统全景

分布式训练可以拆成三条主线：模型如何切分，作业如何编排，故障后如何恢复。模型切分决定通信模式，编排方式决定 rank 到物理节点的映射，恢复机制决定长作业在真实集群里能否持续推进。

从 SRE 视角看，分布式训练是一类“任何单点抖动都会扩散为全局退化”的系统。一次 NCCL hang、一次慢 checkpoint、一次 spot 驱逐，都可能让数百张 GPU 在数分钟内进入低效甚至空转状态。因此必须把可恢复性设计成默认能力，而不是事后补丁。

## DDP、FSDP、ZeRO、TP、PP、EP 的工程影响

DDP 的优点是心智模型简单，适合中小规模作业，但它需要每个 rank 保存完整模型副本，显存压力较大。FSDP 和 ZeRO 通过参数、梯度和优化器状态分片降低显存占用，让更大模型进入可训练范围，但代价是通信路径更复杂，对网络稳定性和 checkpoint 逻辑要求更高。

TP 会把单层计算切到多卡上，能解决单卡放不下的问题，但显著提升对高速互联和低延迟同步的依赖。PP 通过分层流水化降低单卡压力，却引入 pipeline bubble 和阶段负载均衡问题。EP 则把 MoE expert 分布到不同 rank，带来更高的路由复杂度和更强的尾延迟敏感性。

平台团队不必为每种并行方案做算法级优化，但必须理解它们带来的工程代价：显存压力是否转成网络压力，单机问题是否会升级为全局问题，checkpoint 是聚合保存还是分片保存，恢复时是否需要严格的 world size 一致性。

## rank 拓扑与作业编排

rank 编排不是简单地把进程编号发下去，而是把通信拓扑映射到真实硬件。理想状态下，通信最频繁的 rank 应优先落在 NVLink 域内，其次落在同机架低延迟网络内，最后才跨更远的交换层。错误的 rank 映射会让同样的模型和代码出现完全不同的 step time。

SRE 和平台团队要确保 launcher、调度器和节点标签之间信息一致，包括节点名、机架、GPU 拓扑、网卡能力和故障域。作业编排还要定义 rendezvous 超时、重启上限、失联节点处理方式以及日志归档位置。没有这些约束时，分布式训练故障通常会被误判成“框架偶发不稳定”。

## checkpoint / resume / 断点续训

checkpoint 机制要回答三个问题：保存什么、多久保存一次、恢复时如何校验一致性。对大模型来说，参数、优化器状态、随机数状态、数据游标和并行配置都可能影响 resume 结果。只保存权重而不保存训练上下文，会让恢复后的 loss 曲线出现不可解释跳变。

断点续训能力必须经过真实演练。建议定期做三类验证：正常保存并恢复、故障中断后恢复、变更后向前兼容恢复。平台团队还要关注 checkpoint 粒度与恢复时间的 trade-off。间隔过短会拖慢训练，间隔过长会放大资源浪费和重算时间。

## Spot / preemptible 与容错策略

spot 或 preemptible 资源的价值在于显著降低训练成本，但前提是平台能承受更高的中断概率。它适合具备快速重排、频繁 checkpoint、弹性 world size 或分层容灾能力的作业；不适合完全依赖长时间稳定占用的脆弱训练流程。

常见策略包括：把关键 rank 固定在按需节点，把可弹性部分放到 spot；在收到驱逐信号后立刻触发紧急 checkpoint；使用分阶段作业，把高风险阶段与低风险阶段拆开；为调度器配置抢占后优先恢复策略。核心原则是让中断成为可预算事件，而不是灾难事件。

## 关键指标与告警

分布式训练的关键指标需要比单机训练更强调同步与恢复：

- 通信指标：all-reduce/all-gather 时延，NCCL error/hang 次数，RDMA 重传，跨节点流量分布。
- 训练指标：step time 分位数，straggler rank 比例，global batch 是否稳定，loss 是否异常跳变。
- 恢复指标：checkpoint 时长、checkpoint 失败率、resume 成功率、平均恢复时间。
- 资源指标：每 rank 显存占用、CPU 数据加载瓶颈、网卡带宽、存储吞吐和元数据延迟。

告警上应优先识别“同步异常”和“恢复失效”两类问题，因为它们往往会快速放大为大面积算力浪费。单个 GPU 利用率下降未必严重，但如果伴随 straggler rank 增长和 step time 抖动，就需要尽快介入。

## 典型故障与排查路径

### NCCL hang

表现通常是作业不退出、GPU 利用率下降或部分 rank 卡在 collective。优先检查 rank 是否有单点提前失败、NCCL debug 日志、交换机和网卡错误计数、CUDA stream 阻塞、以及调度器是否把作业落到了异常拓扑。常见根因包括某个 rank OOM 后未被全局感知、RDMA 配置漂移、节点间时钟或网络抖动，以及不兼容的 NCCL/驱动组合。排查时先确认“是通信层 hang，还是上层某个 rank 没有按时进入 collective”，不要一开始就假设是网络故障。

### checkpoint 过慢

表现是 step time 周期性抖动、保存窗口拉长，甚至触发全局超时。优先检查 checkpoint 大小、写入并发度、对象存储或并行文件系统吞吐、元数据服务延迟，以及是否存在大量小文件。常见根因包括全量保存过于频繁、优化器状态过大、共享存储竞争激烈、序列化线程模型低效。解决方向通常是分片保存、异步落盘、本地盘中转或减少非必要状态。

### 节点中途被驱逐

表现可能是 spot 中断通知、节点 NotReady、作业 world size 失配或 launcher 一直等待失联 rank。优先检查云平台驱逐事件、调度器重建行为、最近一次成功 checkpoint 时间和 resume 日志。常见根因包括 spot 容量回收、节点维护、自动扩缩容回收策略不当，以及作业没有为驱逐事件预留缓冲时间。平台侧应验证收到驱逐信号后是否能在窗口内完成保存与退出。

## 设计权衡

更激进的并行方案通常能换来更大模型或更高吞吐，但也会引入更复杂的通信和恢复路径。更频繁的 checkpoint 能降低重算损失，却会抬高 steady-state 开销。更多 spot 资源能降低单次训练成本，却会增加调度抖动和恢复复杂度。

因此，设计时不应只问“最快方案是什么”，而应同时问“故障后还能不能继续推进”。SRE 的职责是让这些 trade-off 可量化，例如用恢复时间、失败半径、单位有效 token 成本来评估架构，而不是只用峰值 samples/s。

## 实践建议

- 先用小规模拓扑做通信和恢复演练，再扩大到完整集群，不要直接在全量 GPU 上试错。
- 对每一种并行配置保留经过验证的环境、launcher 参数和 checkpoint 格式，减少自由组合。
- 把故障注入纳入平台例行验证，例如主动杀掉单个 rank、限速存储、模拟 spot 驱逐。
- 为长作业定义明确的恢复目标，例如最多丢失多少分钟进度、多久内必须恢复成功。
- 用版本化元数据绑定模型、数据、并行策略和 checkpoint 格式，确保恢复与对比都有依据。
