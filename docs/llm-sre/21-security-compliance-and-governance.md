# LLM SRE 21：安全、合规与治理

## 这篇文档解决什么问题

这篇文档讨论 LLM 平台在生产环境中怎样控制访问、阻断滥用、保护敏感数据并建立审计与归因能力。对 AI 系统来说，安全和治理不是上线后的附加项，而是平台能否扩大规模、接入企业数据、支持多租户和通过审计的前提。

很多团队把安全只理解成“把模型接口加鉴权”，但真正的风险分布在整条链路里：谁能访问模型和知识库，谁能触发工具调用，Prompt 注入是否能绕过边界，PII 是否会流入日志，成本是否能按租户追踪，审计是否能解释一次敏感调用。

本文聚焦运行治理与平台边界；[20-rag-agent-and-application-platform.md](./20-rag-agent-and-application-platform.md) 负责 RAG/Agent 运行链路，[18-inference-observability-and-slo.md](./18-inference-observability-and-slo.md) 负责基础可观测性。

## 系统全景

安全与治理要覆盖身份、数据、模型、工具和审计五个面，缺任何一个都容易出现“接口安全，但系统整体不安全”的情况。

```text
用户 / 服务账号 / 租户
        |
        v
身份层：SSO / API Key / OIDC / RBAC / ABAC
        |
        v
控制层：配额 / 限流 / 内容安全 / Prompt Guard / Policy Engine
        |
        v
执行层：LLM / RAG / Agent Runtime / Tool Calling
        |
        +------> 数据资产：文档、向量库、会话状态、日志、训练样本
        |
        +------> 模型资产：基础模型、微调模型、LoRA、Prompt、评测集
        |
        v
审计层：访问日志 / 变更记录 / 成本归因 / 合规报表
```

系统设计要能明确回答：谁可以访问什么资产，谁可以触发什么动作，什么数据可以进入模型，什么数据绝不能进入日志，以及事后如何证明这些边界被执行了。

## 数据与模型资产访问控制

访问控制首先要对资产分类。LLM 平台至少要区分数据资产和模型资产。数据资产包括知识库、用户上传文档、会话历史、评测数据和审计日志；模型资产包括基础模型权重、微调检查点、LoRA 适配器、Prompt 模板和路由配置。

控制策略不应只停留在 API 级别的 RBAC。实践上通常需要组合：

- 身份认证：人类用户走 SSO/OIDC，服务调用走短期凭证或工作负载身份。
- 角色控制：谁能调用生产模型、谁能发布 Prompt、谁能读写向量索引。
- 属性控制：按租户、数据分类、地域、环境和项目进一步限制访问。
- 运行时隔离：生产与测试、在线与离线、租户之间的资源和数据边界。

对模型资产还要建立制品可信链。模型权重、量化产物、LoRA 和 Prompt 不应绕过制品仓库直接上线，否则无法保证版本追踪、签名校验和回滚一致性。

## Prompt 注入、越权调用与内容安全

Prompt 注入的本质，是让模型把不可信输入误当成可信控制指令。RAG 和 agent 场景风险更高，因为恶意指令既可以来自用户，也可以来自被检索到的文档、网页或工具返回值。

防御重点不在某一个“万能检测器”，而在分层边界：

- 输入分层：区分系统提示、开发者提示、用户输入、检索内容和工具输出。
- 权限分层：模型即使看到了某段文本，也不代表它有权限执行对应动作。
- 工具分层：tool calling 必须经过 allowlist、参数校验和最小权限控制。
- 输出分层：对高风险内容、敏感操作建议和外发动作做二次审查。

越权调用通常发生在 agent runtime 里。模型生成的工具参数不能直接视为可信命令，而应经过 policy engine、schema 校验和业务规则检查。否则“模型会不会犯错”就会直接变成“平台会不会误执行”。

内容安全不仅针对违规内容生成，也要覆盖外部内容回传。检索到的恶意网页、带毒文档和伪造工具响应，都可能成为攻击面。SRE 角度要知道内容安全策略放在哪一层、失败时是拒绝、替换还是人工审核。

## 密钥、审计、PII 与合规

密钥管理的目标不是“把密钥放到 Secret 里”这么简单，而是减少长期凭证、缩短暴露窗口并确保轮换可执行。模型 API Key、向量库凭证、第三方工具 token 和对象存储访问密钥，都应纳入统一的发放、轮换和吊销体系。

审计要覆盖三类事件：谁访问了什么，谁改了什么，谁触发了高风险动作。一个可用的审计记录至少应包含身份、租户、模型/数据资产、输入来源、工具调用摘要、策略命中结果、输出去向和成本归因。只记录“调用成功”不足以满足复盘和审计要求。

PII 处理要关注采集、传输、存储、日志和导出五个环节。常见做法包括入口脱敏、字段级标签、日志打码、检索前过滤和训练前清洗。最常见的事故不是模型“主动泄密”，而是平台把原始输入、上下文或工具响应原封不动写进日志和追踪系统。

合规要求会因行业和地域不同而变化，但平台上至少要准备好：数据保留策略、删除与导出能力、访问审计、环境隔离、供应商清单和第三方共享边界。没有这些基础能力时，任何合规承诺都很难落地。

## 多租户隔离与成本归因

多租户治理要同时解决安全隔离和资源公平。常见隔离面包括身份空间、索引空间、对象存储路径、缓存命名空间、会话状态和模型池配额。只做逻辑隔离而没有配额保护时，一个大租户就可能拖垮所有人。

成本归因是治理的一部分，不只是财务报表。平台需要按租户、模型、Prompt、RAG 链路和工具调用统计 token 成本、GPU 占用、embedding 成本和外部 API 成本。没有成本归因，平台很难判断某类请求是否值得继续提供复杂能力。

对共享模型池，建议至少区分：

- 请求成本：输入/输出 token、reranker、embedding、工具调用费用。
- 容量成本：保底 GPU、预热池、缓存占用和跨地域复制。
- 事故成本：fallback 到更贵模型、超量重试、异常回放和评测补跑。

这能帮助团队把“安全隔离”“配额保护”和“成本控制”放在同一治理框架里看。

## 关键指标与告警

| 类别 | 核心指标 | 说明 |
| --- | --- | --- |
| 访问控制 | 鉴权失败率、越权请求数、策略拒绝率 | 发现身份边界是否被探测或绕过 |
| 内容安全 | Prompt 注入命中率、高风险输出拦截率、误杀率 | 判断保护是否有效且不过度 |
| 数据保护 | PII 命中率、日志脱敏失败数、敏感数据导出次数 | 防止泄露路径被忽略 |
| 密钥与审计 | 密钥轮换成功率、过期凭证使用数、审计缺失率 | 确保控制面不是形式化存在 |
| 多租户 | 单租户资源占比、限流命中率、异常成本突增 | 防止热点租户冲垮共享池 |

告警应特别关注“高风险但低频”的事件，例如生产 Prompt 被越权修改、敏感租户索引被跨租户访问、工具调用触发敏感操作、日志中出现未脱敏 PII。这类事件即使量很小，也需要高优先级响应。

## 典型故障与排查路径

| 故障现象 | 优先检查项 | 常见根因 |
| --- | --- | --- |
| 某租户能看到别的租户数据 | 鉴权上下文、过滤条件、索引命名空间、缓存键 | 多租户边界缺失、缓存污染、查询条件丢失 |
| agent 执行了不该执行的工具动作 | 工具 allowlist、schema 校验、策略引擎审计 | 模型输出被直接执行、工具权限过大 |
| 审计日志无法解释一次敏感操作 | trace ID、调用链、变更记录、日志保留策略 | 日志字段不全、跨系统 ID 未贯通 |
| 日志平台出现 PII | 脱敏规则、采样策略、原始 payload 记录点 | 调试日志遗漏脱敏、追踪系统直存输入 |
| 成本突然异常增长 | 租户级 token、fallback 比例、工具调用次数、重试量 | Prompt 膨胀、攻击流量、回退到昂贵模型 |

排查安全事件时要优先保留证据链。先冻结关键日志、配置和制品版本，再执行缓解动作。很多团队在事故处置中先改配置，结果把最重要的审计线索一起覆盖掉。

## 设计权衡

- 更严格的内容安全和工具策略能降低风险，但也可能增加误杀和业务摩擦。
- 更细粒度的 ABAC 和数据标签提高隔离性，但会提高策略维护成本。
- 更全面的审计提升可追溯性，但也会增加存储成本和 PII 暴露面，需要配合脱敏。
- 共享模型池能提高利用率，但多租户隔离和成本归因会更复杂。
- 强制短期凭证和频繁轮换更安全，但控制面成熟度不够时会影响可用性。

治理设计的目标不是把系统变得“绝对安全”，而是在可接受成本下把高风险动作变得可限制、可观察、可追责。

## 实践建议

- 为模型、Prompt、LoRA、向量索引和工具权限建立统一制品与变更审计链。
- 所有 tool calling 默认 deny，显式 allowlist，并做参数级校验和超时限制。
- 对输入、检索内容、工具输出和日志分别做脱敏与风险扫描，不要只扫用户输入。
- 多租户场景至少做到身份隔离、命名空间隔离、配额隔离和成本归因四件事。
- 把安全策略命中、人工放行和误杀复盘接入常规运营，而不是只在审计前临时整理。
