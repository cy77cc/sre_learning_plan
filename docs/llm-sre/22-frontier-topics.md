### 0. 前沿技术成熟度评估框架

在逐一讨论具体技术之前，先建立一个通用评估框架。SRE 视角下的前沿技术评估不只是"它能不能跑起来"，而是"它在生产环境里能不能被可靠地运行"。

#### 成熟度分级

```
┌─────────────────────────────────────────────────────────────────────┐
│                前沿技术成熟度矩阵（SRE 视角）                         │
├─────────┬──────────────┬──────────────┬──────────────┬─────────────┤
│  级别   │   实验室阶段  │   试点阶段   │   平台化阶段  │   常态化阶段 │
├─────────┼──────────────┼──────────────┼──────────────┼─────────────┤
│ 代码    │ 开源 PoC     │ 内部分支     │ 控制面集成    │ 标准 API    │
│ 运维    │ 手动操作     │ 运维剧本初稿 │ 自动化运维    │ 全自愈      │
│ 监控    │ 日志级别     │ 基础指标     │ 分层可观测    │ 联动告警    │
│ 容量    │ 固定配置     │ 手动扩缩     │ 策略驱动     │ 自适应      │
│ 故障    │ 人工排查     │ 已知模式     │ 预案覆盖     │ 自动回退    │
│ 质量    │ 人工抽检     │ 基准测试     │ 持续评测     │ 闭环治理    │
│ 适合    │ 研究团队     │ 早期采用者   │ 主力平台     │ 全量业务    │
└─────────┴──────────────┴──────────────┴──────────────┴─────────────┘
```

#### 五维评估清单

对任何前沿技术，用以下五个维度打分（1-5 分）：

| 维度 | 评估问题 | 权重 |
|------|---------|------|
| 运维就绪度 | 我们能监控它吗？能快速定位问题吗？能自动回退吗？ | 30% |
| 质量保障度 | 有基准测试吗？能量化精度变化吗？有回归检测吗？ | 25% |
| 成本可预测性 | 成本模型清晰吗？有容量基线吗？异常成本能被发现吗？ | 20% |
| 故障隔离性 | 故障会影响多少用户？回退半径多大？有灰度能力吗？ | 15% |
| 团队能力匹配 | 团队理解这项技术吗？排障经验够吗？有外部支持吗？ | 10% |

总分 < 12：继续观察，不要上生产。
12-18：可以在隔离环境试点。
18-22：可以在非关键路径小范围引入。
> 22：可以在关键路径评估引入。

### 1. MoE Serving 与 Expert Parallel

#### 这是什么

MoE（Mixture of Experts，混合专家）是一种模型架构：模型包含多个"专家"子网络，每个请求通过路由器（Router）只激活其中一小部分专家，而不是激活全部参数。

Expert Parallel（专家并行）是 MoE 模型的推理部署策略：把不同专家分布在不同 GPU 上，通过 all-to-all 通信把 token 发送到对应专家所在的设备。

```
┌─────────────────────────────────────────────────────────────────────┐
│                    MoE 架构与 Expert Parallel                       │
│                                                                     │
│  Input Token                                                        │
│      │                                                              │
│      ▼                                                              │
│  ┌────────┐                                                         │
│  │ Router │  ← 门控网络，决定每个 token 发给哪些专家                  │
│  └───┬────┘                                                         │
│      │ 路由决策                                                     │
│      ├────────────────────┬──────────────────┬──────────────┐       │
│      ▼                    ▼                  ▼              ▼       │
│  ┌────────┐          ┌────────┐         ┌────────┐    ┌────────┐   │
│  │Expert 0│          │Expert 1│         │Expert 2│    │Expert N│   │
│  │(GPU 0) │          │(GPU 1) │         │(GPU 2) │    │(GPU N) │   │
│  └───┬────┘          └───┬────┘         └───┬────┘    └───┬────┘   │
│      │                    │                  │              │       │
│      └────────┬───────────┴──────────┬───────┴──────┬──────┘       │
│               ▼                      ▼              ▼               │
│          all-to-all              all-to-all     all-to-all          │
│          通信汇聚                 通信汇聚       通信汇聚             │
│               │                      │              │               │
│               └──────────┬───────────┴──────────────┘               │
│                          ▼                                          │
│                    加权聚合输出                                      │
│                                                                     │
│  关键指标：                                                          │
│  - Expert 命中分布（是否均匀？）                                      │
│  - Router 负载倾斜（是否有热点专家？）                                 │
│  - all-to-all 通信时延（跨节点 vs 节点内）                            │
│  - 单 Expert OOM 率                                                 │
└─────────────────────────────────────────────────────────────────────┘
```

#### 为什么重要

MoE 让模型参数规模继续扩大（数千亿甚至万亿参数），同时把单次推理的计算量控制在可接受范围内。典型 MoE 模型只激活 10%-20% 的参数，因此推理成本远低于同等参数量的稠密模型。

#### 对 SRE / 平台工程的影响

**显存管理更复杂。** 虽然单次推理只激活部分专家，但所有专家的权重都需要常驻显存（或至少可快速加载）。一个 8-expert MoE 模型，即使每个请求只用 2 个专家，8 个专家的权重仍需全部加载到 GPU 上。

**调度复杂度上升。** Expert Parallel 要求把专家分布到多个 GPU 上，且路由决策决定了 token 的流向。调度器需要感知专家分布，避免跨节点通信成为瓶颈。

**故障域更微妙。** 单个 GPU 故障可能只影响部分专家，导致特定模式的请求失败（取决于路由到该专家的概率），而非全局失败。这使得故障检测更困难。

**尾延迟更难控制。** 不同专家的处理时间可能不同，加上路由倾斜，会导致某些请求的延迟显著高于平均值。平均 GPU 利用率会掩盖热点专家的问题。

#### 应该观察哪些指标和信号

| 指标 | 含义 | 告警阈值建议 |
|------|------|-------------|
| expert_hit_distribution | 各专家被命中的比例 | 偏差 > 3x 均值时关注 |
| router_load_skew | 路由器负载倾斜系数 | > 0.7 时告警 |
| all_to_all_latency_p99 | 跨节点 all-to-all 通信 P99 延迟 | > 2ms 时告警 |
| ttft_by_expert | 按专家分组的 TTFT | 单专家 P99 > 2x 均值时关注 |
| expert_oom_rate | 单专家 OOM 率 | > 0.1% 时告警 |
| hot_expert_retry_rate | 热点专家重试率 | > 1% 时告警 |

#### 适用边界

**适合：**
- 有成熟的多 GPU 并行推理基础设施
- 网络拓扑支持高带宽 all-to-all 通信（如 NVLink、InfiniBand）
- 有分布式调度和容错经验
- 模型规模确实需要 MoE 架构来平衡成本

**不适合：**
- 控制面薄弱，无法感知专家分布和路由状态
- 节点间网络不稳定或带宽不足
- 排障能力不足，难以诊断跨节点问题
- 小规模部署，MoE 的复杂度得不偿失

### 2. Ultra-long Context 与 Context Compression

#### 这是什么

Ultra-long context（超长上下文）指模型支持数十万甚至数百万 token 的上下文窗口。Context compression（上下文压缩）是对长上下文进行压缩、摘要或选择性保留的技术，以降低推理成本。

#### 为什么重要

超长上下文能减少对外部检索系统的依赖，把更多原始材料直接放进一次推理中。这对长文档分析、整个代码仓库的问答、多轮复杂会话等场景价值很大。但无限制地使用长上下文会让成本和延迟失控，因此 context compression 成为必要补充。

#### 对 SRE / 平台工程的影响

```
┌─────────────────────────────────────────────────────────────────────┐
│           Ultra-long Context 对推理资源的影响                        │
│                                                                     │
│  上下文长度 ──────────────────────────────────────────────►          │
│                                                                     │
│  Prefill   │████████████████████████████████████████████│            │
│  延迟      │  线性甚至超线性增长                         │            │
│                                                                     │
│  KV Cache  │████████████████████████████████████████████████████│    │
│  占用      │  线性增长，且在整个 Decode 阶段保持             │    │
│                                                                     │
│  排队      │████████████████████████████████│                       │
│  时间      │  长请求占住 GPU 更久，短请求被迫等待            │        │
│                                                                     │
│  成本      │████████████████████████████████████████████████│        │
│  /请求     │  与上下文长度近似线性                         │        │
│                                                                     │
│  关键风险：长请求拖垮整个资源池                                      │
│  ────────────────────────────────────────────────────────────────   │
│  现有扩容/限流/配额模型可能失效：                                    │
│  - 按请求数限流 → 长请求仍独占大量资源                               │
│  - 按固定比例扩容 → 长请求潮涌时容量不足                             │
│  - 统一超时 → 长请求合理但被误杀                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**KV Cache 压力。** 上下文越长，KV Cache 越大。一个 128K token 的请求，KV Cache 可能占用数十 GB 显存，且在整个解码阶段都要保持。

**Prefill 延迟飙升。** 预填充阶段需要处理全部输入 token，延迟与上下文长度近似线性甚至超线性增长。

**资源管理模型失效。** 按请求数的限流、按固定比例的扩容、统一的超时策略，在长上下文场景下都可能失效。

#### 应该观察哪些指标和信号

| 指标 | 含义 | 告警阈值建议 |
|------|------|-------------|
| input_token_distribution | 输入 token 长度分布 | P99 突增时关注 |
| prefill_latency_p99 | 预填充阶段 P99 延迟 | > 10s 时告警 |
| kv_cache_utilization | KV Cache 利用率 | > 85% 时告警 |
| long_request_rejection_rate | 长请求被拒绝的比例 | > 5% 时关注 |
| context_truncation_rate | 上下文被截断的比例 | > 1% 时告警 |
| ttft_by_length_bucket | 按长度分桶的 TTFT | 差异 > 5x 时关注 |

#### 适用边界

**适合：**
- 确实需要原始长材料直接推理的场景（长文档分析、代码仓库级问答）
- 有成熟的 KV Cache 管理和调度能力
- 成本模型已考虑上下文长度差异

**不适合：**
- 问题本应由检索、摘要或流程拆解来解决
- 把超长上下文当作"不需要做 RAG"的捷径
- 资源池规模有限，无法承受长请求的资源波动

### 3. Prefill-Decode Disaggregation（PD 分离）

#### 这是什么

PD 分离是把推理的两个阶段——Prefill（预填充，计算密集）和 Decode（解码，访存密集）——拆分到不同的资源池或不同类型的硬件实例上执行。

```
┌─────────────────────────────────────────────────────────────────────┐
│                    PD 分离架构                                       │
│                                                                     │
│  请求到达                                                            │
│      │                                                              │
│      ▼                                                              │
│  ┌──────────────┐                                                   │
│  │  请求路由器   │  ← 判断请求阶段，分发到对应资源池                  │
│  └──────┬───────┘                                                   │
│         │                                                           │
│    ┌────┴────┐                                                      │
│    ▼         ▼                                                      │
│  ┌──────┐  ┌──────┐                                                 │
│  │Prefill│  │Prefill│   Prefill 资源池                               │
│  │Pool   │  │Pool   │   - 高计算密度 GPU                             │
│  │(GPU A)│  │(GPU B)│   - 可独立扩缩容                               │
│  └──┬───┘  └──┬───┘   - 按计算需求调度                               │
│     │         │                                                     │
│     └────┬────┘                                                     │
│          │ KV Cache + Hidden States 传输                             │
│          │ （通过高速网络或共享存储）                                  │
│          │                                                          │
│     ┌────┴────┐                                                     │
│     ▼         ▼                                                     │
│  ┌──────┐  ┌──────┐                                                 │
│  │Decode │  │Decode │   Decode 资源池                                │
│  │Pool   │  │Pool   │   - 高访存带宽 GPU                             │
│  │(GPU C)│  │(GPU D)│   - 可独立扩缩容                               │
│  └──┬───┘  └──┬───┘   - 按 token 生成需求调度                       │
│     │         │                                                     │
│     └────┬────┘                                                     │
│          ▼                                                          │
│      输出返回                                                        │
│                                                                     │
│  关键 SRE 挑战：                                                     │
│  1. 状态传输可靠性（KV Cache 不丢失）                                 │
│  2. 两个池独立扩缩的协调                                              │
│  3. 故障时的跨阶段恢复                                                │
│  4. 端到端延迟归因（问题在哪个池？）                                   │
└─────────────────────────────────────────────────────────────────────┘
```

#### 为什么重要

Prefill 阶段是计算密集型（大量矩阵乘法处理输入 token），适合高算力 GPU；Decode 阶段是访存密集型（逐 token 生成，瓶颈在显存带宽），适合高带宽 GPU。把它们混在同一实例上，两种特性无法同时优化。

分离后可以：
- 用不同类型的硬件分别优化两个阶段
- 独立扩缩容（Prefill 池按并发请求数扩，Decode 池按活跃 token 数扩）
- 更精确的成本归因

#### 对 SRE / 平台工程的影响

**状态传输是关键路径。** Prefill 完成后，KV Cache 和 hidden states 需要传输到 Decode 池。这个传输的延迟、带宽和可靠性直接影响端到端体验。传输失败意味着需要重新 Prefill。

**观测面需要拆分。** TTFT 变慢时，需要判断问题在 Prefill 池（计算慢）、状态传输（网络慢）还是 Decode 池（排队久）。原先统一的推理延迟指标不再够用。

**调度策略更复杂。** 调度器需要同时感知两个池的状态，且要考虑"哪个 Prefill 实例的结果送到哪个 Decode 实例"的亲和性。

**故障恢复更难。** Prefill 完成但 Decode 实例故障时，需要决定是重做 Prefill 还是把 KV Cache 转移到另一个 Decode 实例。

#### 应该观察哪些指标和信号

| 指标 | 含义 | 告警阈值建议 |
|------|------|-------------|
| prefill_queue_depth | Prefill 队列深度 | > 100 时告警 |
| decode_queue_depth | Decode 队列深度 | > 200 时告警 |
| state_transfer_latency_p99 | 状态传输 P99 延迟 | > 50ms 时告警 |
| state_transfer_failure_rate | 状态传输失败率 | > 0.5% 时告警 |
| prefill_gpu_utilization | Prefill 池 GPU 利用率 | < 30% 或 > 90% 时关注 |
| decode_gpu_utilization | Decode 池 GPU 利用率 | < 30% 或 > 90% 时关注 |
| e2e_ttft_breakdown | 端到端 TTFT 分段归因 | 任一段 > 60% 时关注 |

#### 适用边界

**适合：**
- 大规模推理平台，请求量足够让两个池都保持合理利用率
- 异构资源池（有不同类型 GPU 可用）
- 已有稳定的分阶段指标和排障能力
- 网络基础设施支持低延迟大带宽状态传输

**不适合：**
- 实例数少，拆分后每个池的利用率太低
- 控制面简单，无法维护两套调度和监控
- 还没有稳定的分阶段指标，连"慢在哪"都判断不了
- 网络条件不允许低延迟状态传输

### 4. SGLang 与结构化生成 Runtime

#### 这是什么

SGLang 是一种结构化生成运行时，核心特性包括 RadixAttention（基于基数树的 KV Cache 复用）和受约束解码（constrained decoding）。它让模型输出严格遵循 JSON schema、函数签名或其他结构化格式。

#### 为什么重要

Agent 和工作流场景要求模型输出稳定、可解析。自由格式的文本输出无法被程序可靠消费。结构化生成通过在解码时施加约束（如 JSON schema），确保输出格式正确。

RadixAttention 通过基数树结构管理 KV Cache 的前缀共享，让多个请求共享公共前缀的 KV Cache，显著减少重复计算。

#### 对 SRE / 平台工程的影响

**引擎选型更复杂。** SGLang vs vLLM vs TensorRT-LLM，各有侧重。SGLang 在结构化生成和前缀复用上有优势，但在通用场景下不一定最优。

**故障模式更多样。** 故障不再只是"模型慢"或"模型报错"，还可能是：结构化输出失真（格式对但内容错）、schema 校验失败、约束解码导致的回退和重试、运行时状态机卡死。

**缓存策略更精细。** RadixAttention 的缓存命中率直接影响性能，需要监控基数树的命中率和驱逐率。

#### 应该观察哪些指标和信号

| 指标 | 含义 | 告警阈值建议 |
|------|------|-------------|
| structured_output_success_rate | 结构化输出成功率 | < 99% 时告警 |
| schema_validation_failure_rate | Schema 校验失败率 | > 1% 时告警 |
| constrained_decoding_fallback_rate | 约束解码回退率 | > 2% 时告警 |
| radix_cache_hit_rate | RadixAttention 缓存命中率 | < 50% 时关注 |
| runtime_state_machine_stall | 运行时状态机卡死事件 | 任何发生时告警 |
| per_step_latency_p99 | 单步骤耗时 P99 | > 基线 2x 时告警 |

#### 适用边界

**适合：**
- 需要稳定结构化输出的 Agent 和工作流场景
- 多请求共享公共前缀（如系统 prompt）的工作负载
- 能接受运行时层额外复杂度的团队

**不适合：**
- 只做简单聊天、不需要结构化输出的接口
- 不愿意引入额外运行时依赖的极简架构
- 对约束解码带来的延迟开销敏感的场景

---

### 5. FP8/INT4 低精度推理

#### 这是什么

FP8（8 位浮点）和 INT4（4 位整数）是比传统 FP16/BF16 更低精度的数值表示方式。通过量化（quantization），把模型权重和激活值从高精度转换为低精度，以减少显存占用和提升计算吞吐。

```
┌─────────────────────────────────────────────────────────────────────┐
│                量化精度 vs 性能权衡                                  │
│                                                                     │
│  精度        FP32 ──► BF16/FP16 ──► FP8 ──► INT4                   │
│                                                                     │
│  显存占用    ████████████████████  100%                              │
│             ██████████            50%                               │
│             ██████                31%                               │
│             ███                   19%                               │
│                                                                     │
│  推理速度    ████                  基线                              │
│             ████████              ~2x                               │
│             ██████████████        ~3-4x（硬件依赖）                  │
│             ████████████████      ~4-5x（硬件依赖）                  │
│                                                                     │
│  精度损失    ▏  基线               无                                │
│             ▎  微小               可接受                             │
│             █  明显               需要评测                           │
│             ██ 显著               高风险                             │
│                                                                     │
│  关键：量化不是免费午餐，精度损失需要量化验证（pun intended）         │
└─────────────────────────────────────────────────────────────────────┘
```

#### 为什么重要

低精度推理直接影响成本密度。同样一张 GPU，FP8 可能跑比 FP16 大一倍的模型，或者开两倍的副本。对于成本敏感的推理平台，这是显著的杠杆。

#### 对 SRE / 平台工程的影响

**模型验证成为必经流程。** 每次量化后都必须跑完整的质量评测，确认精度损失在可接受范围内。这不只是"跑几个例子看看"，而是需要系统化的基准测试和回归检测。

**制品管理更复杂。** 同一个模型可能有 FP16、FP8、INT4 多个版本，每个版本适用于不同场景。制品仓库需要管理多个精度版本及其对应的评测结果。

**硬件兼容性差异。** 不同 GPU 对低精度的支持程度不同。FP8 在 H100 上原生支持，但在 A100 上需要软件模拟。INT4 在消费级 GPU 上可能表现不稳定。

**回退策略必要。** 量化模型在特定输入上可能出现异常输出，需要有快速回退到高精度版本的能力。

#### 应该观察哪些指标和信号

| 指标 | 含义 | 告警阈值建议 |
|------|------|-------------|
| ttft_after_quantization | 量化后 TTFT 变化 | 退化 > 20% 时关注 |
| tpot_after_quantization | 量化后 TPOT 变化 | 退化 > 20% 时关注 |
| memory_savings | 显存节省比例 | 记录基线 |
| oom_rate_after_quantization | 量化后 OOM 率 | > 0.1% 时告警 |
| quality_regression_score | 输出质量回归分数 | < 基线 95% 时告警 |
| fallback_to_high_precision_rate | 回退到高精度的比例 | > 5% 时关注 |
| complaint_rate_by_model_version | 按模型版本分组的投诉率 | 差异 > 2x 时关注 |

#### 适用边界

**适合：**
- 成本敏感或显存受限的场景
- 已建立完整的量化评测流水线
- 模型对精度损失有较好容错性（如对话、摘要）
- 有快速回退到高精度的能力

**不适合：**
- 高风险任务（医疗、法律、金融）在未充分评测前直接全量切换
- 模型对精度极度敏感（如数学推理、代码生成）
- 没有系统化的质量评测流程

### 6. Inference Cache Hierarchy

#### 这是什么

推理缓存分层是指在推理链路中建立多级缓存体系，从 GPU HBM（高带宽显存）到 CPU DRAM（系统内存）到 SSD（固态硬盘），不同层级有不同的容量、延迟和成本特征。

```
┌─────────────────────────────────────────────────────────────────────┐
│                Inference Cache Hierarchy                            │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  L1: GPU HBM                                                │   │
│  │  ┌───────────────────────────────────────────────────────┐  │   │
│  │  │ 容量: 40-192 GB/GPU     延迟: ~1μs    成本: $$$$       │  │   │
│  │  │ 内容: 活跃 KV Cache, 权重, 当前请求状态               │  │   │
│  │  │ 命中: 直接参与计算                                      │  │   │
│  │  └───────────────────────────────────────────────────────┘  │   │
│  └─────────────────────────────────────────────────────────────┘   │
│           │ Miss（驱逐/换出）                                       │
│           ▼                                                        │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  L2: CPU DRAM                                               │   │
│  │  ┌───────────────────────────────────────────────────────┐  │   │
│  │  │ 容量: 256GB-2TB/节点    延迟: ~100μs   成本: $$$       │  │   │
│  │  │ 内容: 近期 KV Cache, 前缀缓存, 权重缓存               │  │   │
│  │  │ 命中: 需要 PCIe 传输回 GPU                             │  │   │
│  │  └───────────────────────────────────────────────────────┘  │   │
│  └─────────────────────────────────────────────────────────────┘   │
│           │ Miss（驱逐/换出）                                       │
│           ▼                                                        │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  L3: SSD / NVMe                                             │   │
│  │  ┌───────────────────────────────────────────────────────┐  │   │
│  │  │ 容量: 数TB/节点         延迟: ~1ms     成本: $$        │  │   │
│  │  │ 内容: 冷 KV Cache, 量化权重快照, 模型 checkpoint      │  │   │
│  │  │ 命中: 需要完整加载路径                                  │  │   │
│  │  └───────────────────────────────────────────────────────┘  │   │
│  └─────────────────────────────────────────────────────────────┘   │
│           │ Miss（驱逐/换出）                                       │
│           ▼                                                        │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  L4: 分布式存储 / 对象存储                                   │   │
│  │  ┌───────────────────────────────────────────────────────┐  │   │
│  │  │ 容量: 无限        延迟: ~10-100ms    成本: $           │  │   │
│  │  │ 内容: 模型权重, 全量 checkpoint, 评测数据集            │  │   │
│  │  │ 命中: 冷启动加载                                        │  │   │
│  │  └───────────────────────────────────────────────────────┘  │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  各层 SRE 关注点：                                                  │
│  L1 → 容量规划、驱逐策略、碎片化                                    │
│  L2 → PCIe 带宽瓶颈、换入换出频率                                   │
│  L3 → SSD 寿命、IOPS 上限                                          │
│  L4 → 冷启动延迟、带宽成本                                          │
└─────────────────────────────────────────────────────────────────────┘
```

#### 为什么重要

缓存命中直接影响 TTFT、吞吐和成本。很多推理优化收益并不是来自模型更快，而是来自避免重复计算和重复 I/O。一个良好的缓存分层体系可以让共享相同前缀的请求复用 KV Cache，把 TTFT 从秒级降到毫秒级。

#### 对 SRE / 平台工程的影响

**缓存成为一级运行对象。** 缓存不再只是性能优化手段，而是一级运行对象，有自己的容量、命中率、驱逐率和一致性问题。

**驱逐策略影响体验。** 当 L1 缓存满时，驱逐哪些 KV Cache 会直接影响后续请求的延迟。LRU、LFU、优先级策略各有取舍。

**一致性与失效。** 模型更新时，缓存需要被正确失效。如果新模型的 KV Cache 格式与旧版本不兼容，残留缓存会导致错误结果。

**跨副本复用。** Prefix Cache 的价值在于多请求共享。如果请求被路由到不同副本，缓存无法复用，需要调度器感知缓存亲和性。

#### 应该观察哪些指标和信号

| 指标 | 含义 | 告警阈值建议 |
|------|------|-------------|
| l1_hit_rate | GPU HBM 缓存命中率 | < 60% 时关注 |
| l2_hit_rate | CPU DRAM 缓存命中率 | < 40% 时关注 |
| eviction_rate | 各层驱逐率 | 突增时关注 |
| cache_invalidation_latency | 缓存失效延迟 | > 预期时告警 |
| ttft_by_cache_hit | 按缓存命中分组的 TTFT | 差异 > 10x 时关注 |
| cross_replica_cache_miss | 跨副本缓存未命中 | > 30% 时关注调度策略 |
| ssd_write_amplification | SSD 写放大 | > 3x 时关注寿命 |

#### 适用边界

**适合：**
- 重复前缀多的工作负载（共享系统 prompt、工具描述）
- 热点明显的业务模式
- 工具结果可复用的 Agent 场景

**不适合：**
- 数据高度随机、缓存命中率天然很低
- 强一致性要求极高，缓存难以安全失效
- 成本敏感到缓存层本身的资源开销不可接受

### 7. Agent Runtime 与 Tool Execution Sandbox

#### 这是什么

Agent Runtime 是把模型调用、工具执行、状态管理、计划编排和人工接管组织成可持续运行系统的运行时层。Tool Execution Sandbox 是为 Agent 调用的外部工具提供安全隔离的执行环境。

#### 为什么重要

Agent 让模型从"回答问题"扩展到"完成任务"。但 Agent 的多步执行、外部工具调用和自主决策能力，也带来了远超单次推理的安全和可靠性挑战。

#### 对 SRE / 平台工程的影响

**资源隔离。** 每个 Agent 可能并行调用多个工具，需要 CPU、内存、网络和磁盘的隔离，防止一个 Agent 的工具调用影响其他服务。

**超时控制。** Agent 可能陷入无限循环或多步推理链过长。需要在多个层级设置超时：单步工具调用超时、单任务总超时、会话级超时。

**安全审计。** Agent 的每一步决策和工具调用都需要审计日志，用于事后分析和合规。特别是涉及文件操作、数据库写入、API 调用等有副作用的操作。

**状态管理。** Agent 的中间状态需要持久化，支持暂停恢复、人工接管和异常中断后的恢复。

**成本控制。** Agent 可能在短时间内消耗大量推理调用，需要预算限制和成本追踪。

#### 应该观察哪些指标和信号

| 指标 | 含义 | 告警阈值建议 |
|------|------|-------------|
| task_completion_rate | 任务完成率 | < 90% 时关注 |
| avg_steps_per_task | 平均步骤数 | 突增时关注（可能陷入循环） |
| tool_timeout_rate | 工具调用超时率 | > 5% 时告警 |
| human_takeover_rate | 人工接管率 | > 10% 时关注 |
| session_state_size | 会话状态大小 | > 10MB 时关注 |
| cost_per_task | 单任务成本 | 超预算时告警 |
| abnormal_termination_rate | 异常终止率 | > 2% 时告警 |
| security_audit_flag_rate | 安全审计标记率 | > 0 时审查 |

#### 适用边界

**适合：**
- 确实需要多步骤决策和外部执行的业务
- 有成熟的安全沙箱和审计能力
- 有清晰的任务边界和预算控制
- 团队理解 Agent 的非确定性特征

**不适合：**
- 为了"更智能"把简单同步接口过度 Agent 化
- 没有安全沙箱，Agent 可以直接操作生产环境
- 无法接受 Agent 执行时间的不确定性
- 预算控制不严格，Agent 可能产生意外高成本

### 8. Synthetic Data 与自动评测

#### 这是什么

Synthetic Data（合成数据）是用模型或程序自动生成的测试样本和评测数据。Automated Eval（自动评测）是用这些数据持续验证模型、Prompt、RAG 和 Agent 变更的流水线。

#### 为什么重要

AI 系统很难只靠传统的单元测试保护质量。模型输出具有概率性，同一输入可能在不同版本产生不同输出。自动评测能把发布验证从人工抽查扩展到持续回归检查，是平台化运营的基础。

#### 对 SRE / 平台工程的影响

**评测系统成为控制面依赖。** 评测系统本身需要高可用，如果评测流水线故障，发布流程可能被阻塞。

**样本管理。** 评测样本需要版本控制、覆盖度追踪和定期更新。过时的样本无法检测新的回归模式。

**成本预算。** 大规模评测需要消耗大量推理调用，评测成本本身需要预算控制。

**误报与漏报。** 自动评测不是完美的。误报会浪费工程师时间，漏报会让问题逃逸到生产环境。

**与发布流水线集成。** 评测结果需要与 CI/CD 流水线集成，作为质量门禁。

#### 应该观察哪些指标和信号

| 指标 | 含义 | 告警阈值建议 |
|------|------|-------------|
| eval_pass_rate | 评测通过率 | < 95% 时阻断发布 |
| capability_score_breakdown | 关键能力分项分数 | 单项退化 > 5% 时告警 |
| regression_alert_count | 回归告警数 | 突增时关注 |
| sample_coverage_rate | 样本覆盖率 | < 80% 时关注 |
| eval_latency | 评测时延 | > 发布窗口时关注 |
| eval_cost_per_release | 单次发布评测成本 | 超预算时告警 |
| false_positive_rate | 误报率 | > 10% 时优化评测 |
| human_review_deviation | 人工复核偏差 | > 20% 时校准评测标准 |

#### 适用边界

**适合：**
- 经常变更模型、Prompt、检索或工具链路的团队
- 已建立评测基准和质量标准
- 有预算支撑评测的推理成本

**不适合：**
- 把自动评测结果当成唯一真相，忽略真实用户反馈
- 评测样本长期不更新，无法覆盖新场景
- 没有预算或不愿意为评测投入推理资源

### 9. Model Routing 与 Small-Large Cascade

#### 这是什么

Model Routing（模型路由）是根据请求特征把流量分发到不同模型的策略。Small-Large Cascade（大小模型级联）是其中一种具体模式：让小模型先尝试处理请求，如果小模型判断自己无法胜任（置信度低、复杂度高），再升级到大模型。

```
┌─────────────────────────────────────────────────────────────────────┐
│              Model Routing 决策树                                    │
│                                                                     │
│                      请求到达                                        │
│                         │                                           │
│                         ▼                                           │
│               ┌─────────────────┐                                   │
│               │ 请求特征提取     │                                   │
│               │ - token 数       │                                   │
│               │ - 复杂度评分      │                                   │
│               │ - 租户等级       │                                   │
│               │ - 任务类型       │                                   │
│               │ - 历史质量数据   │                                   │
│               └────────┬────────┘                                   │
│                        │                                            │
│              ┌─────────┴─────────┐                                  │
│              ▼                   ▼                                  │
│     ┌──────────────┐    ┌──────────────┐                            │
│     │ 复杂度评估    │    │ 路由策略匹配  │                            │
│     │ (小模型打分)  │    │ (规则/ML)     │                            │
│     └──────┬───────┘    └──────┬───────┘                            │
│            │                   │                                    │
│     ┌──────┴──────┐     ┌──────┴──────┐                             │
│     ▼             ▼     ▼             ▼                             │
│  ┌──────┐    ┌──────┐ ┌──────┐    ┌──────┐                          │
│  │ 简单 │    │ 复杂 │ │ 低级 │    │ 高级 │                          │
│  │ 请求 │    │ 请求 │ │ 别   │    │ 别   │                          │
│  └──┬───┘    └──┬───┘ └──┬───┘    └──┬───┘                          │
│     │           │        │           │                              │
│     ▼           ▼        ▼           ▼                              │
│  ┌──────┐    ┌──────┐ ┌──────┐    ┌──────┐                          │
│  │小模型│    │大模型│ │小模型│    │大模型│                          │
│  │快速  │    │高质  │ │经济  │    │保证  │                          │
│  │处理  │    │量处理│ │模式  │    │质量  │                          │
│  └──┬───┘    └──┬───┘ └──┬───┘    └──┬───┘                          │
│     │           │        │           │                              │
│     ▼           ▼        ▼           ▼                              │
│  ┌─────────────────────────────────────────┐                        │
│  │         输出质量监控 + 置信度检查         │                        │
│  │   低置信度 → 升级到大模型 (Cascade)       │                        │
│  └─────────────────────────────────────────┘                        │
│                                                                     │
│  关键 SRE 挑战：                                                     │
│  1. 路由决策可解释性（为什么这个请求去了小模型？）                     │
│  2. 误路由成本（小模型处理不了的质量损失）                            │
│  3. 多模型回退链路（小→大→更大，每级增加延迟和成本）                   │
│  4. 缓存割裂（不同模型的 KV Cache 无法共享）                          │
│  5. 容量联动（大模型池需要为小模型的升级请求预留容量）                  │
└─────────────────────────────────────────────────────────────────────┘
```

#### 为什么重要

不是所有请求都值得占用最贵的模型容量。通过路由和级联策略，可以在成本、延迟和质量之间找到最优平衡。典型场景下，60%-80% 的请求可以由小模型处理，只有 20%-40% 需要升级到大模型。

#### 对 SRE / 平台工程的影响

**路由层成为关键控制面。** 路由决策直接影响用户体验和成本。路由层的故障或误判会导致大面积质量下降或成本飙升。

**误路由需要量化。** 需要持续测量"小模型处理了但质量不达标"的比例（误路由率），以及"不需要大模型但路由到了大模型"的比例（过度路由率）。

**多模型回退链路。** 小模型→大模型→更大的模型，每一级都增加延迟和成本。需要定义清晰的升级条件和降级策略。

**缓存割裂。** 不小模型的 KV Cache 无法共享，路由变更会导致缓存命中率下降。

**容量联动。** 大模型池需要为小模型的升级请求预留容量。如果小模型批量升级，大模型池可能被突发流量冲击。

#### 应应该观察哪些指标和信号

| 指标 | 含义 | 告警阈值建议 |
|------|------|-------------|
| traffic_share_by_model | 各模型流量占比 | 突变时关注 |
| escalation_rate | 小模型升级率 | > 40% 时优化小模型或路由 |
| misroute_rate | 误路由率 | > 5% 时告警 |
| ttft_by_route | 按路由分组的 TTFT | 差异 > 3x 时关注 |
| cost_by_route | 按路由分组的成本 | 记录基线 |
| fallback_ratio | 回退比例 | > 10% 时关注 |
| quality_complaint_after_routing | 路由后质量投诉 | 突增时告警 |
| error_budget_consumption_by_route | 按路由分组的错误预算消耗 | 差异 > 2x 时关注 |

#### 适用边界

**适合：**
- 请求复杂度差异大（简单问答 vs 深度推理）
- 模型层级清晰（小、中、大模型各有明确定位）
- 有较好评测能力，能量化路由效果
- 有路由决策的可观测性和可解释性

**不适合：**
- 模型差异难以量化（不知道小模型能做什么、不能做什么）
- 路由策略不可解释（无法回答"为什么这个请求去了哪个模型"）
- 缺少回归验证（路由变更后无法检测质量退化）
- 数据薄弱团队（没有足够的历史数据来训练路由策略）

## SRE 实战案例

### 案例 1：引入 PD 分离后的运维挑战

**背景。** 一个日均处理 1000 万次推理请求的平台，决定引入 PD 分离来优化资源利用率。Prefill 池使用 A100（高算力），Decode 池使用 H100（高带宽）。

**评估过程。** 团队先用 5% 的流量做了两周灰度。基线指标：TTFT P50 为 800ms，P99 为 2.5s；TPOT P50 为 30ms。

**引入后发现的问题：**

1. **状态传输延迟波动。** 在流量高峰期，Prefill 和 Decode 池之间的网络出现拥塞，KV Cache 传输延迟从正常的 10ms 波动到 200ms。这导致 TTFT P99 从 2.5s 退化到 3.8s。根因：共享网络带宽被其他服务占用。

2. **调度不匹配。** Prefill 池的扩缩容策略基于并发请求数，Decode 池基于活跃 token 数。在突发流量下，Prefill 池快速扩容，但 Decode 池的扩容滞后，导致 KV Cache 堆积在传输层，Decode 池排队。

3. **故障恢复困难。** 一次 Decode 实例故障导致正在处理的 50 个请求丢失 KV Cache。回退方案是重新 Prefill，但这 50 个请求的 TTFT 从预期的 1s 变成了 5s。

**运维教训：**

- PD 分离的网络必须是专用的、有保障带宽的，不能与业务流量共享
- 两个池的扩缩容策略需要联动，不能独立决策
- 故障恢复预案必须覆盖"Prefill 已完成但 Decode 失败"的场景
- 端到端的延迟归因能力（分段 tracing）必须在引入前就位

**最终方案：** 为 PD 通信分配专用网络路径；开发联动扩缩容控制器，根据 Prefill 输出速率动态调整 Decode 池容量；实现 KV Cache 的快速重做（利用 Prefix Cache 减少重算成本）。

### 案例 2：MoE 模型上线的调度问题

**背景。** 一个团队上线了一个 8-expert 的 MoE 模型，每个请求激活 2 个专家。部署在 4 台 8-GPU 服务器上，每个 GPU 持有一个专家副本。

**引入后发现的问题：**

1. **路由倾斜导致热点。** 由于业务请求的特征分布不均匀，Expert 3 和 Expert 7 的命中率是其他专家的 4 倍。这两张 GPU 持续满载，而其他 GPU 利用率只有 30%。平均 GPU 利用率 50%，看起来不错，但实际是被热点拖累。

2. **显存管理意外。** 虽然每个请求只激活 2 个专家，但路由器的门控网络需要读取所有专家的元数据来做出路由决策。这部分显存开销在评估时被忽略，导致实际显存占用比预期高 15%。

3. **故障域不清晰。** 一次 Expert 3 所在 GPU 的 ECC 错误导致该专家间歇性输出异常。但由于路由倾斜，大约 40% 的请求受到影响。其他专家的 GPU 故障只影响约 10% 的请求。团队没有预料到故障影响范围与路由分布强相关。

**运维教训：**

- MoE 的容量规划不能只看平均利用率，必须看专家级别的利用率分布
- 路由策略需要纳入容量均衡目标，可能需要牺牲少量推理质量来换取负载均衡
- 故障域评估必须与路由分布结合：热门专家的故障影响范围远大于冷门专家
- 显存预算需要包含路由器和门控网络的开销

**最终方案：** 引入负载感知路由，在专家负载超过阈值时将请求路由到次优但负载较低的专家；为热门专家部署更多副本；建立专家级别的健康检查和故障隔离。

## 💻 实战练习

### 练习 1：基础操作——评估一项前沿技术的适用性

**目标：** 用五维评估框架评估一项技术，做出引入/观望的决策。

**场景：** 你的团队运营一个日均 500 万次推理请求的平台，当前使用 FP16 精度。管理层要求在 3 个月内降低 30% 的推理成本。团队评估了以下三个选项：

- 选项 A：引入 FP8 量化
- 选项 B：引入 Model Routing（小模型处理 60% 请求）
- 选项 C：引入 PD 分离

**任务：**

1. 对每个选项，用五维评估框架打分（1-5 分）
2. 计算加权总分
3. 做出推荐决策，并说明理由
4. 为推荐选项设计一个 4 周的原型验证计划

**评分参考：**

| 维度 | FP8 | Model Routing | PD 分离 |
|------|-----|---------------|---------|
| 运维就绪度 | 4 | 3 | 2 |
| 质量保障度 | 3 | 4 | 4 |
| 成本可预测性 | 4 | 4 | 3 |
| 故障隔离性 | 4 | 3 | 2 |
| 团队能力匹配 | 3 | 3 | 2 |

参考答案要点：FP8 加权总分 3.55，Model Routing 3.45，PD 分离 2.65。建议先引入 FP8（成熟度最高、风险最低），同时启动 Model Routing 的原型验证。PD 分离留待基础设施更成熟后考虑。

### 练习 2：进阶场景——设计一个 PD 分离的原型架构

**目标：** 设计一个可在隔离环境中验证的 PD 分离原型。

**场景：** 你有 4 台 A100 服务器和 4 台 H100 服务器。当前推理服务跑在 A100 上。你希望验证 PD 分离是否能提升资源利用率。

**任务：**

1. 设计 Prefill 池和 Decode 池的分配方案
2. 定义状态传输机制（KV Cache 如何从 Prefill 池传到 Decode 池）
3. 设计监控指标体系（至少 10 个指标）
4. 定义成功标准（什么情况下认为原型验证成功）
5. 定义回退方案（什么情况下放弃 PD 分离）

**设计要点参考：**

- Prefill 池：2 台 A100（高算力），Decode 池：4 台 H100（高带宽），剩余 2 台 A100 作为热备
- 状态传输：通过 RDMA 或 NVLink 传输 KV Cache，目标延迟 < 20ms
- 成功标准：TTFT P99 退化 < 10%，GPU 利用率提升 > 20%，状态传输失败率 < 0.1%
- 回退条件：TTFT P99 退化 > 30%，或状态传输失败率 > 1%，或运维复杂度超出团队能力

### 练习 3：故障排查挑战——分析前沿技术引入后的性能回退

**目标：** 分析一个由前沿技术引入导致的性能回退案例。

**场景：** 你的团队上周引入了 Model Routing，把 60% 的简单请求路由到小模型。上线后发现：

- 整体 TTFT P50 改善了 40%（小模型更快）
- 但 TTFT P99 恶化了 60%
- 用户投诉率上升了 15%
- 小模型的升级率（从大模型回退）为 25%

**任务：**

1. 分析可能的原因（至少 3 个假设）
2. 设计排查步骤（先看什么指标，再看什么指标）
3. 提出短期止血方案
4. 提出长期优化方案

**排查思路参考：**

假设 1：小模型对某些请求类型处理质量差，导致升级请求集中在大模型的高峰期，造成大模型池突发拥堵。
- 验证：查看升级请求的时间分布和请求特征

假设 2：路由决策有延迟（需要先提取特征），增加了整体 TTFT P99。
- 验证：查看路由决策本身的延迟分布

假设 3：升级请求需要重新处理（小模型的结果无法复用），相当于大模型做了两次推理。
- 验证：查看升级请求的端到端延迟，与直接发大模型的延迟对比

短期止血：降低小模型流量比例到 30%，观察 P99 是否恢复。
长期优化：优化路由决策延迟；实现小模型到大模型的 KV Cache 传递；改进路由策略的误判率。

## 🎯 面试题精选

### 问题 1：如何评估一项前沿技术是否值得引入生产环境？

**参考答案：**

评估框架包含五个维度：运维就绪度（能否监控、排障、回退）、质量保障度（有无基准测试和回归检测）、成本可预测性（成本模型是否清晰）、故障隔离性（故障影响范围是否可控）、团队能力匹配（团队是否理解这项技术）。

评估流程：先定义评估目标（解决什么问题），收集基线数据，在隔离环境原型验证，灰度引入，持续监控关键指标。每一步都需要明确的退出标准——什么情况下暂停或放弃引入。

关键原则：不只看技术收益，还要看运维成本；不只看平均性能，还要看尾部行为；不只看正常情况，还要看故障场景。

### 问题 2：PD 分离的适用条件是什么？架构设计中需要注意什么？

**参考答案：**

适用条件：大规模推理平台（请求量足够让两个池都保持合理利用率）、异构资源池（有不同类型 GPU）、已有稳定的分阶段指标、网络基础设施支持低延迟大带宽状态传输。

架构设计注意事项：
1. 状态传输机制：KV Cache 的传输延迟和可靠性是关键路径，需要专用网络路径
2. 扩缩容联动：Prefill 池和 Decode 池的扩缩容不能独立决策，需要联动控制
3. 故障恢复：需要覆盖"Prefill 完成但 Decode 失败"的场景，考虑 KV Cache 重做或转移
4. 观测面拆分：端到端延迟需要分段归因（Prefill、传输、Decode 各占多少）

### 问题 3：MoE 模型在生产环境有哪些运维挑战？

**参考答案：**

1. **路由倾斜：** 请求分布不均导致部分专家过载，平均 GPU 利用率掩盖热点问题。需要监控专家级别的命中分布和负载倾斜。
2. **显存管理：** 所有专家权重都需常驻显存，加上路由器和门控网络的开销，显存预算比同参数量的稠密模型更高。
3. **故障域不清晰：** 单 GPU 故障只影响部分专家，故障影响范围与路由分布强相关。热门专家的故障影响范围远大于冷门专家。
4. **跨节点通信：** Expert Parallel 需要 all-to-all 通信，网络带宽和延迟直接影响推理性能。
5. **容量规划复杂：** 不能只看平均利用率，需要看专家级别的利用率分布，容量规划维度更多。

### 问题 4：低精度推理（FP8/INT4）的质量保障策略是什么？

**参考答案：**

1. **系统化评测：** 每次量化后跑完整的基准测试，不只是几个例子，而是覆盖各能力维度的标准化评测集。
2. **回归检测：** 建立质量回归告警，当量化版本的质量分数低于基线一定比例时自动阻断发布。
3. **分场景评估：** 不同任务对精度敏感度不同。对话、摘要可能对 FP8 容错性好，数学推理、代码生成可能对 INT4 很敏感。
4. **灰度发布：** 从非关键路径开始，逐步扩大流量比例，持续监控质量指标。
5. **快速回退：** 保留高精度版本，确保可以在分钟级回退。量化模型在特定输入上可能出现异常输出，回退能力是安全网。
6. **制品管理：** 管理多个精度版本及其对应的评测结果，支持按场景选择精度。

### 问题 5：Agent Runtime 的安全设计应该包含哪些方面？

**参考答案：**

1. **执行隔离：** 每个 Agent 的工具调用在沙箱中执行，CPU、内存、网络和磁盘隔离，防止一个 Agent 影响其他服务。
2. **权限最小化：** Agent 只能访问其任务所需的最小资源集，不能有生产环境的直接写权限。
3. **超时控制：** 多层超时——单步工具调用超时、单任务总超时、会话级超时。防止无限循环和资源耗尽。
4. **审计日志：** 每一步决策和工具调用都需要审计日志，记录输入、输出、决策理由。用于事后分析和合规。
5. **人工接管：** 高风险操作（数据库写入、文件删除、API 调用）需要人工确认或预定义白名单。
6. **预算限制：** 推理调用次数和成本预算，超预算自动停止。防止 Agent 在短时间内消耗大量资源。
7. **输入验证：** 对 Agent 接收的外部输入（工具返回值、用户指令）进行验证，防止注入攻击。

### 问题 6：如何设计 Model Routing 的质量保障机制？

**参考答案：**

1. **路由决策可解释性：** 每个路由决策都需要记录理由（基于什么特征做出的判断），支持事后审计。
2. **误路由率监控：** 持续测量"小模型处理了但质量不达标"的比例。通过在线采样评测或用户反馈来估计。
3. **升级链路保障：** 小模型到大模型的升级链路需要低延迟和高可靠性。升级请求不能因为大模型池拥堵而超时。
4. **容量联动：** 大模型池需要为升级请求预留容量。监控升级率，当升级率突增时，可能意味着小模型能力不足或路由策略需要调整。
5. **缓存策略：** 路由变更会导致缓存命中率下降（不同模型的 KV Cache 无法共享）。需要评估路由变更对缓存的影响。
6. **A/B 测试：** 路由策略变更前，先用 A/B 测试验证对质量指标的影响，再全量发布。

### 问题 7：Inference Cache Hierarchy 的驱逐策略应该如何设计？

**参考答案：**

驱逐策略需要考虑多个因素：

1. **访问频率：** 高频访问的缓存条目应该保留更久（LFU）。
2. **最近使用：** 最近被访问的缓存条目有更高的复用概率（LRU）。
3. **重建成本：** 重建成本高的条目（如长前缀的 KV Cache）应该优先保留。
4. **业务优先级：** 高优先级租户的缓存应该优先保留。
5. **时效性：** 某些缓存条目有时效性（如工具结果缓存），过期后应该被驱逐。

实际策略通常是多因素加权的组合。例如：优先级 = 访问频率权重 * 0.3 + 最近使用权重 * 0.3 + 重建成本权重 * 0.2 + 业务优先级权重 * 0.2。

还需要考虑驱逐的时机：主动驱逐（缓存水位达到阈值时）vs 被动驱逐（有新条目需要空间时）。

### 问题 8：合成数据的质量如何保障？

**参考答案：**

1. **多样性保障：** 合成数据需要覆盖足够多的场景、边界条件和对抗样本，不能只覆盖"正常"路径。
2. **人工校准：** 定期用人工标注的数据校准合成数据的质量。如果合成数据的评测结果与人工评测偏差过大，需要调整生成策略。
3. **版本控制：** 评测样本需要版本控制，追踪每次变更的原因和影响。
4. **覆盖度监控：** 追踪评测样本对各能力维度的覆盖度，发现覆盖盲区。
5. **对抗样本：** 专门构造对抗样本（边界条件、异常输入、恶意输入），测试系统的鲁棒性。
6. **回归基线：** 建立评测基线，每次评测结果与基线对比，检测回归。
