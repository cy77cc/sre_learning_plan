# LLM SRE 32：容量规划速查表

## 适用场景

- 新模型上线前，先给出推理、训练和 RAG 配套资源的保守估算。
- 大促、活动、租户扩容或跨地域部署前，快速判断余量是否足够。
- 事故复盘后，需要把 TTFT、tokens/s、KV Cache 或训练 step time 的退化翻译成扩容动作。
- 预算评审时，需要用统一口径解释 GPU、存储、向量库和预热池成本。

## 推理容量估算

先把推理拆成两类压力：请求到达速率和 token 处理速率。仅看 QPS 容易低估长上下文和长输出的负载。

```text
需求 tokens/s ≈ QPS × (平均输入 tokens + 平均输出 tokens)

所需 GPU 数 ≈ 峰值需求 tokens/s ÷ 单 GPU 可持续 tokens/s ÷ 目标利用率
```

- 峰值口径优先使用 `p95 输入长度`、`p95 输出长度` 和活动期间峰值 QPS，不用日均值。
- 单 GPU 可持续 tokens/s 取压测稳定区间，不取最佳瞬时值。
- 目标利用率建议预留缓冲，不让核心模型池长期跑到极限；共享池应单独留出回退和冷启动余量。
- 若 TTFT 主要受 queue time 影响，先补实例数；若 TTFT 主要受 Prefill 影响，优先控制上下文长度和长请求比例。
- 多模型、多 LoRA 或多租户混跑时，应按模型池分别估算，不能直接共享一个 tokens/s 基线。

## 训练容量估算

训练容量同时受总 token 量、并行效率和 checkpoint 开销影响。单看 GPU 数量没有意义。

```text
训练总时长 ≈ 总训练 tokens ÷ (集群有效 tokens/s)

集群有效 tokens/s ≈ 单卡 tokens/s × GPU 数 × 并行效率
```

- 并行效率不要按理想值估，需扣除 all-reduce、pipeline bubble、数据读取和 checkpoint 写入损耗。
- 大模型训练还要单独核对网络带宽、存储吞吐和恢复窗口，避免 GPU 够了但 checkpoint 路径拖垮作业。
- 对微调任务，除主训练资源外，还要预留评测、制品上传和回滚验证窗口。
- 训练与推理共平台时，训练队列必须有硬配额，不能用“夜间空闲”当容量承诺。

## KV Cache 与上下文长度估算

KV Cache 决定长上下文和高并发是否能落地。上下文窗口配置必须和显存预算一起看。

```text
KV Cache 总量 ≈ 并发会话数 × 平均上下文 tokens × 每 token KV 占用

安全并发上限 ≈ 可用于 KV Cache 的显存 ÷ 单会话 KV Cache 占用
```

- `平均上下文 tokens` 不要只看用户输入，还要加上 system prompt、RAG 片段、工具返回和历史会话。
- 长会话、慢输出和高并发会同时放大 KV Cache 水位，应按最坏组合评估而不是逐项分开乐观估计。
- Prefix Cache、Paged Attention 和量化会改变显存利用率，但不能替代上下文准入控制。
- 若 KV Cache 长期接近上限，优先考虑缩短上下文、分层流量或拆分模型池，再决定是否硬扩显存。

## 压测口径

- 压测必须覆盖真实长度分布，至少拆分短请求、长上下文请求、长输出请求和 RAG 请求四类流量。
- 同时记录 TTFT、TPOT、tokens/s、queue time、错误率、KV Cache 水位和冷启动时长，不只看吞吐峰值。
- 压测要区分单模型稳定区和混部区；混部时要加入多租户噪声、LoRA 切换或索引查询开销。
- 训练压测至少包含数据加载、NCCL 通信、checkpoint 写入和故障恢复，不接受只跑单 step 的结论。
- 所有容量结论都要标注压测日期、模型版本、量化方案、上下文窗口和路由策略。

## 扩容决策

- 当 `queue time` 持续抬升且实例已处于稳定高利用率，优先横向扩容或切流到备用模型池。
- 当 `TTFT` 抬升但 `queue time` 正常，先排查长上下文、Prefix Cache 失效、冷启动和索引膨胀，不要直接加卡。
- 当 `tokens/s` 下降且 batch 质量变差，先检查流量结构、调度和优化开关，再决定是否扩池。
- 当 `KV Cache` 水位逼近上限并伴随拒绝请求，优先做上下文治理、分池或限流；显存扩容是第二选择。
- 当训练作业排队时间超过承诺窗口，先看资源碎片和队列策略，再决定新建节点池或扩建网络/存储通道。
- 扩容动作必须同步评估预热时间、制品拉取、对象存储带宽和下游向量库容量，避免只补单点。

## 常见误判

- 用平均 QPS 或平均 tokens 估算容量，结果活动流量一来就打穿 TTFT。
- 只按 GPU 利用率决定扩容，忽略 queue time、KV Cache 和冷启动导致的真实瓶颈。
- 把离线 benchmark 当线上承诺，没有考虑多租户噪声、长上下文和 RAG 链路。
- 把训练 GPU 数量当成训练吞吐，没有扣除并行效率、网络抖动和 checkpoint 开销。
- 认为显存打满就一定要扩卡，实际上很多时候是上下文准入、索引膨胀或 LoRA 混跑策略失控。
- 索引重建、embedding 重跑或评测补跑没有单独算容量，最终在线业务被后台任务拖垮。
