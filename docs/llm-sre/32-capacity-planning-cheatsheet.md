## 📖 核心知识点

### 1. 为什么需要容量规划

#### 1.1 LLM 服务的资源特征

LLM 服务与传统 Web 服务有本质区别，容量规划必须考虑以下特征：

| 特征 | 传统 Web 服务 | LLM 推理服务 |
|------|---------------|-------------|
| 计算模式 | 请求级短时计算 | 秒级到分钟级持续计算 |
| 资源类型 | CPU + 内存 | GPU + 显存 + 高带宽网络 |
| 弹性速度 | 秒级扩容 | 分钟级扩容（模型加载） |
| 请求特征 | 响应时间相对一致 | 随上下文长度剧烈波动 |
| 内存模型 | 请求结束后释放 | KV Cache 持续占用 |
| 成本结构 | CPU/内存成本线性 | GPU 成本指数级增长 |

#### 1.2 容量不足的后果

```
容量不足的连锁反应：

  请求到达 ──→ 队列积压 ──→ TTFT 飙升
                  │
                  ├──→ 超时 ──→ 用户流失
                  │
                  ├──→ 重试风暴 ──→ 负载进一步恶化
                  │
                  └──→ OOM ──→ 实例崩溃 ──→ 可用性下降
```

典型事故链：

1. 流量突增，GPU 利用率打满
2. 请求进入队列，queue time 持续增长
3. TTFT p99 从 2s 飙升到 30s+
4. 客户端超时重试，流量翻倍
5. KV Cache 耗尽，触发 OOM，实例崩溃
6. 剩余实例负载加重，雪崩效应
7. 服务完全不可用

#### 1.3 容量过剩的成本

GPU 资源极其昂贵，容量过剩直接侵蚀利润：

```
成本影响示例：

  一张 A100-80G 云上月租 ≈ ¥10,000 - ¥15,000
  一个 8 卡节点月租 ≈ ¥80,000 - ¥120,000

  过剩 50% 的容量 = 每月浪费 ¥40,000 - ¥60,000 / 节点
  全年浪费 ≈ ¥480,000 - ¥720,000 / 节点

  如果集群有 10 个节点过剩 = 每年浪费 ¥500 万 - ¥700 万
```

### 2. 推理容量估算

#### 2.1 容量估算流程总览

```
推理容量估算流程:

  ① 收集业务指标         ② 计算 tokens/s        ③ 计算 GPU 数
  ┌──────────────┐      ┌──────────────────┐    ┌──────────────────┐
  │ 峰值 QPS     │      │ 需求 tokens/s    │    │ GPU 数           │
  │ p95 输入长度  │─────→│ = 峰值 QPS       │───→│ = 需求 tokens/s  │
  │ p95 输出长度  │      │   × (p95输入     │    │   ÷ 单GPU吞吐   │
  │ 并发会话数    │      │     + p95输出)   │    │   ÷ 目标利用率   │
  └──────────────┘      └──────────────────┘    └────────┬─────────┘
                                                         │
                      ⑤ 取较大值          ④ 验证显存约束   │
                      ┌──────────────────┐  ┌─────────────┴────────┐
                      │ 最终 GPU 数      │←─┤ 权重+KV+激活+系统    │
                      │ = max(吞吐,显存) │  │ ≤ 单卡显存           │
                      └──────────────────┘  └──────────────────────┘
```

#### 2.2 基础公式

**第一步：估算 tokens/s 需求**

```
需求 tokens/s ≈ 峰值 QPS × (p95 输入 tokens + p95 输出 tokens)
```

关键点：
- 必须使用峰值 QPS，不能用日均 QPS
- 必须使用 p95/p99 token 长度，不能用平均值
- 输入 tokens 需包含 system prompt、RAG 片段、历史会话

**第二步：估算 GPU 数量**

```
所需 GPU 数 ≈ 峰值需求 tokens/s ÷ 单 GPU 可持续 tokens/s ÷ 目标利用率
```

关键点：
- 单 GPU 可持续 tokens/s 取压测稳定区间值，不取最佳瞬时值
- 目标利用率建议 60%-70%，留出安全余量
- 多模型混跑时按模型池分别估算

**第三步：验证显存约束**

```
单卡显存需求 = 模型权重显存 + KV Cache 显存 + 激活值显存 + 系统开销

所需 GPU 数（显存约束）= 总显存需求 ÷ 单卡可用显存
```

**最终结果：取两者的较大值**

```
最终 GPU 数 = max(吞吐约束 GPU 数, 显存约束 GPU 数)
```

#### 2.3 显存构成详解

```
单 GPU 显存构成 (80GB A100):

  ┌──────────────────────────────────────────────────────────────┐
  │  模型权重 (40%-70%)                                           │
  │  FP16: 参数量 × 2 bytes | INT8: × 1 byte | INT4: × 0.5 byte │
  │  例: 70B FP16 = 140 GB (需 2 卡) | 70B INT4 = 35 GB          │
  ├──────────────────────────────────────────────────────────────┤
  │  KV Cache (20%-40%)                                           │
  │  = 2 × 层数 × KV头数 × 头维度 × 序列长度 × 并发数 × 字节数   │
  │  动态变化，随并发和上下文长度增长                               │
  ├──────────────────────────────────────────────────────────────┤
  │  激活值 (2%-5%)    │  与 batch size 和序列长度相关，1-4 GB     │
  ├────────────────────┤─────────────────────────────────────────┤
  │  系统开销 (1%-3%)  │  CUDA context、框架开销，0.5-2 GB        │
  └──────────────────────────────────────────────────────────────┘
```

#### 2.4 计算示例

**场景 1：对话服务（短上下文、高并发）**

业务参数：
- 峰值 QPS：100
- p95 输入 tokens：500（含 system prompt）
- p95 输出 tokens：200
- 目标并发用户数：500
- 模型：LLaMA-3-8B（FP16，约 16 GB 权重）
- 单 GPU：A100-80G

```
Step 1: 需求 tokens/s
  = 100 QPS × (500 + 200) tokens
  = 70,000 tokens/s

Step 2: GPU 数量（吞吐约束）
  单卡可持续吞吐 ≈ 2,000 tokens/s（实测稳定值）
  目标利用率 = 70%
  GPU 数 = 70,000 ÷ 2,000 ÷ 0.7 = 50 张

Step 3: GPU 数量（显存约束）
  模型权重 = 16 GB
  KV Cache = 2 × 32层 × 32头 × 128维度 × 500 tokens × 32并发 × 2 bytes
           ≈ 2 × 32 × 32 × 128 × 500 × 32 × 2
           ≈ 26.2 GB（单卡可承载约 32 并发）
  激活值 ≈ 1 GB
  系统开销 ≈ 1 GB
  单卡总需求 ≈ 16 + 26.2 + 1 + 1 = 44.2 GB < 80 GB ✓
  500 并发所需卡数 = 500 ÷ 32 ≈ 16 张（显存约束）

Step 4: 最终结果
  GPU 数 = max(50, 16) = 50 张
  考虑 20% 安全余量：50 × 1.2 = 60 张
  节点数 = 60 ÷ 8 = 8 个节点（每节点 8 卡）
```

**场景 2：文档处理（长上下文、低并发）**

业务参数：
- 峰值 QPS：10
- p95 输入 tokens：8,000（长文档 + RAG）
- p95 输出 tokens：2,000
- 目标并发会话数：20
- 模型：LLaMA-3-70B（INT4 量化，约 35 GB 权重）
- 单 GPU：A100-80G

```
Step 1: 需求 tokens/s
  = 10 QPS × (8,000 + 2,000) tokens
  = 100,000 tokens/s

Step 2: GPU 数量（吞吐约束）
  单卡可持续吞吐 ≈ 800 tokens/s（70B INT4 实测值）
  目标利用率 = 70%
  GPU 数 = 100,000 ÷ 800 ÷ 0.7 ≈ 179 张

Step 3: GPU 数量（显存约束）
  模型权重 = 35 GB（需要张量并行，至少 2 卡）
  KV Cache 单会话 = 2 × 80层 × 64头 × 128维度 × 10,000 tokens × 2 bytes
                  ≈ 2 × 80 × 64 × 128 × 10,000 × 2
                  ≈ 26.2 GB / 会话
  20 并发 × 26.2 GB = 524 GB KV Cache 总量
  单卡可用显存 = 80 - 35（权重，2卡分摊后17.5） - 1（系统） = 61.5 GB
  显存约束 GPU 数 = 524 ÷ 61.5 ≈ 9 张
  但模型需要至少 2 卡张量并行，所以按节点对齐：10 张

Step 4: 最终结果
  GPU 数 = max(179, 10) = 179 张
  考虑 20% 安全余量：179 × 1.2 ≈ 216 张
  节点数 = 216 ÷ 8 = 27 个节点

  ⚠️ 成本提示：27 节点月成本约 ¥216 万，需评估业务 ROI
```

**场景 3：混合负载（对话 + 文档处理）**

业务参数：
- 对话服务：50 QPS，输入 500 tokens，输出 200 tokens
- 文档服务：5 QPS，输入 6,000 tokens，输出 1,500 tokens
- 共用模型：LLaMA-3-8B（FP16）

```
Step 1: 分别计算需求
  对话 tokens/s = 50 × (500 + 200) = 35,000 tokens/s
  文档 tokens/s = 5 × (6,000 + 1,500) = 37,500 tokens/s
  总需求 = 35,000 + 37,500 = 72,500 tokens/s

Step 2: 加权单卡吞吐
  对话场景单卡吞吐 ≈ 2,000 tokens/s（短上下文，batch 效率高）
  文档场景单卡吞吐 ≈ 600 tokens/s（长上下文，KV Cache 压力大）
  加权吞吐 = (35,000/72,500) × 2,000 + (37,500/72,500) × 600
           ≈ 0.483 × 2,000 + 0.517 × 600
           ≈ 966 + 310 = 1,276 tokens/s

Step 3: GPU 数量
  GPU 数 = 72,500 ÷ 1,276 ÷ 0.7 ≈ 81 张
  安全余量后 ≈ 98 张 → 13 个节点

Step 4: 建议
  考虑对话和文档使用不同模型池，各自独立弹性伸缩
  对话池：35,000 ÷ 2,000 ÷ 0.7 = 25 张 → 4 节点
  文档池：37,500 ÷ 600 ÷ 0.7 = 89 张 → 12 节点
  分池后总需求更大，但弹性更好，资源利用率更高
```

### 3. 训练容量估算

#### 3.1 基础公式

```
训练总时长 ≈ 总训练 tokens ÷ 集群有效 tokens/s

集群有效 tokens/s ≈ 单卡 tokens/s × GPU 数 × 并行效率

GPU 小时 = 训练总时长 × GPU 数 = 总训练 tokens ÷ (单卡 tokens/s × 并行效率)
```

#### 3.2 FLOPS 需求估算

```
训练 FLOPS ≈ 6 × 模型参数量 × 训练 tokens 数

示例：
  模型参数量 = 7B (7 × 10^9)
  训练 tokens = 2T (2 × 10^12)
  总 FLOPS = 6 × 7×10^9 × 2×10^12 = 84 × 10^21 = 8.4 × 10^22 FLOPS

  A100 BF16 峰值 = 312 TFLOPS = 3.12 × 10^14 FLOPS/s
  理论 GPU 秒数 = 8.4×10^22 ÷ 3.12×10^14 ≈ 2.69 × 10^8 秒
  理论 GPU 小时 = 2.69×10^8 ÷ 3600 ≈ 74,722 GPU 小时

  实际 MFU (Model FLOPS Utilization) ≈ 40%-55%
  实际 GPU 小时 = 74,722 ÷ 0.45 ≈ 166,049 GPU 小时
```

#### 3.3 并行效率分析

```
总并行效率 = 数据并行效率 × 张量并行效率 × 流水线并行效率

  并行类型     效率公式                              典型范围    约束条件
  ─────────────────────────────────────────────────────────────────────
  数据并行 DP  ≈ 1 - 通信开销占比                     85%-95%    网络带宽
  张量并行 TP  ≈ 1 - all-reduce延迟 / 计算时间        80%-90%    NVLink (TP≤8)
  流水线并行 PP ≈ 1 - (PP-1)/(PP-1+micro_batches)    70%-90%    micro batch 数
  ─────────────────────────────────────────────────────────────────────
  综合效率示例: 0.90 × 0.85 × 0.85 = 65%
```

#### 3.4 通信开销估算

```
每步通信量估算 (All-Reduce):

  每步通信量 = 2 × 参数量 × 每参数字节数 × (DP-1) / DP

  示例 (70B 模型, BF16, DP=64):
    参数量 = 70 × 10^9
    每参数字节数 = 2 (BF16)
    通信量 = 2 × 70×10^9 × 2 × 63/64
           ≈ 275.6 GB / 步

  所需带宽:
    目标每步时间 = 1 秒
    所需带宽 = 275.6 GB / 1s = 275.6 GB/s
    需要多卡并行通信或多节点 NVLink 支撑
```

#### 3.5 Checkpoint I/O 开销

```
Checkpoint 写入时间估算:

  单次 Checkpoint 数据量 = 模型参数 + 优化器状态 + 梯度

  示例 (70B 模型, BF16, Adam 优化器):
    模型参数 = 70 × 10^9 × 2 bytes = 140 GB
    优化器状态 = 70 × 10^9 × 8 bytes = 560 GB (FP32 参数副本 + momentum + variance)
    梯度 = 70 × 10^9 × 2 bytes = 140 GB
    总计 = 140 + 560 + 140 = 840 GB

  写入时间:
    本地 NVMe SSD (3 GB/s): 840 / 3 = 280 秒 ≈ 4.7 分钟
    共享存储 (1 GB/s): 840 / 1 = 840 秒 ≈ 14 分钟
    对象存储 (500 MB/s): 840 / 0.5 = 1680 秒 ≈ 28 分钟

  Checkpoint 频率影响:
    每 1000 步存一次, 每步 2 秒
    Checkpoint 开销占比 = 280 / (1000 × 2) = 14% (本地 SSD)
    Checkpoint 开销占比 = 1680 / (1000 × 2) = 84% (对象存储, 不可接受)
```

### 4. KV Cache 与上下文长度

#### 4.1 KV Cache 计算公式

```
每 token KV Cache 大小 = 2 × 层数 × 头数 × 头维度 × 每元素字节数

常见模型 KV Cache 大小:

  ┌──────────────┬────────┬────────┬──────────┬─────────────────┐
  │ 模型          │ 层数    │ 头数    │ 头维度    │ 每 token KV     │
  ├──────────────┼────────┼────────┼──────────┼─────────────────┤
  │ LLaMA-3-8B   │ 32     │ 32     │ 128      │ 1.0 MB          │
  │ LLaMA-3-70B  │ 80     │ 64     │ 128      │ 5.0 MB          │
  │ LLaMA-3-405B │ 126    │ 128    │ 128      │ 16.0 MB         │
  │ Qwen-2-72B   │ 80     │ 64     │ 128      │ 5.0 MB          │
  │ DeepSeek-V3  │ 61     │ 128    │ 128      │ 7.8 MB          │
  └──────────────┴────────┴────────┴──────────┴─────────────────┘

  注: 使用 GQA (Grouped Query Attention) 时, KV 头数 ≠ Q 头数
  LLaMA-3-70B 使用 GQA, KV 头数 = 8, 实际每 token KV = 0.625 MB
```

#### 4.2 总 KV Cache 计算

```
KV Cache 总量 = 并发会话数 × 平均上下文长度 × 每 token KV 大小

示例 (LLaMA-3-70B, GQA):
  并发会话数 = 100
  平均上下文长度 = 4,000 tokens
  每 token KV 大小 = 0.625 MB

  KV Cache 总量 = 100 × 4,000 × 0.625 MB = 250,000 MB = 250 GB

  分布在 8 张 A100-80G 上:
  每卡 KV Cache = 250 / 8 = 31.25 GB
  模型权重 (INT4) = 35 GB / 8 ≈ 4.4 GB / 卡 (张量并行)
  每卡总需求 = 31.25 + 4.4 + 1 ≈ 36.65 GB < 80 GB ✓
```

#### 4.3 安全并发数限制

```
安全并发上限 = 可用于 KV Cache 的显存 ÷ 单会话 KV Cache 占用

示例 (LLaMA-3-70B, A100-80G, 8 卡张量并行):
  单卡总显存 = 80 GB
  模型权重 = 35 GB (INT4, 8卡分摊后 4.4 GB/卡)
  系统开销 = 2 GB
  可用于 KV Cache = 80 - 4.4 - 2 = 73.6 GB / 卡
  8 卡总计可用于 KV Cache = 73.6 × 8 = 588.8 GB

  单会话 KV Cache (4K 上下文) = 4,000 × 0.625 MB = 2.5 GB
  安全并发上限 = 588.8 / 2.5 ≈ 235 会话

  单会话 KV Cache (32K 上下文) = 32,000 × 0.625 MB = 20 GB
  安全并发上限 = 588.8 / 20 ≈ 29 会话

  ⚠️ 上下文长度从 4K 增长到 32K, 并发能力下降 8 倍!
```

#### 4.4 上下文长度对容量的影响

```
上下文长度与资源需求关系:

  资源需求
     ▲
     │                                    ╱ KV Cache (线性增长)
     │                                  ╱
     │                                ╱
     │                              ╱
     │                            ╱
     │                          ╱
     │                        ╱
     │                      ╱
     │    ───────────────────── 模型权重 (固定)
     │                  ╱
     │                ╱  Prefill 时间 (二次增长)
     │              ╱
     │            ╱
     │          ╱
     │        ╱
     │      ╱
     │    ╱
     │  ╱
     └──────────────────────────────────→ 上下文长度
         1K    4K    8K    16K   32K   64K

  关键观察:
  - 模型权重是固定开销，不受上下文长度影响
  - KV Cache 随上下文长度线性增长
  - Prefill 时间随上下文长度二次增长（注意力计算）
  - 长上下文场景下，KV Cache 成为主要瓶颈
```

#### 4.5 RAG 场景的上下文膨胀

```
RAG 上下文 = System Prompt + 用户输入 + 检索文档(×N) + 工具返回 + 历史摘要 + 格式开销

示例:
  System Prompt: 500 | 用户输入: 200 | 检索文档: 5×1000=5000 | 工具: 300 | 历史: 1000 | 格式: 500
  总计: 7,500 tokens（用户仅输入 200，膨胀 37.5 倍）
```

### 5. 压测方法论

#### 5.1 四种流量类型

```
四种流量模式:

  ① 固定并发            ② 递增负载            ③ 脉冲流量            ④ 真实回放
  ┌──────────────┐   ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
  │ ████████████ │   │           ╱  │    │     █       │    │  ╱╲  ╱╲     │
  │ ████████████ │   │        ╱     │    │  █  █  █  █ │    │╱  ╲╱  ╲ ╱╲  │
  │ ████████████ │   │     ╱        │    │  █  █  █  █ │    │        ╲╱  ╲ │
  └──────────────┘   └──────────────┘    └──────────────┘    └──────────────┘
  测试稳态吞吐基线     找到系统拐点         测试突发恢复能力      验证真实场景表现
```

#### 5.2 压测指标体系

| 指标 | 含义 | 目标值 | 采集方式 |
|------|------|--------|---------|
| TTFT p50 | 首 token 延迟中位数 | < 500ms | 客户端埋点 |
| TTFT p95 | 首 token 延迟 95 分位 | < 2s | 客户端埋点 |
| TTFT p99 | 首 token 延迟 99 分位 | < 5s | 客户端埋点 |
| TPOT p50 | 每 token 输出延迟中位数 | < 50ms | 客户端埋点 |
| TPOT p95 | 每 token 输出延迟 95 分位 | < 100ms | 客户端埋点 |
| TPS | 每秒处理 token 数 | 参考基线 | 服务端指标 |
| Queue Time | 请求排队时间 | < 100ms | 服务端指标 |
| GPU 利用率 | SM 活跃比例 | 60%-80% | nvidia-smi / DCGM |
| 显存使用率 | 显存占用比例 | < 85% | nvidia-smi / DCGM |
| KV Cache 命中率 | Prefix Cache 命中比例 | > 50% (如有) | 服务端指标 |
| 错误率 | 请求失败比例 | < 0.1% | 服务端指标 |
| 拒绝率 | 被限流/拒绝比例 | < 1% | 服务端指标 |

#### 5.3 压测工具选型

| 工具 | 适用场景 | 优势 | 劣势 |
|------|---------|------|------|
| vLLM benchmark | vLLM 服务基准测试 | 开箱即用，指标全面 | 仅限 vLLM |
| locust + 自定义 client | 复杂场景压测 | 灵活，支持自定义逻辑 | 需要开发 |
| vegeta + HTTP | HTTP 层压测 | 简单高效 | 不理解 SSE/流式 |
| k6 | 云端压测 | 支持分布式，云原生 | 学习曲线 |
| 自研压测框架 | 深度定制 | 完全可控 | 维护成本高 |

#### 5.4 压测执行步骤

```
压测执行流程:

  ① 准备 → 确定目标、准备数据、配置监控、通知相关方、准备回滚方案
     │
     ▼
  ② 基线 → 低并发 (10%) 运行 5 分钟，记录 TTFT/TPOT/TPS/GPU 基线
     │
     ▼
  ③ 递增 → 从 20% 开始，每 5 分钟 +20%，找到延迟拐点
     │
     ▼
  ④ 稳态 → 拐点 80% 负载运行 30 分钟，观察内存泄漏和延迟漂移
     │
     ▼
  ⑤ 异常 → 脉冲 3x 负载、长上下文突发、节点故障模拟
     │
     ▼
  ⑥ 报告 → 汇总指标、绘制延迟-吞吐曲线、确定安全容量上限
```

### 6. 扩容决策矩阵

#### 6.1 信号与行动对照表

| 信号 | 含义 | 紧急程度 | 行动 |
|------|------|---------|------|
| GPU 利用率 > 80% 且延迟正常 | 接近容量上限 | 中 | 预扩容，评估增长趋势 |
| TTFT p95 升高且 queue time 增加 | 排队压力增大 | 高 | 立即扩容或切流 |
| KV Cache > 90% | 显存压力 | 高 | 扩容或限制上下文长度 |
| 频繁 OOM | 超出容量 | 紧急 | 紧急扩容 + 限制并发 |
| TPOT 持续升高 | 计算瓶颈 | 中 | 扩容或优化模型 |
| 错误率 > 1% | 服务质量下降 | 紧急 | 排查 + 扩容 |
| 冷启动时间过长 | 预热不足 | 低 | 优化预热或保活策略 |

#### 6.2 决策流程图

```
扩容决策流程:

  监控异常 → queue time 升高? ─是→ 横向扩容 + 限流
                │ 否
                ▼
           TTFT 升高但 queue 正常? ─是→ 排查长上下文 / Prefix Cache / 冷启动
                │ 否
                ▼
           KV Cache 接近上限? ─是→ 限制上下文 + 分池 + 扩显存
                │ 否
                ▼
           TPOT 升高? ─是→ 扩计算资源 + 优化模型
                │ 否
                ▼
           持续观察，无需立即行动
```

在执行扩容前，必须确认以下事项：

扩容前检查清单:

  □ 确认瓶颈类型（计算/显存/队列/IO）
  □ 评估扩容成本和 ROI
  □ 确认目标集群有足够资源

### 7. 常见误判

| 误判 | 错误推理 | 实际情况 | 正确做法 |
|------|---------|---------|---------|
| 只看 GPU 利用率 | "利用率 60%，余量充足" | TTFT p99 已 10s，长上下文阻塞短请求 | 同时监控 GPU 利用率 + TTFT + queue time |
| 忽略上下文分布 | "平均 1,000 tokens，很充裕" | 5% 长请求占 50%+ KV Cache | 用 p95/p99 上下文长度，长请求分池 |
| 低估 KV Cache | "80G 卡还有 45 GB 余量" | KV Cache 31 GB/卡，实际余量仅 13% | 将 KV Cache 作为显存规划核心 |
| 忽略冷启动 | "扩容 5 分钟完成" | 模型加载+预热+流量导入需 5-15 分钟 | 扩容提前量 = 增长时间 - 冷启动时间 |
| 压测不真实 | "压测通过，线上没问题" | 压测无长尾、无多租户、无 RAG 链路 | 真实流量回放 + 长尾分布 + 联合压测 |

**冷启动时间分解：**

```
模型加载 (70B INT4, 35 GB):
  对象存储: 35 GB ÷ 500 MB/s = 70 秒
  本地缓存: 35 GB ÷ 3 GB/s = 12 秒

预热: CUDA 初始化 5-10s + JIT 编译 10-30s + Prefix Cache 60-300s
负载均衡: 健康检查 30-60s + 流量导入 60-120s

总计: 缓存加载 2-10 分钟 | 存储加载 5-15 分钟
```

**压测 vs 真实流量差异：**

| 维度 | 压测流量 | 真实流量 |
|------|---------|---------|
| 上下文长度分布 | 均匀或固定 | 严重偏斜 |
| 多租户干扰 | 无 | 有 |
| Prefix Cache 命中 | 高（重复请求） | 低（多样化请求） |
| RAG 链路 | 简化或跳过 | 完整链路 |
| 错误重试 | 无 | 有 |

### 练习 1：基础操作 — 估算对话服务的 GPU 需求

**背景：** 你需要为一个客服对话服务做容量规划。

**业务参数：**
- 预估峰值 QPS：200
- p95 输入 tokens：800（含 system prompt 和历史）
- p95 输出 tokens：300
- 模型：Qwen-2-7B（FP16，约 14 GB 权重）
- 可用 GPU：A100-80G
- 单卡实测吞吐：2,500 tokens/s

**步骤：**

```
Step 1: 计算需求 tokens/s
  需求 = _____ QPS × (_____ 输入 + _____ 输出)
  需求 = _____ tokens/s

Step 2: 计算 GPU 数量（吞吐约束）
  单卡吞吐 = _____ tokens/s
  目标利用率 = 70%
  GPU 数 = _____ ÷ _____ ÷ 0.7 = _____ 张

Step 3: 计算 KV Cache 显存
  Qwen-2-7B: 28 层, 32 头, 128 维度, GQA (KV 头数=4)
  每 token KV = 2 × 28 × 4 × 128 × 2 bytes = _____ bytes = _____ KB
  KV Cache 总量 = 100 并发 × 800 tokens × _____ KB = _____ GB

Step 4: 验证单卡显存
  模型权重 = 14 GB
  KV Cache / 卡 = _____ GB ÷ 卡数
  激活值 ≈ 1 GB
  系统 ≈ 1 GB
  单卡总需求 = _____ GB < 80 GB?

Step 5: 最终结果
  安全余量 20%
  最终 GPU 数 = _____ × 1.2 = _____ 张
  节点数 = _____ ÷ 8 = _____ 个节点
```

**参考答案：**

```
Step 1: 200 × (800 + 300) = 220,000 tokens/s
Step 2: 220,000 ÷ 2,500 ÷ 0.7 = 125.7 → 126 张
Step 3: 每 token KV = 2 × 28 × 4 × 128 × 2 = 57,344 bytes ≈ 56 KB
        KV Cache = 100 × 800 × 56 KB = 4.48 GB 总量
Step 4: 单卡显存 = 14 + 4.48/126 + 1 + 1 ≈ 16 GB << 80 GB ✓
Step 5: max(126, ~1) = 126 张 × 1.2 = 152 张 → 19 个节点

  ⚠️ 注意: 126 张卡的需求主要是吞吐驱动，显存很充裕
  这是典型的高并发短上下文场景特征
```

## 🎯 面试题精选

### 面试题 1：如何估算 LLM 推理服务的 GPU 需求？

**答题框架：**

1. **从需求出发**：收集峰值 QPS、p95 输入/输出 token 长度、目标并发数
2. **计算吞吐需求**：需求 tokens/s = 峰值 QPS × (p95 输入 + p95 输出)
3. **计算吞吐约束 GPU 数**：GPU 数 = 需求 tokens/s ÷ 单卡吞吐 ÷ 目标利用率
4. **计算显存约束 GPU 数**：显存 = 模型权重 + KV Cache + 激活值 + 系统开销
5. **取较大值**：最终 GPU 数 = max(吞吐约束, 显存约束)
6. **加安全余量**：通常 20%-30%
7. **考虑实际约束**：节点对齐、模型并行要求、负载均衡

**加分点：**
- 强调必须使用峰值 QPS 和 p95/p99 token 长度，不能用平均值
- 提到 KV Cache 是长上下文场景的主要瓶颈
- 提到多模型混跑需要分别估算
- 提到扩容需要考虑冷启动时间

---

### 面试题 2：KV Cache 如何影响容量规划？

**答题框架：**

1. **KV Cache 的定义**：存储已计算的 Key-Value 对，避免重复计算
2. **计算公式**：KV Cache = 并发数 × 上下文长度 × 每 token KV 大小
3. **影响因素**：
   - 并发数：线性影响
   - 上下文长度：线性影响
   - 模型大小：层数、头数、维度决定每 token 大小
4. **容量影响**：
   - 显存分配：KV Cache 可能占显存的 20%-40%
   - 并发上限：KV Cache 耗尽时无法接受新请求
   - 上下文限制：长上下文大幅降低并发能力
5. **优化手段**：
   - GQA/MQA 减少 KV 头数
   - KV Cache 量化（FP8/INT8）
   - Prefix Cache 共享公共前缀
   - Paged Attention 动态分配
   - 上下文准入控制

### 面试题 3：压测应该关注哪些指标？

**答题框架：** 四类指标缺一不可

| 类别 | 指标 | 说明 |
|------|------|------|
| 用户体验 | TTFT、TPOT、端到端延迟 | 影响用户感知 |
| 系统性能 | TPS、Queue time、并发会话数 | 反映系统压力 |
| 资源 | GPU 利用率、显存、KV Cache | 资源使用情况 |
| 可靠性 | 错误率、拒绝率、OOM 频率 | 服务质量 |

关键点：关注 p95/p99 而非平均值；指标需关联分析，不能孤立看待；压测指标要标注环境配置。

---

### 面试题 4：扩容决策的关键信号是什么？

**答题框架：** 三类信号对应不同行动

| 信号 | 指标 | 行动 |
|------|------|------|
| 计算瓶颈 | GPU > 80%、TPOT 升高 | 扩容计算资源 |
| 队列压力 | Queue time 升高、TTFT 升高 | 横向扩容 + 限流 |
| 显存压力 | KV Cache > 90%、OOM | 扩显存或限制上下文 |

决策原则：先定位瓶颈再扩容；优先治理（限流、上下文控制）再扩硬件；评估成本和 ROI；考虑冷启动提前量。

---

### 面试题 5：如何避免容量规划中的常见误判？

**答题框架：** 五类误判及纠正

| 误判 | 错误做法 | 正确做法 |
|------|---------|---------|
| 数据选择 | 平均 QPS、平均 token 长度 | 峰值 QPS、p95/p99 token 长度 |
| 指标片面 | 只看 GPU 利用率 | 关联 GPU + TTFT + queue + KV Cache |
| 流量差异 | 压测等同真实流量 | 长尾分布 + 多租户 + RAG 链路 |
| 资源遗漏 | 只算模型权重 | 权重 + KV Cache + 激活值 + 系统 |
| 时间维度 | 扩容 5 分钟完成 | 模型加载 + 预热 + 流量导入 = 5-15 分钟 |
