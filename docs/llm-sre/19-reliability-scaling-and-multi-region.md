# LLM SRE 19：可靠性、扩缩容与多地域

## 这篇文档解决什么问题

这篇文档讨论 LLM 在线服务怎样在流量波动、实例故障、区域故障和发布变更下保持可用。很多团队已经能把模型跑起来，但一遇到冷启动、GPU 池抖动、流量突发或跨地域切流，就会发现传统 Web 服务经验不够用。

LLM 服务的可靠性难点在于，用户体验不只取决于“接口是否返回 200”，还取决于 TTFT、TPOT、回退质量和成本是否同时可控。SRE 和平台团队需要把副本策略、扩缩容、发布机制、流量治理和告警设计串成一条链路。

本文聚焦在线推理面向生产运行的高可用能力；[16-inference-engines-and-serving-architecture.md](./16-inference-engines-and-serving-architecture.md) 负责推理引擎与服务架构，[18-inference-observability-and-slo.md](./18-inference-observability-and-slo.md) 负责指标体系与 SLO。

## 系统全景

可靠性设计可以拆成五层：接入、路由、模型服务、依赖服务和恢复控制面。每层都要明确容量边界、故障域和自动化动作。

```text
用户 / SDK / API Gateway
        |
        v
全局流量入口：DNS / GSLB / Anycast / 全局 LB
        |
        v
地域入口：WAF / Ingress / API Router / Rate Limit
        |
        v
模型服务池：多副本推理实例 / 批处理器 / KV Cache / Adapter Cache
        |
        +------> 依赖：权重仓库 / Prompt Registry / Feature Store
        |
        +------> 依赖：Embedding / Reranker / Vector DB / Tool Backend
        |
        v
控制面：扩缩容 / 发布 / 健康探测 / 告警 / 自动回滚
```

系统全景的关键不是把所有组件都堆上去，而是回答三个问题：请求进入后会经过哪些故障点，哪一层负责隔离故障，哪一层负责恢复服务。如果这三个问题答不清，多地域和自动扩容往往只是表面上的“高级配置”。

## 多副本、多可用区、多地域部署

多副本是最基础的可靠性手段。单副本模型服务即使 GPU 很强，也经不起节点驱逐、驱动异常、显存碎片积累和滚动升级。副本数至少要满足单实例故障后仍能维持目标 SLO，而不是只满足平均负载。

多可用区部署的重点是故障域隔离。实践上应同时使用 `podAntiAffinity`、`topologySpreadConstraints` 和节点池标签，让同一模型池的副本分散到不同节点、机架和可用区。否则看起来是三副本，实际上可能都挤在同一故障域里。

多地域部署进一步解决区域级故障、主干网络抖动和合规驻留问题，但也引入复制、一致性和成本复杂度。常见模式有：

- `active-active`：多地域同时接流量，恢复快，但要处理会话亲和、缓存命中下降和跨地域成本。
- `active-standby`：主地域服务、备地域热待命，实现简单，但平时资源利用率较低。
- `regional specialization`：不同地域承载不同模型或租户，便于合规隔离，但切换路径更复杂。

LLM 场景下，多地域不仅是“再放一套 Deployment”。你还要同步模型权重、LoRA 制品、路由配置、Prompt 版本、RAG 索引和配额规则。控制面没有跟上时，切流成功也可能只会把故障搬到另一个地域。

## 扩缩容：HPA、KEDA、自定义指标

CPU 和内存不是 LLM 服务最好的扩容信号。很多时候请求排队时间（queue time）已经飙升，但 CPU 仍然很闲；GPU 利用率很高，也不代表继续加副本就会改善 TTFT。扩容应围绕请求排队、token 吞吐、显存水位和冷启动时间设计。

HPA 适合基于稳定指标做副本调节，例如并发请求数、queue time、tokens/s、GPU 利用率或自定义 backlog。它的优点是原生、简单，缺点是面对突刺和长冷启动时反应偏慢。KEDA 更适合事件驱动扩缩容，例如从 Kafka、SQS、Redis Stream 或 Prometheus backlog 指标触发扩容。

自定义指标通常比通用资源指标更可靠，常见选择包括：

- `queue_time_p95`：最贴近用户体验，但要做好平滑与抖动控制。
- `inflight_requests` 或 `waiting_requests`：适合路由层或 batcher 层。
- `tokens_per_second` 与 `generated_tokens_per_second`：更接近真实负载强度。
- `kv_cache_usage_ratio`：长上下文场景很关键，可提前发现显存风险。
- `cold_start_in_progress`：避免扩容时把尚未 ready 的实例当作可用容量。

扩缩容策略需要同时定义上升、下降和保护条件。上升过慢会放大排队；下降过快会在模型加载成本很高的场景中造成抖动。对加载分钟级权重的大模型，建议结合最小副本、预热池和峰值前定时扩容，而不是只信任纯自动策略。

## 灰度、影子流量（shadow traffic）、蓝绿与回滚

发布策略是可靠性体系的一部分，因为很多事故来自变更而不是硬件。LLM 服务发布不只是镜像升级，还包括模型版本切换、量化参数变化、Prompt 模板变更、LoRA 适配器替换和路由规则调整。

灰度发布适合逐步放量，重点观察 TTFT、错误率、回退率、截断率和用户反馈是否与基线偏离。对推理服务来说，单看 5xx 不够，因为质量退化通常先体现在输出差异和重试率上。

影子流量适合验证新模型或新运行时的行为，但要明确它不应该影响主链路 SLO。shadow 请求需要隔离配额、日志和成本归因，否则很容易把实验流量误算进生产容量。

蓝绿发布适合需要快速切换的稳定版本替换，前提是两套环境都完成预热，并且连接状态、缓存与索引版本兼容。回滚则要足够“短路径”：切流回旧池、恢复旧 Prompt、回退适配器、撤销路由规则，都应有一键化入口。事故里最危险的不是没有回滚，而是回滚还需要人工拼步骤。

## 回退（fallback）、熔断、限流、降级

LLM 平台不能把每个请求都视为“必须在原计划上成功”。可靠性的核心能力之一，是在主路径不稳定时有明确的次优路径。

回退常见于三类场景：主模型不可用时切到备用模型，RAG 检索失败时退化为无检索回答或固定模板，工具调用超时时返回部分结果。fallback 的前提是质量边界可接受，否则只是把显式错误改成隐式错误。

熔断用于阻止故障扩散。某个下游 embedding 服务、向量库或工具服务持续超时时，继续压请求只会把线程池、连接池和重试预算一起打爆。限流则解决容量保护问题，常见维度包括租户、模型、请求 token、并发会话和工具调用次数。

降级要有层次，而不是只有“返回 503”。常见做法包括：

- 降低最大上下文长度，优先保住整体可用性。
- 关闭 reranker、工具调用或多步 agent 链路，缩短关键路径。
- 将长文本生成改为摘要模式，限制输出 token 上限。
- 将低优先级租户切到便宜或较慢的备用池。

这些机制要提前演练。没有演练的 fallback，往往会在真正故障时暴露出配置失效、质量不可接受或成本失控的问题。

## 关键指标与告警

可靠性章节关注的是“是否扛得住故障和波动”，所以指标要覆盖流量、容量、发布和恢复动作。

| 类别 | 核心指标 | 为什么重要 |
| --- | --- | --- |
| 体验 | `TTFT p95/p99`、`TPOT p95`、端到端错误率 | 判断用户是否真实受到影响 |
| 排队 | `queue time`、等待请求数（`waiting requests`）、丢弃请求数 | 区分是容量不足还是模型慢 |
| 容量 | 副本数、ready 副本数、冷启动时长、GPU/显存/KV Cache 水位 | 判断扩容是否有效 |
| 发布 | 灰度池错误率、shadow 偏差、回滚次数、变更失败率 | 识别变更是否引入故障 |
| 治理动作 | fallback 比例、熔断开启次数、限流命中率、降级命中率 | 判断保护机制是否过度或失效 |
| 多地域 | 各地域成功率、切流时长、跨地域流量比例、配置同步延迟 | 判断灾备是否真实可用 |

告警建议按恢复动作组织，而不是按组件分组。例如“TTFT 高且 queue time 同步升高”应指向扩容和限流手册，“备用地域接管失败”应指向全局流量切换与配置核验手册。没有对应动作的告警通常只是噪声。

## 典型故障与排查路径

| 故障现象 | 优先检查项 | 常见根因 |
| --- | --- | --- |
| 流量上涨后 TTFT 急剧恶化 | queue time、ready 副本、冷启动、HPA/KEDA 事件 | 扩容滞后、最小副本过低、模型加载慢 |
| 单地域成功率下降 | 地域入口 5xx、节点池状态、依赖连通性、全局路由权重 | 区域网络抖动、GPU 节点批量异常、配置漂移 |
| 发布后质量投诉暴增但错误率正常 | 灰度池输出差异、截断率、fallback 比例、Prompt 版本 | 模型切换、Prompt 变更、量化回归 |
| 全局可用但少数租户持续超时 | 按租户配额、限流、路由池、会话长度分布 | 大租户流量尖峰、配额不合理、长上下文热点 |
| 备用模型频繁接管 | 主池健康、熔断阈值、依赖超时、成本曲线 | 主池部分退化、保护阈值过敏、下游不稳 |

排查顺序建议固定为：先看影响范围，再看近期变更，再区分容量问题还是依赖问题，最后才深入单实例。LLM 平台容易在实例级细节里迷路，但很多故障本质上是发布、路由或配额问题。

## 设计权衡

高可用不是“开更多副本”这么简单，核心权衡通常在以下几组矛盾之间：

- 更高副本和更大预热池提升恢复速度，但会显著增加 GPU 常驻成本。
- `active-active` 多地域恢复快，但会损失缓存命中并提高跨地域治理复杂度。
- 激进自动扩容改善峰值体验，但容易被冷启动和抖动反噬。
- 强 fallback 和多层降级提高可用性，但可能隐藏质量回归。
- 发布更快意味着学习速度更快，但也更容易快速烧掉错误预算。

因此，可靠性设计必须和业务目标一起看。面向交互式高价值流量的模型池，通常愿意为低 TTFT 支付更高常驻成本；面向离线批处理的模型池，则更在意吞吐和资源利用率。

## 实践建议

- 为每个模型池定义最小可用副本和单故障域失效后的剩余容量，不要只看平均负载。
- 扩容策略至少同时接入一个用户体验信号和一个资源信号，例如 `queue time` 加 `ready replicas`。
- 把 Prompt、模型、LoRA、RAG 索引和路由配置纳入同一发布审计链路，避免“代码回滚了，配置没回滚”。
- 对 fallback、熔断、限流和多地域切流做演练，确认动作真实可执行且质量可接受。
- 发布后监控不只看错误率，还要看截断率、重试率、回退比例和成本突增。
