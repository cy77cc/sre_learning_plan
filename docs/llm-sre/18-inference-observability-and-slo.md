# LLM SRE 18：推理可观测性与 SLO

## 这篇文档解决什么问题

这篇文档讨论推理服务应该观测什么、如何设计 SLO、告警应该如何贴近用户影响，以及值班人员在事故中如何从指标、日志和链路追踪（Tracing）拼出根因。很多团队的监控仍停留在“GPU 利用率高不高”，但用户真正感知的是 TTFT、TPOT、错误率和输出质量是否稳定。

推理可观测性的难点在于它同时跨越在线服务、GPU 基础设施和模型行为。只看单一层面的指标，通常不足以支撑 SLO 和事故处置。

## 系统全景

推理可观测性至少要覆盖四层信号：请求体验、服务状态、资源消耗、模型输出质量。SLO 设计要围绕这四层建立因果链，而不是把几十个指标堆在一个大盘里。

```text
用户请求
   |
   v
体验层：TTFT / TPOT / queue time / 错误率
   |
   v
服务层：路由 / 批处理 / KV Cache / 实例健康
   |
   v
资源层：GPU / 显存 / CPU / 网络 / 缓存
   |
   v
质量层：拒答率 / 截断率 / 工具失败率 / 人工反馈
```

SRE 的工作重点是把这四层串起来。否则你只能知道“某张卡很忙”，却不知道忙带来了什么用户影响，或者某个租户的故障是否已经耗尽错误预算。

## 核心指标：TTFT、TPOT、tokens/s、queue time

TTFT 代表首个 token 返回前的等待，通常包含 queue time 和 Prefill 时间，是用户最先感知的延迟指标。TPOT 反映每个输出 token 的平均生成时间，更贴近 Decode 效率和流式输出的连贯性。TPS（tokens/s）用于描述系统处理 token 的速率，既可看实例级吞吐，也可看模型池和租户维度吞吐。

queue time 则是区分“平台太忙”还是“模型本身太慢”的关键指标。没有 queue time，TTFT 上升时很难判断该扩容、限流还是回退流量。建议所有核心大盘和告警都把 TTFT 与 queue time 成对展示。

## 资源指标：GPU、显存、CPU、缓存

资源指标的意义不在于“看到硬件很满”，而在于解释延迟与错误。GPU 利用率可以帮助判断 batch 是否充分，但不能单独说明服务健康；显存使用率和 KV Cache 占用更能解释拒绝请求、OOM 和 TPOT 抖动；CPU 使用率和事件循环延迟则影响网关、tokenization、日志处理和路由控制面。

缓存指标要被单独对待。这里的缓存既包括 KV Cache，也包括 Prefix Cache、本地权重缓存、LoRA 适配器缓存和可能存在的远端缓存。缓存命中下降往往先表现为 TTFT 恶化，随后才是 GPU 和显存曲线变化。

## 请求级 tracing 与质量信号

链路追踪（Tracing）是推理平台从“看总体趋势”走向“解释单次故障”的关键。一个请求级 trace 至少应包含：租户、模型、路由目标、输入输出 token 数、queue time、Prefill/Decode 分段耗时、重试与回退动作、下游依赖调用，以及最终状态码。

对 AI 系统来说，请求级观测还应补上质量信号。质量信号不一定等同于模型评测分数，但至少要包含：输出截断率、空响应率、工具调用失败率、安全拦截率、用户中止率、重试率和人工反馈标签。没有这些信号，SLO 只会保护“快地返回错误结果”。

## 告警设计与错误预算

告警应当围绕用户影响、恢复动作和错误预算消耗来设计，而不是围绕“某项指标看起来不顺眼”。建议至少建立可用性、延迟、容量和质量四类告警，并明确哪些会消耗 SLO 错误预算。

| 告警名 | 条件 | 影响 | 处理动作 |
| --- | --- | --- | --- |
| TTFT 高延迟 | `TTFT p95` 连续 10 分钟超过目标且 `queue time p95` 同步上升 | 用户首包慢，交互体验明显变差 | 先看 waiting requests 和扩容状态，再决定限流、扩池或流量回退 |
| TPOT 退化 | `TPOT p95` 连续 10 分钟超过基线且错误率未显著上升 | 输出流式变慢，长回答体验差 | 检查 Decode 吞吐、KV Cache 占用和 batch 波动，必要时降并发 |
| 请求错误率升高 | 5xx/超时/OOM 比例超过阈值并持续 5 分钟 | 直接消耗可用性错误预算 | 区分是否单模型、单租户或单节点故障，触发回退或摘除实例 |
| KV Cache 压力过高 | `KV Cache` 占用接近上限且伴随拒绝请求或换出增加 | TTFT、TPOT 同时恶化，存在 OOM 风险 | 缩减上下文上限、限流长请求、补充容量或切换更大显存池 |
| 冷启动异常 | 新实例加载时长超过基线或 readiness 长时间未通过 | 扩容无效，峰值期间容易放大排队 | 检查权重拉取、节点缓存、镜像和显存初始化，暂停继续扩容 |
| 路由回退异常 | 回退到备用模型/备用池的比例短时突增 | 说明主池退化或路由策略异常 | 检查主池健康、注册表状态和发布变更，必要时冻结路由变更 |

错误预算要按业务等级分开管理。面向交互式问答的高优先级接口，通常更在意 TTFT 和错误率；面向批量生成的接口，可能更关注 TPS（tokens/s）和成本。把所有业务压到同一套预算里，会导致告警和资源策略都失真。

## 仪表盘建议

高层仪表盘建议按三屏组织：

- 体验屏：TTFT、TPOT、queue time、错误率、TPS（tokens/s），按模型池和租户分组。
- 容量屏：GPU 利用率、显存、KV Cache、waiting requests、batch 大小、冷启动数量。
- 诊断屏：按实例、节点、模型版本、LoRA 适配器查看 trace、日志、回退率和错误分布。

大盘要能从“全局异常”快速钻取到“哪个模型、哪个租户、哪批实例出问题”。如果只能看全局均值，事故时几乎没有指导意义。

## 典型故障与排查路径

| 故障现象 | 优先检查项 | 常见根因 |
| --- | --- | --- |
| 用户反馈首包慢 | TTFT、queue time、waiting requests、冷启动记录 | 流量突增、扩容未热身、路由打偏、长 prompt 激增 |
| 流式输出忽快忽慢 | TPOT、Decode 吞吐、KV Cache、水位波动 | 显存带宽紧张、batch 不稳定、长会话抢占资源 |
| 错误率突然升高 | 5xx、OOM、超时、实例重启、路由回退 | 新版本发布异常、节点故障、显存耗尽、依赖超时 |
| 某租户持续抱怨体验差 | 按租户查看 TTFT/TPOT、配额命中、trace 样本 | 配额过紧、路由到低优先级池、请求结构异常 |
| 指标正常但业务认为结果变差 | 截断率、空响应率、安全拦截率、人工反馈 | prompt 模板变更、LoRA 版本错误、回退模型质量下降 |

排查时建议先回答三件事：影响范围是全局还是局部，问题主要落在延迟、错误还是质量，是否与近期发布、扩容或路由变更相关。先定范围，再挖细节。

## 实践建议

- 所有关键请求都记录 TTFT、TPOT、TPS（tokens/s）和 queue time，且能按模型、租户、版本切片。
- 把链路追踪（Tracing）接到推理平台，而不只是网关层；否则看不到 Prefill/Decode 和回退动作。
- 告警直接绑定运行手册，值班人员收到告警后要知道先看哪个大盘、先执行什么动作。
- 质量信号至少要覆盖截断、空响应、工具失败和回退比例，避免 SLO 只保护“快”不保护“对”。
- 错误预算复盘要和容量规划、发布节奏、限流策略联动，而不是只做事后统计。
