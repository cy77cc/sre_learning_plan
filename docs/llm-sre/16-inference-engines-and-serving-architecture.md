# LLM SRE 16：推理引擎与服务架构

## 这篇文档解决什么问题

这篇文档回答三个问题：第一，推理服务的系统边界到底在哪里；第二，vLLM、SGLang、TGI、Triton、TensorRT-LLM 这几类引擎分别适合什么场景；第三，平台团队在网关、路由、多租户、冷启动和容量治理上应该如何设计。很多团队把“起一个模型服务”当成推理平台，但真实线上系统还包含鉴权、调度、缓存、发布、观测和回滚。

本文不展开单个内核优化细节，而是关注推理平台的结构化设计：请求如何进入、模型如何装载、流量如何分配、资源如何隔离、故障如何被发现。

## 系统全景

一个可运营的推理平台通常由六层组成：接入层、控制层、推理引擎层、模型与缓存层、基础设施层、观测与治理层。任何一层设计粗糙，都会在用户侧表现为 TTFT 抖动、TPOT 恶化、错误率升高或成本失控。

```text
客户端 / SDK
    |
    v
API 网关 / 鉴权 / 配额 / 限流
    |
    v
路由控制面 / 租户策略 / 发布策略
    |
    v
推理引擎池（vLLM / SGLang / TGI / Triton / TensorRT-LLM）
    |
    v
模型权重 / LoRA 适配器 / KV Cache / Prefix Cache
    |
    v
GPU / CPU / 网络 / 对象存储 / 容器编排
    |
    v
日志 / 指标 / 链路追踪（Tracing）/ 审计 / 告警
```

从 SRE 视角看，推理平台不是“若干 Pod + GPU”。它是一个对外承诺延迟与可用性、对内管理显存与并发、对上承接租户策略、对下消化模型和硬件差异的控制面。

## 引擎对比：vLLM / SGLang / TGI / Triton / TensorRT-LLM

不同引擎的核心差别，不只在 benchmark，而在于它们把优化点放在哪一层。有的强调通用高吞吐服务化，有的强调编译优化和极致性能，有的更适合复杂模型编排或企业内统一 serving 平台。

| 引擎 | 优势 | 风险 | 适用场景 |
| --- | --- | --- | --- |
| vLLM | OpenAI 兼容度高，continuous batching 与 KV Cache 管理成熟，社区活跃 | 版本升级快，参数矩阵复杂，错误地放大上下文与并发容易把显存打满 | 通用文本生成平台，高吞吐共享集群，快速落地多模型服务 |
| SGLang | 对结构化生成、推理工作流和前缀复用更友好，适合复杂推理链路 | 社区和生态相对更新，团队需要理解其调度模型与编排方式 | 需要 prompt 程序化控制、前缀复用、复杂生成流程的场景 |
| TGI | Hugging Face 生态结合紧，部署心智清晰，适合作为标准化服务层 | 对某些新特性跟进节奏可能不如专用引擎快，极致吞吐不一定最优 | 以 HF 模型仓库为中心、追求稳妥平台化接入的团队 |
| Triton | 多框架统一托管能力强，适合把 LLM 与 CV/ASR 等模型放在同一 serving 平台 | LLM 特有调度优化不是它唯一中心，平台复杂度较高 | 企业统一模型平台，多模型、多框架混合服务 |
| TensorRT-LLM | 编译优化深入，适合追求低延迟和高吞吐上限 | 构建链路复杂，版本与硬件耦合深，调试与回滚成本高 | 稳定模型版本、固定硬件池、强性能目标的生产环境 |

选型时不要只看“单卡 tokens/s”。真正重要的是四个问题：是否能稳定暴露 TTFT/TPOT/TPS（tokens/s）指标，是否支持你的多租户治理模型，是否便于发布回滚，是否能让值班人员快速定位问题。

## API 网关、鉴权、路由与多租户

推理引擎本身不应该承担全部平台职责。API 网关负责认证、配额、速率限制、请求规范化和审计；路由控制面负责模型选择、租户隔离、灰度发布和回退策略；推理引擎负责把请求变成 token。把这些职责混在一起，通常意味着每次模型升级都在改控制面。

多租户设计至少要回答四件事：谁能访问哪些模型，单租户能消耗多少并发和 token，热点流量如何限速，故障时谁先被保护。常见做法包括：

- 按租户、模型和优先级分别配置并发上限与 token 配额。
- 把鉴权结果转换成路由元数据，而不是在引擎实例里硬编码租户逻辑。
- 对高优先级流量预留容量，避免被批量离线请求挤爆。
- 为路由决策打点，保证每个请求最终能回答“为什么被送到这个后端”。

从平台角度看，路由系统本身也是故障源。错误的路由缓存、过期的模型注册、失真的健康检查，都会把健康请求打向不健康实例。

## 单模型、多模型与多 LoRA 部署模式

单模型部署最简单，隔离性最好，适合大模型核心路径和严格 SLO 业务。代价是资源利用率偏低，模型切换慢，容量碎片明显。多模型共享实例可以提升资源利用率，但会引入权重切换、显存争用和 tail latency 放大。多 LoRA 复用则进一步提高灵活性，但会把问题从“是否装得下模型”变成“适配器管理和缓存命中是否稳定”。

实践中常见三种模式：

- 单模型专池：适合主力模型、关键租户、严格延迟目标。
- 小模型共享池：适合长尾模型、实验流量、低优先级业务。
- 基座模型 + 多 LoRA：适合行业定制、租户定制和高频小变体。

SRE 要重点关注复用带来的副作用：显存水位更难预测，冷适配器加载会拉高 TTFT，热点租户会挤占公共 KV Cache，模型与 LoRA 版本配套错误会直接导致结果异常。

## 冷启动、模型加载与预热

推理平台的冷启动远比普通 Web 服务昂贵。拉镜像、下载权重、反序列化、显存分配、图编译、CUDA Graph 捕获、LoRA 装载和 Prefix Cache 建立，都可能消耗数十秒到数分钟。一次不受控的扩容可能把本来只是排队变长的问题放大成整批实例不可用。

冷启动治理的重点包括：

- 把镜像、权重和 tokenizer 缓存到节点本地或近端存储，减少远端拉取抖动。
- 区分 `startupProbe` 与 `readinessProbe`，模型未完成加载前不要接流量。
- 用合成请求做预热，覆盖典型上下文长度，而不是只探活 HTTP 端口。
- 扩容时分批拉起实例，避免同时争抢对象存储、PCIe 和显存。
- 对多 LoRA 平台维护热点适配器预装策略，降低首次命中 TTFT。

很多平台事故的表象是“扩容了但还是慢”，根因其实是新副本尚未完成热身，老副本在接住全部高峰流量。

## 关键指标与告警

推理架构层面的关键指标应覆盖四组信号：

- 体验指标：TTFT、TPOT、TPS（tokens/s）、queue time、E2E latency。
- 引擎指标：running/waiting requests、batch 大小、KV Cache 占用、Prefix Cache 命中率、换出与回收次数。
- 平台指标：每模型流量、每租户配额消耗、路由命中率、冷启动时长、加载失败率。
- 基础设施指标：GPU 利用率、显存使用率、PCIe/RDMA 错误、容器重启、节点驱逐。

告警不要只盯 GPU 利用率。更有价值的告警是“TTFT 上升且 queue time 同步恶化”“某模型加载失败率升高”“路由回退命中异常增加”“热点 LoRA 首次加载时长超基线”。这些告警更接近用户影响和平台动作。

## 设计权衡

推理架构的常见权衡主要集中在四组矛盾：

- 吞吐与隔离：共享池利用率高，但更容易产生 noisy neighbor 和尾延迟放大。
- 灵活性与确定性：多模型、多 LoRA 平台更灵活，但容量模型更难做，回滚路径更复杂。
- 快速扩容与冷启动成本：实例越重，自动扩缩容越难真正解决突发流量。
- 统一平台与专项优化：统一 serving 平台降低运维碎片，但极致性能通常需要更强的引擎定制和硬件绑定。

架构设计的目标不是消灭这些矛盾，而是把代价显式化，让团队知道哪类业务可以共享、哪类业务必须专池。

## 实践建议

- 把“网关/路由/引擎”分层，避免模型升级影响鉴权和租户策略。
- 先按业务等级分池，再在池内讨论单模型、多模型或多 LoRA 复用，不要一开始就做全局共享。
- 以 TTFT、TPOT、queue time 为主指标做容量规划，别只看平均 TPS（tokens/s）。
- 为模型加载、LoRA 装载和预热建立独立观测，避免把所有慢请求都归因给 GPU。
- 预先定义回退策略：回退到旧版本、回退到小模型、拒绝低优先级请求，三者要分开设计。
