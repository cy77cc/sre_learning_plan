# LLM SRE 20：RAG、Agent 与应用平台

## 这篇文档解决什么问题

这篇文档讨论 AI 应用平台如何把“模型调用”扩展成可运行、可观测、可治理的完整系统。很多团队把 RAG、agent 和工具调用（tool calling）当成功能开发问题，但线上真正出故障时，问题往往出在索引更新、embedding 漂移、会话状态、工具超时和上下文膨胀。

SRE 和平台团队需要理解，RAG 与 agent 平台并不是一个单点服务，而是一条由离线摄取、在线检索、上下文构造、推理调用、工具执行和会话状态（session state）组成的链路。任何一段漂移或超时，都会直接影响回答质量与时延。

本文聚焦应用平台运行面，负责运行时可运维性、检索到生成的链路行为、工具链执行表现以及状态管理；[18-inference-observability-and-slo.md](./18-inference-observability-and-slo.md) 负责基础推理指标，[19-reliability-scaling-and-multi-region.md](./19-reliability-scaling-and-multi-region.md) 负责高可用与流量治理，[21-security-compliance-and-governance.md](./21-security-compliance-and-governance.md) 负责围绕这些能力的策略、授权、审计与治理边界。

## 系统全景

RAG/Agent 平台通常同时包含离线和在线两条链路。离线链路负责把知识资产整理成可检索索引，在线链路负责把查询、检索、重排、生成和工具执行串起来。

```text
离线链路：
文档源 -> 解析/清洗 -> 切分 -> embedding -> 索引构建 -> 发布

在线链路：
用户请求
  -> 检索编排器
  -> embedding / query rewrite
  -> 向量检索 / 混合检索
  -> reranker
  -> 上下文拼接
  -> LLM / agent runtime
  -> 工具调用（tool calling） / memory / session state
  -> 输出与审计
```

平台团队的责任是保证这两条链路版本一致、依赖稳定、指标连通。否则最常见的现象就是：检索系统显示健康，但线上回答突然“查不到东西”。

## 文档摄取、切分、向量化、索引与检索

文档摄取首先要解决来源多样和质量参差的问题。PDF、网页、工单、知识库、代码仓库和数据库导出文件，格式、编码和权限模型都不同。摄取链路需要把“抓到文档”变成“得到可信文本和元数据”，这一步如果做坏，后面所有检索优化都只是补锅。

切分策略直接影响召回质量和成本。切得太粗，召回命中后上下文冗余太大；切得太细，语义被打断，相关片段需要依赖 reranker 拼回来。实践上通常在固定窗口切分、语义切分和基于结构的切分之间折中，并保留文档 ID、段落位置、更新时间和权限标签等元数据，方便后续过滤和审计。

向量化和索引发布要明确版本边界。embedding 模型升级后，旧向量通常不能与新向量长期混用；分块策略变化后，也往往需要整库重建。索引发布最好采用“新索引构建完成后原子切换”的方式，避免在线写入与查询同时命中半成品数据。

检索层除了向量检索，还常配合关键词检索、元数据过滤和业务规则过滤。SRE 角度最重要的不是某种算法名词，而是知道查询路径里有几次网络跳转、哪一段最容易抖、发生故障时是否有降级路径。

## embedding 服务与向量数据库运维

embedding 服务本质上是一个延迟敏感的模型服务。它通常比生成模型轻，但在高 QPS、批量重建和多租户竞争下同样会成为瓶颈。平台上要明确区分在线查询 embedding 和离线批量 embedding 两类流量，避免索引重建把线上查询拖垮。

向量数据库的选择，重点看已有基础设施、规模上限、运维复杂度和过滤需求，而不是只看单次 benchmark。

| 维度 | pgvector | Milvus | Qdrant |
| --- | --- | --- | --- |
| 典型定位 | 依附 PostgreSQL 的向量扩展 | 独立分布式向量数据库 | 面向检索场景的独立向量数据库 |
| 运维复杂度 | 低，适合已有 PG 团队 | 高，组件多、容量规划更复杂 | 中，部署相对直接 |
| 扩展能力 | 适合中小规模与强事务整合 | 适合大规模分布式检索 | 适合中到大规模、强调易用性 |
| 过滤/事务能力 | 强，天然继承 SQL 和事务能力 | 过滤可以做，但不是事务数据库 | 过滤能力较好，事务语义较弱 |
| 常见风险 | 索引重建影响数据库负载，IO 抢占明显 | 依赖面广，控制面和存储面排障复杂 | 集群参数、内存水位和分片治理要仔细设计 |
| 适用场景 | 已有 PostgreSQL、希望统一栈、规模可控 | 检索规模大、独立平台团队成熟 | 希望独立部署、快速落地、功能较均衡 |

无论选哪一种，运维上都要盯三件事：索引构建是否影响在线查询，过滤条件是否造成性能退化，数据发布是否可回滚。很多“向量库很慢”的问题，本质上是索引参数、元数据过滤和冷热数据混放造成的。

## reranker、上下文拼接与生成链路

reranker 的作用是把初次召回的候选结果重新排序，提升真正进入上下文的片段质量。它通常能提升准确率，但会引入额外模型调用和尾延迟，因此不应默认对所有流量开启。对高价值问答、复杂搜索和合规问答，reranker 往往值得；对低成本、低延迟接口，则要谨慎评估收益。

上下文拼接是 RAG 平台最容易被低估的环节。问题不在于“把 top-k 拼进去”这么简单，而在于 token 预算、片段去重、来源标注、冲突处理和模板稳定性。拼得过多会推高 TTFT 与成本，拼得过少又会损失召回收益。

生成链路里最好显式记录 query rewrite、检索命中文档、reranker 得分、最终上下文 token 数和引用来源。没有这些记录时，平台只能看到“模型答错了”，却不知道错在召回、重排还是模板。

## agent runtime、tool calling、memory、session state

这一节讨论四个彼此强相关的运行时概念：Agent 运行时（agent runtime）、工具调用（tool calling）、记忆（memory）和会话状态（session state）。后文分别简称为 agent runtime、工具调用、memory 和会话状态。

agent runtime 负责把“单次补全请求”扩展成多步执行。它通常包含计划器、工具调度器、状态存储、重试策略和执行边界。SRE 视角要把 agent runtime 当成一个有状态工作流系统，而不是一个普通 API。

工具调用最大的风险不是功能不可用，而是把外部系统的不稳定性带入主链路。搜索、数据库查询、工单系统、代码仓库、支付接口和内部 API 一旦超时，agent 整体响应时间会迅速失控。因此工具调用必须有超时、并发上限、幂等设计和结果缓存。

memory 与会话状态决定 agent 是否能持续完成多轮任务。短期 memory 常放在 Redis 或会话存储中，长期 memory 可能落在向量库、文档库或业务数据库里。这里要重点防止两类问题：会话状态膨胀导致上下文失控，以及状态不一致导致 agent 重复执行或误执行。

平台上最好明确区分：

- 会话状态：当前任务执行上下文，强调一致性和过期清理。
- 知识记忆：可复用事实或偏好，强调更新策略和权限控制。
- 工具结果缓存：强调 TTL、命中率和失效路径。

这三类东西混在一起时，问题会非常难排。

## 关键指标与告警

RAG/Agent 平台的指标至少应覆盖离线索引、在线检索、生成链路和工具执行四个面。

| 类别 | 核心指标 | 说明 |
| --- | --- | --- |
| 摄取/索引 | 摄取成功率、解析失败率、索引构建时长、索引发布时间 | 判断知识更新是否可信 |
| 检索 | query embedding 延迟、向量检索延迟、命中率、空召回率、过滤拒绝率 | 判断查得快不快、查得到查不到 |
| 上下文 | reranker 延迟、最终上下文 token 数、去重率、引用覆盖率 | 判断拼接是否过重或失真 |
| agent | 单任务步骤数、工具调用成功率、工具超时率、session state 大小 | 判断 agent 是否失控 |
| 体验/成本 | 端到端延迟、TTFT、重试率、单请求 token 成本 | 判断链路是否值得继续维持复杂度 |

告警设计要能区分“知识没更新”“查不到东西”“工具拖慢主链路”“会话状态爆炸”这几类不同故障。把它们全都折叠成一个 5xx 告警，排障效率会非常低。

## 典型故障与排查路径

| 故障现象 | 优先检查项 | 常见根因 |
| --- | --- | --- |
| 线上回答突然过时 | 最新索引版本、摄取任务状态、发布切换记录 | 索引发布失败、增量同步卡住、租户数据未更新 |
| 检索结果明显跑偏 | chunk 策略、embedding 模型版本、过滤条件、query rewrite | 向量重建不完整、元数据污染、模型升级不兼容 |
| 延迟突然上升 | query embedding、向量检索、reranker、上下文 token 数 | reranker 拖慢、top-k 过大、向量库热点 |
| agent 经常卡死或超时 | 工具调用耗时、步骤数、并发限制、session state | 外部 API 抖动、工具重试失控、状态膨胀 |
| 同一问题结果不稳定 | Prompt 模板、索引版本、路由模型、工具返回 | 多版本混用、缓存失效、非幂等工具 |

排障时优先判断问题落在离线链路还是在线链路。离线链路问题通常表现为“内容错、内容旧、内容缺”；在线链路问题通常表现为“慢、抖、工具失败、会话异常”。

## 设计权衡

- 更复杂的 chunk、reranker 和 agent 流程通常能提升质量，但会明显增加尾延迟和成本。
- 把向量检索放进 PostgreSQL 便于统一治理，但大规模下会承受更强的数据库负载压力。
- 独立向量数据库更适合规模化，但也引入新的控制面、备份和排障复杂度。
- 长会话 memory 提升体验，但更容易造成上下文膨胀、权限泄露和状态漂移。
- 强工具能力能扩大自动化边界，但同时把外部系统可靠性问题带进主链路。

因此平台设计应优先保证版本一致、排障可见和降级清晰，再追求更复杂的链路智能化。

## 实践建议

- 为摄取、索引构建和索引发布分别定义状态机与审计记录，避免“看起来更新了，实际没生效”。
- embedding 模型、chunk 策略和索引版本要显式绑定，升级时支持双写或双读验证。
- 对 reranker、tool calling、memory 和 session state 建立独立指标，不要全部折叠进“LLM 延迟”。
- agent runtime 必须有步骤上限、总时长上限、工具并发上限和人工兜底路径。
- 线上请求记录最终引用来源、上下文 token 数和工具调用摘要，便于复盘质量问题。
