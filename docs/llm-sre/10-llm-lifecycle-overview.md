# LLM SRE 10：生命周期总览

## 这篇文档解决什么问题

这篇文档回答两个核心问题：第一，LLM 从数据到应用到底经过哪些阶段；第二，SRE 和平台团队应该在哪些环节介入。很多团队把注意力集中在“模型上线”这一刻，但真正的风险分布在数据、训练、评测、制品、推理、成本、治理和应用编排的整条链路上。没有生命周期视角，就很容易把局部优化误当成系统能力。

## 系统全景

LLM 系统不是单一模型，而是一条持续演化的工程流水线。上游的数据质量会改变训练稳定性，训练与评测结果会影响发布门禁，发布策略会决定推理平台的风险暴露，线上观测又会反向驱动数据回流和版本迭代。

```text
        ┌────────────────┐
        │ 数据与样本工程 │
        └───────┬────────┘
                │
                v
        ┌────────────────┐
        │ 训练与 GPU 集群│
        └───────┬────────┘
                │
                v
        ┌────────────────┐
        │ 评测与验收门禁 │
        └───────┬────────┘
                │
                v
        ┌────────────────┐
        │ 制品与发布管理 │
        └───────┬────────┘
                │
                v
        ┌────────────────┐
        │ 推理与服务化   │
        └───────┬────────┘
                │
                v
        ┌───────────────────────────────┐
        │ 观测 / 容量 / 成本 / 治理     │
        └───────┬───────────────────────┘
                │
                v
        ┌────────────────┐
        │ RAG / Agent / 应用│
        └───────┬────────┘
                │
                v
        ┌────────────────┐
        │ 线上反馈与数据回流│
        └────────────────┘
```

建议把这条链路看成一个闭环系统，而不是线性项目计划。SRE 的价值在于保证闭环可观测、可恢复、可回滚、可审计。

## 阶段 1：数据与样本工程

数据是生命周期的起点，也是最容易被低估的系统性风险源。这里不仅包含原始语料、指令样本、偏好数据和评测集，还包含数据清洗、脱敏、去重、版本化、分层存储和访问控制。

工程上的关键点不是“有没有数据”，而是“数据是否可追溯、可复现、可治理”。样本格式变化、去重策略调整、标签口径漂移、训练集与评测集污染，都会在后续阶段放大。SRE 和平台团队要关注数据管道 SLA、元数据完整性、批处理延迟、数据湖权限边界，以及回填和重跑能力。

## 阶段 2：训练与集群

训练阶段把数据问题转化为资源问题。GPU 节点、网络拓扑、并行策略、存储带宽、调度队列和容器环境，都会直接影响吞吐、稳定性和训练成本。训练系统的本质是一个长时间运行、强耦合、对尾部故障非常敏感的分布式作业。

这里的 SRE 关注点通常包括：驱动和 CUDA/NCCL 版本矩阵是否稳定、拓扑感知调度是否准确、checkpoint 能否在故障前落盘、训练作业是否有明确的超时与重试策略、集群是否能隔离噪声租户。一个“能跑起来”的训练平台，不等于一个“能稳定迭代”的训练平台。

## 阶段 3：评测与验收

训练完成并不等于可发布。评测与验收阶段负责回答：模型是否比上一版更好，是否只是“换了一组 trade-off”，以及是否引入了新的风险。这里通常会同时存在离线基准、任务集回放、人工抽检、红队测试和安全合规检查。

从平台角度看，评测阶段需要强版本绑定。评测结果必须关联到具体的数据版本、训练配置、模型制品、tokenizer 和推理参数，否则结论不可复用。SRE 还需要确保评测环境隔离、资源配额明确、结果可审计，避免因为环境差异导致“实验室通过、线上退化”。

## 阶段 4：模型制品与发布

模型一旦进入制品阶段，就应该像镜像、二进制或 Helm Chart 一样被管理。权重文件、tokenizer、配置文件、推理模板、量化版本、LoRA 适配器和签名元数据都属于制品的一部分。缺少统一制品规范时，最常见的问题不是发布慢，而是回滚不清晰、依赖关系失真、产物来源不可信。

发布阶段的关键能力包括：制品仓库、不可变版本、灰度与回滚、兼容性校验、审批流和审计留痕。SRE 要推动“模型版本”和“服务版本”解耦，避免把应用发布和模型切换绑定成一次高风险事件。

## 阶段 5：推理与服务化

推理阶段是用户最直接感知的部分，但它只是生命周期中的一个服务出口。此时问题从“模型能不能训练好”转变成“请求能不能稳定、低延迟、低成本地被处理”。核心主题包括批处理、KV cache、并发控制、流式输出、弹性伸缩、降级策略和多模型路由。

SRE 在这里要像管理任何关键在线服务一样管理模型服务：定义可用性和延迟目标，区分 TTFT、TPOT、tokens/s 等 LLM 特有指标，设计限流、熔断、排队和 fallback 策略，并处理模型热加载、冷启动和容量突发。

## 阶段 6：观测、容量、成本与治理

很多组织把观测和治理当成上线后的补丁，这会直接导致成本失控和事故不可解释。LLM 系统需要同时观测基础设施、模型行为、应用效果和业务成本。只看 GPU 利用率，会忽略请求结构变化；只看质量指标，会忽略尾延迟和显存碎片。

容量规划应覆盖训练和推理两种完全不同的资源曲线。成本治理则要下沉到 token、实验、租户、项目和团队维度。治理还包含权限、审计、数据合规、内容安全、第三方模型依赖管理和供应链可信度。SRE 在这里承担“把复杂性结构化”的角色。

## 阶段 7：RAG / Agent / 应用平台

当模型进入 RAG、Agent 和应用平台阶段，系统边界再次扩大。问题不再只是模型本身，而是检索链路、工具调用、会话状态、外部 API、工作流编排和多阶段超时控制。很多线上故障最终表现为“模型答得不好”，但根因其实在索引过期、工具失败、上下文拼装错误或策略引擎失效。

对 SRE 来说，这一阶段意味着需要把单点模型服务观念升级为“复合 AI 工作流”观念。SLO 需要覆盖检索、推理、工具执行和最终响应，而不是只盯住模型 RPC。可观测性也要从单请求日志升级到链路级 tracing 和步骤级状态机。

## SRE 在整个生命周期中的职责

SRE 的职责不是替算法团队“看机器”，而是为生命周期建立可靠性控制面。典型职责包括：

- 为数据、训练、评测、发布和推理定义可操作的 SLI/SLO。
- 建设统一的日志、指标、追踪和审计链路，让版本、数据和故障能串起来。
- 推动 checkpoint、回滚、重试、隔离、配额和门禁等恢复性设计前置，而不是事故后补。
- 管理训练与推理共享资源池的容量、优先级和成本分摊。
- 参与变更评审，识别高风险发布窗口、跨阶段耦合和供应链风险。
- 用平台能力替代人工流程，减少“靠经验操作模型”的隐性单点。

## 常见组织误区

误区一是把 LLM 平台理解成“多几台 GPU 的 K8s 集群”。算力只是底座，真正难的是全链路的一致性和恢复性。误区二是只重视训练，不重视评测和发布，结果是模型质量无法稳定复现。误区三是只看在线可用性，不看训练产能和试验效率，最终让平台成为业务瓶颈。

另一个常见问题是团队边界切得过于机械：算法管训练、平台管机器、应用管上线，但没有人为整个生命周期结果负责。这样会导致版本语义断裂、故障归因拉扯、回滚链条过长。更有效的做法是围绕生命周期建立共享接口和明确门禁。
