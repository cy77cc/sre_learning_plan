# LLM SRE 12：训练基础设施与 GPU 集群

## 这篇文档解决什么问题

这篇文档聚焦训练平台的底层工程面：GPU 集群应该如何组织，节点、网络、驱动、存储和调度系统如何协同，以及 SRE 应该监控什么、在故障时先看哪里。目标不是介绍单个工具，而是帮助你建立“训练作业为什么会慢、会挂、会抖”的完整排障框架。

## 系统全景

训练平台通常由五层组成：硬件节点与高速互联、主机驱动与容器运行时、调度与队列系统、数据与 checkpoint 通道、观测与控制面。任何一层失稳，都会在上层表现为吞吐下降、作业失败或恢复时间过长。

平台团队需要明确三个关键边界：第一，节点是否被标准化管理；第二，调度器是否知道拓扑与配额；第三，存储是否能承受多节点并发读写。很多训练事故表面上像是框架问题，实际上是底层基础设施没有给分布式作业提供稳定的假设。

## GPU 节点、拓扑与互联

单节点内要看 GPU 型号、显存容量、NUMA 关系、PCIe 代际、NVLink/NVSwitch 连接方式，以及 GPU 到 NIC 的距离。跨节点则要看 RoCE 或 InfiniBand 网络、交换机收敛比、ECN/PFC 配置和东西向拥塞控制。训练任务对拓扑非常敏感，因为一次 all-reduce 的长尾就会拖慢全局 step time。

对 SRE 来说，拓扑不只是硬件清单，而是调度约束。需要保证作业落在兼容节点组上，尽量避免异构 GPU 混排、跨 NUMA 远程访问和非对称网络路径。资产管理中应长期维护节点拓扑标签，否则调度器无法做出正确决策。

## 驱动、CUDA、NCCL 与容器环境

训练平台最常见的隐患来自版本矩阵失控。主机驱动、CUDA runtime、NCCL、OFED、容器基础镜像、PyTorch/DeepSpeed/Megatron 等框架并不是独立升级的，它们共同决定作业能否稳定通信、是否触发性能回退，以及是否出现难复现的 hang。

平台侧应建立“经过验证的环境组合”，而不是允许团队自由拼装。推荐把驱动版本、CUDA 镜像、NCCL 调优参数和健康检查脚本作为标准发行物管理，并区分实验通道与生产通道。对线上训练集群来说，环境一致性通常比追求最新版本更重要。

## 调度体系：Kubernetes vs Slurm

Kubernetes 更适合与容器平台、配额、声明式发布和统一观测体系集成；Slurm 更接近传统 HPC 模式，在大规模训练队列、裸机控制和批处理语义上更直接。没有绝对优劣，关键在于你的平台目标是“统一云原生资源池”还是“最大化训练吞吐与作业控制”。

| 维度 | Kubernetes | Slurm |
| --- | --- | --- |
| 主要心智模型 | 面向容器服务和控制器 | 面向批处理作业和节点分配 |
| GPU 调度 | 依赖 device plugin、operator、扩展调度器 | 原生面向作业、分区和节点约束 |
| 多租户治理 | 命名空间、RBAC、配额、网络策略成熟 | 依赖账号、队列、分区和外部集成 |
| 弹性与自动化 | 易接 autoscaler、GitOps、服务网格 | 更适合稳定批作业，不强调服务化 |
| 运维生态 | 云原生工具丰富，学习曲线偏平台化 | HPC 经验成熟，学习曲线偏作业化 |
| 典型适用场景 | 训练与推理共平台、需要统一控制面 | 大规模独占训练集群、科研/HPC 环境 |

如果团队同时承担训练与推理，Kubernetes 往往能减少控制面碎片。但如果训练规模大、租户少、作业持续时间长、对裸机性能极度敏感，Slurm 的调度路径可能更短。SRE 需要围绕实际负载分布做决策，而不是围绕社区热度做决策。

## 存储、checkpoint 与数据通道

训练系统对存储的要求是双重的：一方面需要高吞吐读取训练数据，另一方面需要稳定写出 checkpoint。对象存储适合冷数据和制品归档，并行文件系统或本地 NVMe 更适合热路径。单靠共享 NAS 往往很快会在多节点并发下触发瓶颈。

checkpoint 的工程意义远大于“保存进度”。它决定了故障后的恢复时间、spot 资源是否可用、升级窗口是否可控。SRE 应明确 checkpoint 的目标恢复点，监控写入耗时、失败率、对象数量和恢复成功率，并验证 resume 真的可用，而不是只验证文件被写出来。

## 资源隔离与多租户

GPU 是高价值稀缺资源，多租户问题天然比 CPU 集群更敏感。隔离不仅是安全问题，更是性能稳定性问题。错误的共享策略会导致显存争抢、PCIe 拥塞、cache 污染、网卡抢占和 noisy neighbor 问题。

常见隔离手段包括：基于节点池的物理隔离、基于队列和优先级的调度隔离、基于 MIG 的硬切分、基于 namespace/project 的配额管理，以及训练/推理资源池分离。SRE 要避免“表面公平、实际浪费”的策略，例如把大作业排进碎片化节点池，导致整体利用率和成功率同时下降。

## 关键指标与告警

训练平台的核心指标应覆盖四个层面：

- 节点层：GPU 利用率、显存占用、温度、功耗、ECC 错误、Xid、PCIe 重传、网卡错误。
- 作业层：step time、samples/s、tokens/s、作业排队时间、重启次数、失败率、checkpoint 时长。
- 存储层：读写吞吐、IOPS、延迟、对象存储 5xx、文件系统元数据延迟。
- 调度层：待调度作业数、资源碎片率、队列等待分位数、抢占次数、节点不可调度比例。

告警设计要避免只盯底层硬件。真正有用的告警应该能把“GPU 温度升高”关联到“某个作业 step time 抖动”和“checkpoint 超时”，否则值班人员只能看到噪声，无法快速定位影响面。

## 典型故障与排查路径

| 故障现象 | 优先检查项 | 常见根因 |
| --- | --- | --- |
| 作业启动后卡在初始化 | 驱动版本、容器镜像、NCCL 初始化日志、GPU 可见性 | 驱动与 CUDA 不兼容，设备插件异常，容器缺少 RDMA/NCCL 依赖 |
| 多节点训练吞吐明显低于预期 | all-reduce 时间、GPU 到 NIC 拓扑、交换机错误计数 | 跨机网络拥塞，拓扑感知调度失效，落到非对称节点组 |
| 训练运行数小时后随机失败 | dmesg/Xid、ECC、节点事件、磁盘与网卡错误 | GPU 硬件不稳定，主机内核异常，节点出现间歇性 I/O 错误 |
| checkpoint 经常超时 | 写入带宽、文件数量、对象存储响应码、元数据延迟 | 共享存储拥塞，小文件过多，缺少异步或分片写策略 |
| 部分租户经常排队过久 | 队列等待分位数、资源碎片率、优先级策略 | 节点池切分不合理，大作业无法连续分配，配额模型过粗 |

排查训练平台问题时，建议先判断是“单节点问题、拓扑问题、共享资源问题还是调度问题”。这个分类能显著缩短排障时间。直接从框架日志往下挖，往往会错过真正的系统瓶颈。

## 设计权衡

训练平台设计通常在四组目标之间取舍：峰值吞吐与资源利用率、环境自由度与平台稳定性、共享资源池与强隔离、快速交付与严格治理。没有一种架构能同时把这四组目标拉满。

例如，共享大集群能够提高总体利用率，但会放大碎片化和噪声租户问题；完全标准化镜像能提升稳定性，却会降低算法团队试验速度。SRE 需要把这些权衡显式化，并通过分层环境、节点分池和门禁策略减少“全有或全无”的冲突。

## 实践建议

- 先建立少量经过验证的标准环境，再逐步开放实验环境，不要让每个项目维护自己的 CUDA 宇宙。
- 让调度器感知节点拓扑、GPU 类型和网卡布局，避免只按“有几张卡”做分配。
- 把 checkpoint 当成恢复机制来设计和演练，而不是当成训练副产物。
- 为 GPU 节点建立准入与摘除流程，包括 burn-in、健康检查、Xid/ECC 基线和自动隔离。
- 分开统计训练产能和推理容量，避免用同一套利用率指标指导两类完全不同的业务。
