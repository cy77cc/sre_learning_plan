### 2. vLLM 深入

#### 2.1 vLLM 核心技术

```
┌──────────────────────────────────────────────────────────────┐
│                    vLLM 核心技术                               │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  1. PagedAttention（分页注意力）                               │
│  ┌────────────────────────────────────────────────────────┐ │
│  │  问题: KV Cache 需要连续内存，导致显存碎片化              │ │
│  │                                                        │ │
│  │  解决: 借鉴操作系统虚拟内存的分页机制                     │ │
│  │                                                        │ │
│  │  ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐                    │ │
│  │  │Block│ │Block│ │Block│ │Block│  物理显存块           │ │
│  │  │  0  │ │  1  │ │  2  │ │  3  │  (固定大小)          │ │
│  │  └─────┘ └─────┘ └─────┘ └─────┘                    │ │
│  │     ▲       ▲       ▲       ▲                         │ │
│  │     │       │       │       │                         │ │
│  │  ┌──┴───┐┌──┴───┐┌──┴───┐┌──┴───┐                   │ │
│  │  │逻辑页││逻辑页││逻辑页││逻辑页│  逻辑 KV Cache       │ │
│  │  │  0   ││  1   ││  2   ││  3   │  (通过页表映射)     │ │
│  │  └──────┘└──────┘└──────┘└──────┘                   │ │
│  │                                                        │ │
│  │  优势:                                                  │ │
│  │  - 消除显存碎片，显存利用率接近 100%                     │ │
│  │  - 支持动态增长，不需要预分配最大长度                     │ │
│  │  - 支持 copy-on-write，共享相同前缀的请求               │ │
│  └────────────────────────────────────────────────────────┘ │
│                                                              │
│  2. Continuous Batching（连续批处理）                          │
│  ┌────────────────────────────────────────────────────────┐ │
│  │  传统 Static Batching:                                  │ │
│  │  ┌──────────────────────────────────────────────┐     │ │
│  │  │ Request A: ████████░░░░░░░░░░  (等待)        │     │ │
│  │  │ Request B: ████████████████░░  (等待)        │     │ │
│  │  │ Request C: ██████░░░░░░░░░░░░  (等待)        │     │ │
│  │  └──────────────────────────────────────────────┘     │ │
│  │  问题: 最短请求完成后，GPU 空闲等待最长请求              │ │
│  │                                                        │ │
│  │  Continuous Batching:                                   │ │
│  │  ┌──────────────────────────────────────────────┐     │ │
│  │  │ Request A: ████████  完成，新请求 D 加入       │     │ │
│  │  │ Request B: ████████████████                   │     │ │
│  │  │ Request C: ██████  完成，新请求 E 加入          │     │ │
│  │  │ Request D:         ████████████               │     │ │
│  │  │ Request E:              ██████████            │     │ │
│  │  └──────────────────────────────────────────────┘     │ │
│  │  优势: GPU 始终保持忙碌，吞吐量提升 2-3 倍               │ │
│  └────────────────────────────────────────────────────────┘ │
│                                                              │
│  3. Speculative Decoding（投机解码）                          │
│  ┌────────────────────────────────────────────────────────┐ │
│  │  用小模型快速生成多个候选 token                           │ │
│  │  用大模型并行验证这些 token                               │ │
│  │  接受正确的前缀，拒绝错误的                               │ │
│  │  效果: 延迟降低 2-3 倍，输出质量不变                      │ │
│  └────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────┘
```

#### 2.4 vLLM 关键参数说明

| 参数 | 说明 | 默认值 | 推荐值 |
|------|------|--------|--------|
| `--max-model-len` | 最大上下文长度 | 模型最大 | 按需设置（越小越省显存） |
| `--tensor-parallel-size` | 张量并行 GPU 数 | 1 | 2/4/8（按 GPU 数量） |
| `--gpu-memory-utilization` | GPU 显存使用比例 | 0.9 | 0.85-0.95 |
| `--max-num-seqs` | 最大并发序列数 | 256 | 64-256（按显存） |
| `--max-num-batched-tokens` | 最大批次 token 数 | 模型最大 | 按需设置 |
| `--enable-chunked-prefill` | 分块 Prefill | False | True（长上下文推荐） |
| `--enforce-eager` | 禁用 CUDA Graph | False | False（性能更好） |
| `--quantization` | 量化方法 | None | gptq/awq/fp8 |
| `--dtype` | 数据类型 | auto | auto/bfloat16/float16 |
| `--disable-log-requests` | 禁用请求日志 | False | True（生产环境） |

#### 4.2 量化技术详解

```
┌──────────────────────────────────────────────────────────────┐
│                    量化技术原理                                │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  原始模型 (FP16):                                            │
│  每个参数占 2 bytes                                           │
│  70B 模型 = 140 GB                                           │
│                                                              │
│  INT8 量化:                                                  │
│  每个参数占 1 byte                                            │
│  70B 模型 = 70 GB   (显存减半，精度损失极小)                   │
│                                                              │
│  INT4 量化:                                                  │
│  每个参数占 0.5 byte                                          │
│  70B 模型 = 35 GB   (显存减至 1/4，精度略有损失)              │
│                                                              │
│  ┌────────────────────────────────────────────────────────┐ │
│  │  量化方法对比                                           │ │
│  │                                                        │ │
│  │  GPTQ (Post-Training Quantization):                    │ │
│  │  ├─ 基于权重校准集的后训练量化                           │ │
│  │  ├─ 将 FP16 权重量化为 INT4                             │ │
│  │  ├─ 需要校准数据（几百条样本）                           │ │
│  │  ├─ 量化过程耗时（数小时）                               │ │
│  │  └─ 量化后推理速度快，质量损失可控                       │ │
│  │                                                        │ │
│  │  AWQ (Activation-aware Weight Quantization):           │ │
│  │  ├─ 基于激活值分布的权重量化                             │ │
│  │  ├─ 保护重要权重通道不被量化                             │ │
│  │  ├─ 无需大量校准数据                                    │ │
│  │  ├─ 量化质量通常优于 GPTQ                               │ │
│  │  └─ 量化速度更快                                       │ │
│  │                                                        │ │
│  │  GGUF (GPT-Generated Unified Format):                  │ │
│  │  ├─ llama.cpp 使用的格式                                │ │
│  │  ├─ 支持多种量化级别 (Q2-Q8)                            │ │
│  │  ├─ 支持 CPU + GPU 混合推理                             │ │
│  │  ├─ 适合消费级硬件                                      │ │
│  │  └─ Ollama 默认使用 GGUF 格式                           │ │
│  │                                                        │ │
│  │  FP8 (H100 专属):                                      │ │
│  │  ├─ H100 Tensor Core 原生支持                           │ │
│  │  ├─ 8-bit 浮点，精度接近 FP16                           │ │
│  │  ├─ 推理速度提升约 2 倍                                 │ │
│  │  └─ 需要 H100 GPU                                      │ │
│  └────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────┘
```

#### 4.3 量化效果对比

```python
#!/usr/bin/env python3
"""quantization_benchmark.py - 量化效果对比"""

import time
import requests
import json

# 测试不同量化级别
configs = [
    {"name": "FP16 (原始)", "model": "meta-llama/Llama-3.1-8B-Instruct"},
    {"name": "GPTQ INT4",   "model": "TheBloke/Llama-3.1-8B-Instruct-GPTQ"},
    {"name": "AWQ INT4",    "model": "TheBloke/Llama-3.1-8B-Instruct-AWQ"},
]

test_prompts = [
    "What is Site Reliability Engineering?",
    "Explain the difference between SLO, SLA, and SLI.",
    "How does Kubernetes handle pod scheduling?",
    "What are the golden signals in monitoring?",
    "Describe the incident response process.",
]

def test_inference(base_url: str, model: str, prompt: str) -> dict:
    """测试单次推理"""
    start = time.time()
    response = requests.post(
        f"{base_url}/v1/completions",
        json={
            "model": model,
            "prompt": prompt,
            "max_tokens": 200,
            "stream": False,
        },
    )
    elapsed = time.time() - start

    if response.status_code == 200:
        data = response.json()
        usage = data.get("usage", {})
        return {
            "latency_s": round(elapsed, 2),
            "prompt_tokens": usage.get("prompt_tokens", 0),
            "completion_tokens": usage.get("completion_tokens", 0),
            "total_tokens": usage.get("total_tokens", 0),
        }
    return {"error": response.text}

def run_benchmark(base_url: str, model: str, name: str):
    """运行基准测试"""
    print(f"\n=== {name} ({model}) ===")
    results = []
    for prompt in test_prompts:
        result = test_inference(base_url, model, prompt)
        results.append(result)
        if "error" not in result:
            print(f"  Latency: {result['latency_s']}s, "
                  f"Tokens: {result['total_tokens']}")
        else:
            print(f"  Error: {result['error']}")

    latencies = [r["latency_s"] for r in results if "error" not in r]
    if latencies:
        print(f"  Avg Latency: {sum(latencies)/len(latencies):.2f}s")

if __name__ == "__main__":
    for config in configs:
        run_benchmark("http://localhost:8000", config["model"], config["name"])
```

#### 4.4 量化操作实践

```bash
# 1. 使用 AutoGPTQ 量化模型
pip install auto-gptq autoawq

# GPTQ 量化
python3 << 'EOF'
from transformers import AutoTokenizer
from auto_gptq import AutoGPTQForCausalLM, BaseQuantize_config

model_id = "meta-llama/Llama-3.1-8B-Instruct"
quantize_config = BaseQuantize_config(
    bits=4,
    group_size=128,
    damp_percent=0.01,
    desc_act=True,
)

tokenizer = AutoTokenizer.from_pretrained(model_id)
model = AutoGPTQForCausalLM.from_pretrained(model_id, quantize_config)

# 加载校准数据
from datasets import load_dataset
dataset = load_dataset("wikitext", "wikitext-2-raw-v1", split="train[:128]")
calibration_data = [tokenizer(text["text"]) for text in dataset if text["text"].strip()]

# 执行量化
model.quantize(calibration_data)
model.save_quantized("./llama-3.1-8b-gptq")
tokenizer.save_pretrained("./llama-3.1-8b-gptq")
print("GPTQ 量化完成")
EOF

# 2. AWQ 量化
python3 << 'EOF'
from awq import AutoAWQForCausalLM
from transformers import AutoTokenizer

model_id = "meta-llama/Llama-3.1-8B-Instruct"
quant_config = {"zero_point": True, "q_group_size": 128, "w_bit": 4}

model = AutoAWQForCausalLM.from_pretrained(model_id)
tokenizer = AutoTokenizer.from_pretrained(model_id)

# AWQ 量化（自动校准）
model.quantize(tokenizer, quant_config=quant_config)
model.save_quantized("./llama-3.1-8b-awq")
tokenizer.save_pretrained("./llama-3.1-8b-awq")
print("AWQ 量化完成")
EOF

# 3. 转换为 GGUF 格式（供 Ollama 使用）
# 使用 llama.cpp 的转换工具
git clone https://github.com/ggerganov/llama.cpp.git
cd llama.cpp
python3 convert_hf_to_gguf.py ../llama-3.1-8b-instruct --outfile llama-3.1-8b-instruct-f16.gguf --outtype f16

# GGUF 量化
./llama-quantize llama-3.1-8b-instruct-f16.gguf llama-3.1-8b-instruct-q4_k_m.gguf Q4_K_M
```

### 5. 批处理与流式输出

#### 5.1 批处理策略

```
┌──────────────────────────────────────────────────────────────┐
│                    批处理策略对比                              │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  1. Static Batching（静态批处理）                             │
│  ┌────────────────────────────────────────────────────────┐ │
│  │  收集 N 个请求 → 组成一个批次 → 同时处理                 │ │
│  │  优点: 实现简单，GPU 利用率高                            │ │
│  │  缺点: 等待时间长，短请求被长请求阻塞                    │ │
│  │  适用: 离线批处理，对延迟不敏感                          │ │
│  └────────────────────────────────────────────────────────┘ │
│                                                              │
│  2. Dynamic Batching（动态批处理）                            │
│  ┌────────────────────────────────────────────────────────┐ │
│  │  在时间窗口内收集请求 → 组成批次 → 处理                  │ │
│  │  优点: 减少等待时间                                     │ │
│  │  缺点: 批次大小不固定，GPU 利用率不稳定                  │ │
│  │  适用: 中等延迟要求的场景                                │ │
│  └────────────────────────────────────────────────────────┘ │
│                                                              │
│  3. Continuous Batching（连续批处理）- vLLM 核心              │
│  ┌────────────────────────────────────────────────────────┐ │
│  │  每个 decode step 都可以加入新请求、移除完成的请求        │ │
│  │  优点: GPU 利用率最高，吞吐量最大                        │ │
│  │  缺点: 实现复杂                                        │ │
│  │  适用: 在线推理服务（推荐）                              │ │
│  └────────────────────────────────────────────────────────┘ │
│                                                              │
│  4. Chunked Prefill（分块 Prefill）                          │
│  ┌────────────────────────────────────────────────────────┐ │
│  │  将长输入的 Prefill 分成多个 chunk                      │ │
│  │  与其他请求的 Decode 交错执行                            │ │
│  │  优点: 长输入不会阻塞其他请求                            │ │
│  │  缺点: 略增加总延迟                                     │ │
│  │  适用: 输入长度差异大的场景                              │ │
│  └────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────┘
```

```python
# fastapi_llm_server.py - 带流式输出的 LLM API 服务
from fastapi import FastAPI, HTTPException
from fastapi.responses import StreamingResponse
from pydantic import BaseModel
from typing import List, Optional, AsyncGenerator
import httpx
import json
import time

app = FastAPI(title="LLM Inference Proxy")

VLLM_BASE_URL = "http://localhost:8000"

class Message(BaseModel):
    role: str
    content: str

class ChatCompletionRequest(BaseModel):
    model: str
    messages: List[Message]
    max_tokens: Optional[int] = 512
    temperature: Optional[float] = 0.7
    stream: Optional[bool] = False

@app.post("/v1/chat/completions")
async def chat_completions(request: ChatCompletionRequest):
    """OpenAI 兼容的 Chat Completions API"""

    # 构建转发请求
    payload = {
        "model": request.model,
        "messages": [m.dict() for m in request.messages],
        "max_tokens": request.max_tokens,
        "temperature": request.temperature,
        "stream": request.stream,
    }

    if request.stream:
        return StreamingResponse(
            stream_response(payload),
            media_type="text/event-stream",
        )
    else:
        async with httpx.AsyncClient(timeout=120.0) as client:
            response = await client.post(
                f"{VLLM_BASE_URL}/v1/chat/completions",
                json=payload,
            )
            return response.json()

async def stream_response(payload: dict) -> AsyncGenerator[str, None]:
    """流式输出代理"""
    async with httpx.AsyncClient(timeout=120.0) as client:
        async with client.stream(
            "POST",
            f"{VLLM_BASE_URL}/v1/chat/completions",
            json=payload,
        ) as response:
            async for line in response.aiter_lines():
                if line.startswith("data: "):
                    data = line[6:]
                    if data.strip() == "[DONE]":
                        yield "data: [DONE]\n\n"
                        break
                    yield f"data: {data}\n\n"

@app.get("/health")
async def health():
    """健康检查"""
    try:
        async with httpx.AsyncClient(timeout=5.0) as client:
            response = await client.get(f"{VLLM_BASE_URL}/health")
            return {"status": "healthy", "backend": response.status_code}
    except Exception as e:
        raise HTTPException(status_code=503, detail=str(e))

@app.get("/metrics")
async def metrics():
    """Prometheus 指标端点"""
    try:
        async with httpx.AsyncClient(timeout=5.0) as client:
            response = await client.get(f"{VLLM_BASE_URL}/metrics")
            return StreamingResponse(
                iter([response.text]),
                media_type="text/plain",
            )
    except Exception as e:
        raise HTTPException(status_code=503, detail=str(e))
```

## 🎯 面试题精选

### 1. 解释 vLLM 的 PagedAttention 技术，它解决了什么问题？

**参考答案**：
PagedAttention 是 vLLM 的核心技术，借鉴了操作系统的虚拟内存分页机制来管理 KV Cache。

解决的问题：传统 LLM 推理中，KV Cache 需要预分配连续的显存空间，导致：
1. **显存碎片化**：不同请求的 KV Cache 大小不同，释放后留下碎片
2. **显存浪费**：需要按最大长度预分配，实际使用可能远小于此
3. **无法共享**：相同前缀的请求无法共享 KV Cache

PagedAttention 的解决方案：
- 将 KV Cache 分成固定大小的"页"（Block）
- 使用页表将逻辑地址映射到物理显存地址
- 支持按需分配，用多少分配多少
- 支持 Copy-on-Write，共享相同前缀
- 显存利用率从约 20-40% 提升到接近 100%

### 2. Continuous Batching 和 Static Batching 有什么区别？

**参考答案**：
- **Static Batching**：收集固定数量的请求组成一个批次，等所有请求完成后才处理下一批。问题：短请求完成后 GPU 空闲等待长请求，造成浪费。
- **Continuous Batching**：每个 decode step 都可以动态加入新请求、移除已完成的请求。GPU 始终保持忙碌。

效果：Continuous Batching 可以将吞吐量提升 2-3 倍。vLLM 和 TGI 都支持 Continuous Batching。

### 3. GPTQ 和 AWQ 量化有什么区别？如何选择？

**参考答案**：
- **GPTQ**：基于二阶信息（Hessian 矩阵）的后训练量化。需要校准数据集，量化过程较慢（数小时）。技术成熟，社区支持好。
- **AWQ**：基于激活值分布的权重量化。保护重要权重通道，量化速度更快，质量通常优于 GPTQ。

选择建议：
- 新项目优先尝试 AWQ（质量更好，速度更快）
- 已有 GPTQ 模型可以继续使用
- 两者都支持 4-bit 量化，显存节省相同
- 使用 vLLM 部署时两者兼容性都很好

### 4. 如何设计一个高可用的 LLM 推理服务？

**参考答案**：
1. **多实例部署**：部署多个 vLLM 实例，使用负载均衡分发请求
2. **健康检查**：配置 /health 端点，自动剔除不健康实例
3. **流式输出**：使用 SSE 实现流式输出，改善用户体验
4. **限流保护**：在网关层实现请求限流，防止过载
5. **超时控制**：设置合理的请求超时时间（推荐 300s）
6. **优雅关闭**：处理完当前请求后再关闭实例
7. **自动扩缩容**：基于 GPU 利用率和队列长度进行扩缩容
8. **故障转移**：请求失败时自动重试其他实例
9. **模型预热**：启动时预加载模型，减少冷启动时间
10. **监控告警**：监控 TTFT、TPS、GPU 利用率等关键指标

### 5. 流式输出（Streaming）的实现原理是什么？对运维有什么影响？

**参考答案**：
流式输出使用 Server-Sent Events（SSE）协议：
1. 客户端发送请求，设置 `stream: true`
2. 服务端返回 `Content-Type: text/event-stream`
3. 每生成一个 token，立即发送一个 SSE 事件
4. 最后发送 `data: [DONE]` 标记结束

运维影响：
- **超时设置**：流式连接保持时间长，需要增大 proxy_read_timeout
- **缓冲关闭**：必须禁用 Nginx 的 proxy_buffering，否则会缓冲所有数据再发送
- **连接管理**：大量并发流式连接占用文件描述符，需要调整 ulimit
- **监控困难**：传统的请求延迟指标不再适用，需要测量 TTFT 和 TPS
- **负载均衡**：流式连接会长时间占用后端连接，影响负载均衡策略

### 6. 什么是 GGUF 格式？它与其他格式有什么区别？

**参考答案**：
GGUF（GPT-Generated Unified Format）是 llama.cpp 使用的模型格式，主要用于 CPU/GPU 混合推理。

特点：
- 支持多种量化级别（Q2_K 到 Q8_0），灵活性高
- 支持纯 CPU 推理，也支持 CPU + GPU 混合推理
- 文件自包含（包含 tokenizer、元数据等）
- 适合消费级硬件（笔记本、台式机）

与其他格式的区别：
- vs SafeTensors：GGUF 支持量化，SafeTensors 主要是 FP16
- vs TensorRT：GGUF 通用性好，TensorRT 只支持 NVIDIA GPU
- vs GPTQ/AWQ：GGUF 支持更多量化级别，GPTQ/AWQ 主要是 INT4
