## 📖 核心知识点

### 1. Kubernetes 调度器原理

#### 1.1 调度器架构

```
┌─────────────────────────────────────────────────────────────────┐
│                      kube-scheduler                              │
│                                                                 │
│  ┌──────────┐    ┌──────────────┐    ┌──────────────┐          │
│  │  Watch   │───>│   Filter     │───>│   Score      │          │
│  │  (Informer)   │  (Predicates)│    │  (Priority)  │          │
│  └──────────┘    └──────────────┘    └──────────────┘          │
│       │                │                    │                   │
│       v                v                    v                   │
│  监听未调度     过滤不满足条件        对候选节点打分             │
│  的 Pod         的节点               选择最优节点               │
│                                            │                   │
│                                            v                   │
│                                     ┌──────────────┐           │
│                                     │    Bind       │           │
│                                     │  (绑定 Pod)   │           │
│                                     └──────────────┘           │
└─────────────────────────────────────────────────────────────────┘
```

#### 1.2 调度流程详解

Kubernetes 调度器的工作流程分为三个阶段：

**阶段一：过滤（Filtering / Predicates）**

过滤阶段会排除不满足 Pod 调度需求的节点，包括：

- 资源不足（CPU、内存请求超出节点可用量）
- NodeSelector 不匹配
- NodeAffinity 不满足
- Taint 不被容忍
- 节点状态异常（NotReady、DiskPressure 等）
- PodAffinity/PodAntiAffinity 约束
- 拓扑分布约束不满足

**阶段二：打分（Scoring / Priorities）**

通过过滤的节点进入打分阶段，调度器根据多个优先级函数为节点评分：

- `LeastRequestedPriority`：资源空闲越多，分数越高
- `BalancedResourceAllocation`：CPU 和内存使用率越均衡，分数越高
- `ImageLocalityPriority`：节点上已有镜像，分数越高
- `InterPodAffinityPriority`：满足 Pod 亲和性规则加分
- `TopologySpreadConstraints`：满足拓扑分布加分

**阶段三：绑定（Binding）**

选择得分最高的节点，通过 API Server 将 Pod 绑定到该节点。

```
调度流程时间线：

Pod 创建 (Pending)
    │
    ├── 1. Informer 检测到未调度 Pod
    │
    ├── 2. 过滤阶段
    │   ├── 检查 nodeSelector
    │   ├── 检查 nodeAffinity
    │   ├── 检查 Taint/Toleration
    │   ├── 检查资源请求
    │   ├── 检查 PodAffinity/PodAntiAffinity
    │   └── 检查 TopologySpreadConstraints
    │
    ├── 3. 打分阶段
    │   ├── 资源均衡打分
    │   ├── 亲和性打分
    │   └── 拓扑分布打分
    │
    ├── 4. 选择最优节点
    │
    ├── 5. 绑定 Pod 到节点
    │
    └── 6. kubelet 拉取镜像，创建容器
```

#### 1.3 调度器配置查看

```bash
# 查看调度器配置
kubectl get pods -n kube-system | grep scheduler

# 查看调度器日志
kubectl logs -n kube-system -l component=kube-scheduler --tail=50

# 查看 Pod 的调度结果
kubectl describe pod <pod-name> | grep -A 5 "Events:"

# 查看节点的调度状态
kubectl describe node <node-name> | grep -A 10 "Conditions:"
```

#### 1.4 调度失败排查

```bash
# 查找所有 Pending 状态的 Pod
kubectl get pods --all-namespaces --field-selector=status.phase=Pending

# 查看调度失败原因
kubectl describe pod <pod-name> -n <namespace> | grep -A 20 "Events:"

# 常见调度失败原因：
# - FailedScheduling: 0/N nodes are available
# - Insufficient cpu: 节点 CPU 不足
# - Insufficient memory: 节点内存不足
# - node(s) had taint: 节点有污点且 Pod 无容忍
# - node(s) didn't match node selector: nodeSelector 不匹配
```

### 2. nodeSelector — 最简单的节点选择

#### 2.1 基本原理

nodeSelector 是最简单的节点选择约束，通过标签（Label）将 Pod 调度到特定节点上。

```
节点标签匹配流程：

Pod spec.nodeSelector:
  disktype: ssd
  zone: us-east-1a

    │
    v

检查所有节点的标签：

Node-1: disktype=ssd, zone=us-east-1a  ✓ 匹配
Node-2: disktype=hdd, zone=us-east-1a  ✗ disktype 不匹配
Node-3: disktype=ssd, zone=us-west-2a  ✗ zone 不匹配
```

#### 2.2 配置示例

```yaml
# 给节点打标签
# kubectl label nodes node-1 disktype=ssd zone=us-east-1a
# kubectl label nodes node-2 disktype=hdd zone=us-east-1a

apiVersion: v1
kind: Pod
metadata:
  name: nginx-ssd
spec:
  nodeSelector:
    disktype: ssd
    zone: us-east-1a
  containers:
    - name: nginx
      image: nginx:1.25
      resources:
        requests:
          cpu: "100m"
          memory: "128Mi"
        limits:
          cpu: "200m"
          memory: "256Mi"
```

#### 2.3 管理节点标签

```bash
# 查看节点标签
kubectl get nodes --show-labels

# 给节点添加标签
kubectl label nodes node-1 disktype=ssd zone=us-east-1a env=production

# 修改标签（需要 --overwrite）
kubectl label nodes node-1 disktype=nvme --overwrite

# 删除标签（加 - 号后缀）
kubectl label nodes node-1 disktype-

# 按标签筛选节点
kubectl get nodes -l disktype=ssd
kubectl get nodes -l "zone in (us-east-1a, us-east-1b)"
```

#### 2.4 nodeSelector 的局限性

- 只支持精确匹配（AND 关系），不支持 OR、NOT 等逻辑
- 不支持软约束（prefer）
- 不支持复杂的匹配表达式
- 如果没有满足条件的节点，Pod 将一直处于 Pending 状态

### 3. nodeAffinity — 高级节点亲和性

#### 3.1 两种亲和性类型

```
┌─────────────────────────────────────────────────────────────┐
│                    nodeAffinity 类型                          │
├─────────────────────────────┬───────────────────────────────┤
│  requiredDuringScheduling   │  preferredDuringScheduling    │
│  IgnoredDuringExecution     │  IgnoredDuringExecution       │
├─────────────────────────────┼───────────────────────────────┤
│  硬性要求（必须满足）        │  软性偏好（尽量满足）         │
│  不满足则 Pod 不调度         │  不满足也会调度到其他节点      │
│  类似 nodeSelector 的效果    │  通过 weight 设置偏好权重      │
└─────────────────────────────┴───────────────────────────────┘

IgnoredDuringExecution 含义：
  - 调度时必须满足/尽量满足
  - 节点标签变更后，已运行的 Pod 不会被驱逐
```

#### 3.2 匹配操作符

| 操作符 | 含义 | 示例 |
|--------|------|------|
| In | 值在列表中 | `values: ["ssd", "nvme"]` |
| NotIn | 值不在列表中 | `values: ["hdd"]` |
| Exists | 标签存在（不检查值） | `key: disktype` |
| DoesNotExist | 标签不存在 | `key: disktype` |
| Gt | 值大于（字符串比较） | `values: ["3"]` |
| Lt | 值小于（字符串比较） | `values: ["5"]` |

#### 3.3 requiredDuringSchedulingIgnoredDuringExecution（硬性约束）

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      affinity:
        nodeAffinity:
          # 硬性约束：必须调度到 SSD 磁盘的节点
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: disktype
                    operator: In
                    values:
                      - ssd
                      - nvme
              - matchExpressions:
                  - key: kubernetes.io/arch
                    operator: In
                    values:
                      - amd64
                      - arm64
      containers:
        - name: web
          image: nginx:1.25
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"
```

注意：多个 nodeSelectorTerms 之间是 OR 关系，同一 term 内的 matchExpressions 是 AND 关系。

#### 3.4 preferredDuringSchedulingIgnoredDuringExecution（软性偏好）

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: batch-job
spec:
  affinity:
    nodeAffinity:
      # 软性偏好：优先调度到 us-east-1a 区域
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 80  # 权重 1-100
          preference:
            matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values:
                  - us-east-1a
        - weight: 20
          preference:
            matchExpressions:
              - key: node-type
                operator: NotIn
                values:
                  - spot
  containers:
    - name: batch
      image: busybox:1.36
      command: ["sh", "-c", "echo hello && sleep 3600"]
```

#### 3.5 nodeAffinity 与 nodeSelector 对比

| 特性 | nodeSelector | nodeAffinity |
|------|-------------|--------------|
| 匹配方式 | 精确匹配 | 丰富的操作符 |
| 逻辑关系 | 仅 AND | AND + OR |
| 软性约束 | 不支持 | supported（preferred） |
| 权重控制 | 不支持 | supported（weight） |
| 复杂度 | 简单 | 灵活 |
| 推荐场景 | 简单标签匹配 | 生产环境推荐 |

### 4. podAffinity 与 podAntiAffinity — Pod 间亲和与反亲和

#### 4.1 基本概念

```
podAffinity（Pod 亲和性）：
  将 Pod 调度到与其他特定 Pod 在同一拓扑域的节点上

podAntiAffinity（Pod 反亲和性）：
  将 Pod 调度到与其他特定 Pod 不在同一拓扑域的节点上

拓扑域由 topologyKey 定义：
  - kubernetes.io/hostname    → 同一节点
  - topology.kubernetes.io/zone  → 同一可用区
  - topology.kubernetes.io/region → 同一区域
  - 自定义标签                → 自定义拓扑域
```

#### 4.2 亲和性与反亲和性的拓扑域

```
Region: us-east-1
├── Zone: us-east-1a
│   ├── Node-1: [Pod-A, Pod-B]     ← podAntiAffinity 避免同一节点
│   └── Node-2: [Pod-C]
├── Zone: us-east-1b
│   ├── Node-3: [Pod-D]
│   └── Node-4: [Pod-E]
└── Zone: us-east-1c
    ├── Node-5: [Pod-F]
    └── Node-6: [Pod-G]

podAffinity (topologyKey: topology.kubernetes.io/zone):
  Pod-X 会优先调度到与 Pod-A 同一 zone 的节点

podAntiAffinity (topologyKey: topology.kubernetes.io/zone):
  Pod-X 不会调度到 Pod-A 所在 zone 的任何节点
```

#### 4.3 podAffinity 配置示例

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cache-client
  namespace: production
spec:
  replicas: 3
  selector:
    matchLabels:
      app: cache-client
  template:
    metadata:
      labels:
        app: cache-client
        tier: backend
    spec:
      affinity:
        podAffinity:
          # 硬性约束：必须与 Redis Pod 在同一节点
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchExpressions:
                  - key: app
                    operator: In
                    values:
                      - redis
              topologyKey: kubernetes.io/hostname
          # 软性偏好：优先与 API Pod 在同一可用区
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 70
              podAffinityTerm:
                labelSelector:
                  matchExpressions:
                    - key: app
                      operator: In
                      values:
                        - api-server
                topologyKey: topology.kubernetes.io/zone
      containers:
        - name: cache-client
          image: redis-client:1.0
```

#### 4.4 podAntiAffinity — 高可用必备

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-server
  namespace: production
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-server
  template:
    metadata:
      labels:
        app: web-server
        tier: frontend
    spec:
      affinity:
        podAntiAffinity:
          # 硬性约束：同一节点不能运行多个 web-server Pod
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchExpressions:
                  - key: app
                    operator: In
                    values:
                      - web-server
              topologyKey: kubernetes.io/hostname
          # 软性偏好：尽量分散到不同可用区
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchExpressions:
                    - key: app
                      operator: In
                      values:
                        - web-server
                topologyKey: topology.kubernetes.io/zone
      containers:
        - name: web
          image: nginx:1.25
          ports:
            - containerPort: 80
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"
```

#### 4.5 SRE 实战：多副本高可用部署

```yaml
# 生产环境典型的高可用配置
# 确保同一应用的 Pod 分散在不同节点和可用区
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: etcd-cluster
  namespace: kube-system
spec:
  serviceName: etcd
  replicas: 3
  selector:
    matchLabels:
      app: etcd
  template:
    metadata:
      labels:
        app: etcd
    spec:
      affinity:
        podAntiAffinity:
          # 每个节点最多一个 etcd 实例
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchExpressions:
                  - key: app
                    operator: In
                    values:
                      - etcd
              topologyKey: kubernetes.io/hostname
          # 尽量分散到不同可用区
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchExpressions:
                    - key: app
                      operator: In
                      values:
                        - etcd
                topologyKey: topology.kubernetes.io/zone
      containers:
        - name: etcd
          image: registry.k8s.io/etcd:3.5.9-0
          resources:
            requests:
              cpu: "100m"
              memory: "256Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"
```

#### 4.6 常见陷阱

```
陷阱 1：topologyKey 为空
  - 必须指定 topologyKey，否则调度失败

陷阱 2：labelSelector 与 namespaceSelector
  - 默认只在同一 namespace 中查找匹配的 Pod
  - 需要跨 namespace 时必须设置 namespaceSelector

陷阱 3：性能问题
  - podAffinity/podAntiAffinity 的计算复杂度高
  - 集群规模大时可能导致调度延迟
  - 建议：尽量使用 preferred 而非 required

陷阱 4：循环依赖
  - Pod-A 要和 Pod-B 在一起，Pod-B 要和 Pod-A 分开
  - 导致永远无法调度
```

### 5. Taint 与 Toleration — 节点排斥与容忍

#### 5.1 基本概念

```
Taint（污点）：应用于节点，排斥不容忍该污点的 Pod
Toleration（容忍）：应用于 Pod，允许 Pod 被调度到有污点的节点

Taint 效果（Effect）：
┌──────────────────┬────────────────────────────────────────────┐
│ NoSchedule       │ 不允许新 Pod 调度（已运行的不受影响）       │
│ PreferNoSchedule │ 尽量不调度新 Pod（软性排斥）                │
│ NoExecute        │ 不允许新 Pod + 驱逐已运行的不容忍 Pod       │
└──────────────────┴────────────────────────────────────────────┘
```

#### 5.2 Taint 操作

```bash
# 给节点添加污点
kubectl taint nodes node-1 dedicated=gpu:NoSchedule

# 给节点添加多个污点
kubectl taint nodes node-1 dedicated=gpu:NoSchedule env=production:NoExecute

# 查看节点污点
kubectl describe node node-1 | grep -A 5 "Taints:"

# 删除污点（加 - 号后缀）
kubectl taint nodes node-1 dedicated=gpu:NoSchedule-

# 删除所有污点
kubectl taint nodes node-1 dedicated-

# 给 master 节点保留污点（通常默认存在）
kubectl taint nodes master node-role.kubernetes.io/control-plane:NoSchedule
```

#### 5.3 Toleration 配置

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: gpu-workload
spec:
  tolerations:
    # 精确匹配：容忍 dedicated=gpu:NoSchedule
    - key: "dedicated"
      operator: "Equal"
      value: "gpu"
      effect: "NoSchedule"

    # 存在匹配：容忍所有 key=env 的污点（任意值）
    - key: "env"
      operator: "Exists"
      effect: "NoSchedule"

    # 容忍所有 NoExecute 污点（不被驱逐）
    # 注意：慎用，可能导致 Pod 在异常节点上不被驱逐
    # - key: ""
    #   operator: "Exists"
    #   effect: "NoExecute"

  containers:
    - name: gpu-app
      image: nvidia/cuda:12.2.0-base-ubuntu22.04
      resources:
        limits:
          nvidia.com/gpu: "1"
```

#### 5.4 NoExecute 与 TolerationSeconds

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: stateful-app
spec:
  tolerations:
    # 容忍节点 NotReady 污点 300 秒后驱逐
    - key: "node.kubernetes.io/not-ready"
      operator: "Exists"
      effect: "NoExecute"
      tolerationSeconds: 300

    # 容忍节点不可达 600 秒后驱逐
    - key: "node.kubernetes.io/unreachable"
      operator: "Exists"
      effect: "NoExecute"
      tolerationSeconds: 600

  containers:
    - name: app
      image: nginx:1.25
```

#### 5.5 系统内置 Taint

| Taint Key | 含义 | 默认效果 |
|-----------|------|---------|
| node.kubernetes.io/not-ready | 节点未就绪 | NoExecute |
| node.kubernetes.io/unreachable | 节点不可达 | NoExecute |
| node.kubernetes.io/memory-pressure | 内存压力 | NoSchedule |
| node.kubernetes.io/disk-pressure | 磁盘压力 | NoSchedule |
| node.kubernetes.io/pid-pressure | PID 压力 | NoSchedule |
| node.kubernetes.io/network-unavailable | 网络不可用 | NoSchedule |
| node.kubernetes.io/unschedulable | 节点不可调度 | NoSchedule |
| node.cloudprovider.kubernetes.io/uninitialized | 云节点未初始化 | NoSchedule |

### 6. TopologySpreadConstraints — 拓扑分布约束

#### 6.1 基本概念

TopologySpreadConstraints 用于控制 Pod 在集群中的分布方式，确保 Pod 均匀分布在不同的拓扑域中。

```
拓扑分布约束 vs PodAntiAffinity：

PodAntiAffinity：
  - 确保同一拓扑域中不运行特定 Pod
  - 二元决策（是/否）
  - 无法控制"均匀分布"

TopologySpreadConstraints：
  - 确保 Pod 均匀分布在拓扑域中
  - 支持 maxSkew（最大偏差）
  - 支持 whenUnsatisfiable（不满足时的行为）
  - 更细粒度的控制
```

#### 6.2 配置详解

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
  namespace: production
spec:
  replicas: 6
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
        env: production
    spec:
      topologySpreadConstraints:
        # 约束 1：跨节点均匀分布
        - maxSkew: 1  # 最大偏差为 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: DoNotSchedule  # 不满足时不调度
          labelSelector:
            matchLabels:
              app: web-app
          matchLabelKeys:
            - pod-template-hash  # 只计算同一版本的 Pod
          minDomains: 3  # 最少覆盖 3 个域（K8s 1.27+）
          nodeAffinityPolicy: Honor  # 考虑节点亲和性
          nodeTaintsPolicy: Honor  # 考虑节点污点

        # 约束 2：跨可用区均匀分布
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: ScheduleAnyway  # 不满足时尽量调度
          labelSelector:
            matchLabels:
              app: web-app
      containers:
        - name: web
          image: nginx:1.25
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
```

#### 6.3 参数详解

| 参数 | 说明 | 取值 |
|------|------|------|
| maxSkew | 拓扑域之间 Pod 数量的最大差异 | 正整数（≥1） |
| topologyKey | 拓扑域的标签键 | 节点标签键 |
| whenUnsatisfiable | 约束不满足时的行为 | DoNotSchedule / ScheduleAnyway |
| labelSelector | 选择要计算的 Pod 标签 | 标签选择器 |
| matchLabelKeys | 匹配的 Pod 标签键（用于多版本） | 标签键列表 |
| minDomains | 最小拓扑域数量 | 正整数（K8s 1.27+） |
| nodeAffinityPolicy | 是否考虑节点亲和性 | Honor / Ignore |
| nodeTaintsPolicy | 是否考虑节点污点 | Honor / Ignore |

#### 6.4 maxSkew 示例

```
假设 3 个节点，maxSkew=1：

初始状态：
  Node-1: 0 个 Pod
  Node-2: 0 个 Pod
  Node-3: 0 个 Pod

Pod-1 调度到 Node-1：
  Node-1: 1 个 Pod  (max: 1, min: 0, skew: 1 ✓)

Pod-2 调度到 Node-2：
  Node-1: 1 个 Pod  (max: 1, min: 0, skew: 1 ✓)
  Node-2: 1 个 Pod

Pod-3 调度到 Node-3：
  Node-1: 1 个 Pod
  Node-2: 1 个 Pod
  Node-3: 1 个 Pod  (max: 1, min: 1, skew: 0 ✓)

Pod-4 可以调到任意节点（因为增加后 skew 仍为 1）：
  Node-1: 2 个 Pod  (max: 2, min: 1, skew: 1 ✓)
  Node-2: 1 个 Pod
  Node-3: 1 个 Pod
```

```yaml

  name: api-server
```

### 7. PriorityClass 与优先级抢占

#### 7.1 基本概念

```
PriorityClass 定义 Pod 的优先级：
  - 高优先级 Pod 可以抢占低优先级 Pod
  - 用于确保关键系统组件始终有资源

抢占流程：
  1. 高优先级 Pod 调度失败
  2. 调度器寻找可被抢占的低优先级 Pod
  3. 驱逐低优先级 Pod
  4. 调度高优先级 Pod
```

#### 7.2 系统内置 PriorityClass

```bash
# 查看系统内置的 PriorityClass
kubectl get priorityclasses

# 输出示例：
# NAME                      VALUE        GLOBAL-DEFAULT   AGE
# system-node-critical      2000000000   false            24d
# system-cluster-critical   1000000000   false            24d
# scheduling.k8s.io/default 0            true             24d
```

#### 7.3 自定义 PriorityClass

```yaml
# 高优先级：关键业务组件
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: critical-service
value: 1000000000
globalDefault: false
preemptionPolicy: PreemptLowerPriority  # 可以抢占低优先级 Pod
description: "Critical business services"

---
# 中优先级：普通业务组件
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: standard-service
value: 500000000
globalDefault: false
preemptionPolicy: PreemptLowerPriority
description: "Standard business services"

---
# 低优先级：批处理任务
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: batch-job
value: 100000
globalDefault: false
preemptionPolicy: Never  # 不抢占其他 Pod
description: "Batch processing jobs"
```

#### 7.4 使用 PriorityClass

```yaml
# 关键业务使用高优先级
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service
  namespace: production
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payment
  template:
    metadata:
      labels:
        app: payment
    spec:
      priorityClassName: critical-service
      containers:
        - name: payment
          image: my-registry/payment:v1.2.0
          resources:
            requests:
              cpu: "500m"
              memory: "512Mi"
            limits:
              cpu: "1"
              memory: "1Gi"

---
# 批处理任务使用低优先级
apiVersion: batch/v1
kind: Job
metadata:
  name: data-export
spec:
  template:
    spec:
      priorityClassName: batch-job
      restartPolicy: Never
      containers:
        - name: export
          image: my-registry/exporter:v1.0
          command: ["python", "export.py"]
```

#### 7.5 抢占机制详解

```
抢占决策流程：

Pod-X (Priority: 1000000000) 调度失败
    │
    ├── 1. 检查是否有可被抢占的低优先级 Pod
    │
    ├── 2. 找到候选被抢占 Pod（Priority < 1000000000）
    │
    ├── 3. 检查抢占后是否能满足 Pod-X 的资源需求
    │
    ├── 4. 检查被抢占 Pod 的 PDB 是否允许
    │
    ├── 5. 选择"最合适"的被抢占对象
    │   - 优先选择优先级最低的 Pod
    │   - 选择最少数量的 Pod 来满足资源需求
    │
    ├── 6. 发送驱逐信号给被抢占 Pod
    │
    └── 7. 调度 Pod-X

注意事项：
  - 抢占不保证成功（可能被 PDB 阻止）
  - 抢占有延迟（等待 Pod 终止）
  - preemptionPolicy: Never 表示该优先级 Pod 不会抢占其他 Pod
  - Pod 可能被更高优先级的 Pod 抢占
```

#### 7.6 SRE 实战：生产环境优先级策略

```yaml

# 层级 1：系统关键组件 (value: 2000000000)

#   - 不需要手动设置，系统已内置
```

```bash
kubectl label nodes node-1 disktype=ssd zone=us-east-1a env=production

# 步骤 2：验证标签
kubectl get nodes --show-labels | grep -E "disktype|zone|env"
```

创建一个 Deployment，要求：
- 必须调度到 SSD 磁盘的节点
- 优先调度到 production 环境的节点
- 使用 nodeAffinity 实现

```yaml

  name: affinity-test
spec:
  replicas: 3
  selector:
    matchLabels:
      app: affinity-test
  template:
    metadata:
      labels:
        app: affinity-test
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: disktype
                    operator: In
                    values:
                      - ssd
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 80
              preference:
                matchExpressions:
                  - key: env
                    operator: In
                    values:
                      - production
      containers:
        - name: app
          image: nginx:1.25
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
```

## 🎯 面试题精选

### 1. kube-scheduler 的调度流程是什么？

**答**：调度流程分为三个阶段：
1. **过滤（Filtering）**：排除不满足条件的节点（资源不足、标签不匹配、污点不容忍等）
2. **打分（Scoring）**：对通过过滤的节点进行评分，考虑资源均衡、镜像本地性、亲和性等因素
3. **绑定（Binding）**：选择得分最高的节点，通过 API Server 将 Pod 绑定到该节点

### 2. nodeAffinity 的 required 和 preferred 有什么区别？

**答**：
- `requiredDuringSchedulingIgnoredDuringExecution`：硬性约束，不满足条件的节点会被排除，Pod 不会调度到这些节点上
- `preferredDuringSchedulingIgnoredDuringExecution`：软性偏好，通过 weight（1-100）设置偏好权重，不满足也会调度到其他节点
- `IgnoredDuringExecution` 表示节点标签变更后，已运行的 Pod 不会被驱逐

### 3. Taint 的三种 Effect 有什么区别？

**答**：
- `NoSchedule`：不允许新 Pod 调度到该节点，已运行的 Pod 不受影响
- `PreferNoSchedule`：尽量不调度新 Pod，但不强制（软性排斥）
- `NoExecute`：不允许新 Pod 调度 + 驱逐已运行的不容忍 Pod

### 4. podAntiAffinity 的 required 和 TopologySpreadConstraints 的区别？

**答**：
- podAntiAffinity 是二元决策（是/否），只决定是否允许，不控制"均匀分布"
- TopologySpreadConstraints 支持 maxSkew（最大偏差），可以控制 Pod 在拓扑域间的均匀分布程度
- TopologySpreadConstraints 还支持 whenUnsatisfiable（DoNotSchedule / ScheduleAnyway），更灵活
- 生产环境建议使用 TopologySpreadConstraints 实现跨可用区高可用分布

### 5. 什么是 PriorityClass 的 preemptionPolicy？

**答**：
- `PreemptLowerPriority`（默认）：当高优先级 Pod 调度失败时，可以抢占低优先级 Pod 的资源
- `Never`：该优先级的 Pod 不会抢占其他 Pod，但仍然可以被更高优先级的 Pod 抢占
- 适用于批处理任务等不需要抢占资源的场景

### 6. 如何为 GPU 节点配置专用调度策略？

**答**：
1. 给 GPU 节点打标签：`kubectl label nodes gpu-node hardware=gpu`
2. 给 GPU 节点添加污点：`kubectl taint nodes gpu-node dedicated=gpu:NoSchedule`
3. GPU 工作负载配置 nodeSelector 和 toleration
4. 这样非 GPU 工作负载不会被调度到 GPU 节点

### 7. TopologySpreadConstraints 的 maxSkew 参数是什么含义？

**答**：maxSkew 表示拓扑域之间 Pod 数量的最大差异。例如 maxSkew=1 表示任何两个拓扑域之间的 Pod 数量差不能超过 1。值越大，分布越不均匀；值为 1 时，分布最均匀。

### 8. 如何查看 Pod 的调度失败原因？

**答**：
```bash
kubectl describe pod <pod-name> | grep -A 20 "Events:"
```
常见失败原因：Insufficient cpu/memory、node(s) had taint、node(s) didn't match node selector/affinity、FailedScheduling。

### 9. nodeAffinity 中的 nodeSelectorTerms 和 matchExpressions 的关系？

**答**：
- 多个 nodeSelectorTerms 之间是 OR 关系（满足任一即可）
- 同一 nodeSelectorTerms 内的多个 matchExpressions 是 AND 关系（必须全部满足）
- 这与 Pod 的 nodeSelector 的 AND 关系不同，nodeSelector 只支持 AND

### 10. 如何实现 Pod 在三个可用区的均匀分布？

**答**：使用 TopologySpreadConstraints 配置跨 zone 的分布约束：
```yaml
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: my-app
```
配合 podAntiAffinity 确保同一节点不运行多个副本。
