#### 1.1 为什么需要多副本

```
┌──────────────────────────────────────────────────────────────────┐
│                    单副本 vs 多副本对比                            │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  单副本（单点故障）:                                              │
│  ┌──────────┐                                                    │

│       │                                                          │

│  └──────────┘                                                    │
│                                                                  │
│  多副本（高可用）:                                                │
│  ┌──────────┐                                                    │
│  │  Client  │                                                    │
│  └────┬─────┘                                                    │
│       │                                                          │
│       ▼                                                          │
│  ┌──────────────────────────────────────────┐                   │
│  │         Load Balancer (Service)           │                   │
│  └────┬────────────┬────────────┬───────────┘                   │
│       │            │            │                                 │
│       ▼            ▼            ▼                                 │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐                            │
│  │ Pod 1   │ │ Pod 2   │ │ Pod 3   │                            │
│  │ Node A  │ │ Node B  │ │ Node C  │                            │
│  │ GPU 0,1 │ │ GPU 0,1 │ │ GPU 0,1 │                            │
│  └─────────┘ └─────────┘ └─────────┘                            │
│                                                                  │
│  优势:                                                           │
│  ├── 单节点故障不影响服务（Pod 自动调度到其他节点）              │
│  ├── 滚动更新零停机                                             │
│  ├── 水平扩展提升吞吐                                           │
│  └── 请求分散降低单节点压力                                     │
```

### 2. 推理端点负载均衡

#### 2.1 负载均衡策略对比

```
┌──────────────────────────────────────────────────────────────────┐
│                    推理端点负载均衡策略                            │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  策略 1: Round-Robin（轮询）                                     │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │  请求 1 → Pod 1                                            │ │
│  │  请求 2 → Pod 2                                            │ │
│  │  请求 3 → Pod 3                                            │ │
│  │  请求 4 → Pod 1                                            │ │
│  │  ...                                                       │ │
│  │                                                            │ │
│  │  优点: 实现简单，均匀分配                                   │ │
│  │  缺点: 不考虑 GPU 负载，可能导致某些 Pod 过载              │ │
│  │  适用: 请求特征均匀、GPU 利用率差异小的场景                │ │
│  └────────────────────────────────────────────────────────────┘ │
│                                                                  │
│  策略 2: Least-Connections（最少连接）                           │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │  请求 → 当前活跃连接最少的 Pod                              │ │
│  │                                                            │ │
│  │  Pod 1: 5 个活跃请求                                       │ │
│  │  Pod 2: 2 个活跃请求 ← 新请求分配到这里                    │ │
│  │  Pod 3: 8 个活跃请求                                       │ │
│  │                                                            │ │
│  │  优点: 考虑实际负载                                        │ │
│  │  缺点: 长连接场景下效果差                                  │ │
│  │  适用: 请求时长差异大的场景                                │ │
│  └────────────────────────────────────────────────────────────┘ │
│                                                                  │
│  策略 3: GPU-Aware（GPU 感知）                                   │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │  请求 → GPU 利用率最低 / 排队最少的 Pod                     │ │
│  │                                                            │ │
│  │  Pod 1: GPU 95%, 队列 30 ← 不选择                         │ │
│  │  Pod 2: GPU 60%, 队列 5  ← 新请求分配到这里               │ │
│  │  Pod 3: GPU 80%, 队列 15                                  │ │
│  │                                                            │ │
│  │  优点: 最优性能，避免 GPU 过载                             │ │
│  │  缺点: 需要额外指标采集和决策逻辑                          │ │
│  │  适用: 生产环境推荐                                        │ │
│  └────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────┘
```

#### 2.2 负载均衡策略对比表

| 策略 | 实现复杂度 | GPU 感知 | 长请求友好 | 推荐场景 |
|------|-----------|---------|-----------|---------|
| Round-Robin | 低 | 否 | 一般 | 测试环境 |
| Least-Connections | 中 | 否 | 好 | 通用场景 |
| Least-Requests (vLLM) | 中 | 是 | 好 | vLLM 推荐 |
| GPU Utilization Based | 高 | 是 | 好 | 生产环境 |
| Queue Depth Based | 高 | 是 | 好 | 高并发场景 |
| Latency Based | 高 | 是 | 好 | 低延迟要求 |

#### 2.4 GPU 感知负载均衡（Python 实现）

```python
"""
gpu_aware_load_balancer.py
GPU 感知负载均衡器：根据 GPU 利用率和队列深度分配请求
"""

import asyncio
import time
import httpx
from dataclasses import dataclass
from typing import Optional

@dataclass
class BackendMetrics:
    """后端实例指标"""
    endpoint: str
    gpu_utilization: float = 0.0       # GPU 利用率 (0-100)
    queue_depth: int = 0                # 排队请求数
    active_requests: int = 0            # 活跃请求数
    avg_latency_ms: float = 0.0         # 平均延迟
    last_updated: float = 0.0           # 最后更新时间
    is_healthy: bool = True             # 健康状态

class GPUAwareLoadBalancer:
    """GPU 感知负载均衡器"""

    def __init__(self, backends: list[str], metrics_interval: float = 5.0):
        self.backends = {ep: BackendMetrics(endpoint=ep) for ep in backends}
        self.metrics_interval = metrics_interval
        self.client = httpx.AsyncClient(timeout=30.0)

    async def fetch_metrics(self, endpoint: str) -> Optional[BackendMetrics]:
        """从后端实例获取指标"""
        try:
            # 获取 vLLM 指标
            resp = await self.client.get(f"http://{endpoint}/metrics")
            if resp.status_code == 200:
                metrics = self._parse_vllm_metrics(resp.text)
                backend = self.backends[endpoint]
                backend.gpu_utilization = metrics.get("gpu_util", 0.0)
                backend.queue_depth = int(metrics.get("queue_depth", 0))
                backend.active_requests = int(metrics.get("active_requests", 0))
                backend.avg_latency_ms = metrics.get("avg_latency", 0.0)
                backend.last_updated = time.time()
                backend.is_healthy = True
                return backend
        except Exception:
            self.backends[endpoint].is_healthy = False
        return None

    def _parse_vllm_metrics(self, text: str) -> dict:
        """解析 vLLM Prometheus 指标"""
        result = {}
        for line in text.split("\n"):
            if line.startswith("#"):
                continue
            if "num_requests_waiting" in line:
                result["queue_depth"] = float(line.split()[-1])
            elif "num_requests_running" in line:
                result["active_requests"] = float(line.split()[-1])
            elif "gpu_cache_usage_perc" in line:
                result["gpu_util"] = float(line.split()[-1]) * 100
        return result

    def select_backend(self) -> Optional[str]:
        """选择最优后端实例（综合评分）"""
        healthy_backends = [
            b for b in self.backends.values()
            if b.is_healthy and (time.time() - b.last_updated) < 30
        ]

        if not healthy_backends:
            return None

        # 综合评分：GPU 利用率权重 0.4，队列深度权重 0.4，延迟权重 0.2
        def score(backend: BackendMetrics) -> float:
            gpu_score = 100 - backend.gpu_utilization     # 越低越好
            queue_score = max(0, 100 - backend.queue_depth * 2)  # 越低越好
            latency_score = max(0, 100 - backend.avg_latency_ms / 10)
            return gpu_score * 0.4 + queue_score * 0.4 + latency_score * 0.2

        best = max(healthy_backends, key=score)
        return best.endpoint

    async def forward_request(self, request_data: dict) -> dict:
        """转发请求到最优后端"""
        backend = self.select_backend()
        if not backend:
            raise RuntimeError("没有可用的后端实例")

        resp = await self.client.post(
            f"http://{backend}/v1/chat/completions",
            json=request_data,
            timeout=300.0
        )
        return resp.json()

    async def metrics_collector_loop(self):
        """后台指标采集循环"""
        while True:
            tasks = [
                self.fetch_metrics(ep)
                for ep in self.backends
            ]
            await asyncio.gather(*tasks, return_exceptions=True)
            await asyncio.sleep(self.metrics_interval)
```

#### 3.3 GPU 监控 Python 脚本

```python
"""
gpu_monitor.py
GPU 利用率实时监控与告警
"""

import subprocess
import json
import time
from dataclasses import dataclass
from typing import list

@dataclass
class GPUInfo:
    index: int
    name: str
    temperature: int
    memory_used: int
    memory_total: int
    utilization: int
    ecc_uncorrected: int

def get_gpu_info() -> list[GPUInfo]:
    """通过 nvidia-smi 获取 GPU 信息"""
    cmd = [
        "nvidia-smi",
        "--query-gpu=index,name,temperature.gpu,memory.used,memory.total,"
        "utilization.gpu,ecc.errors.uncorrected.aggregate.total",
        "--format=csv,noheader,nounits"
    ]
    result = subprocess.run(cmd, capture_output=True, text=True)
    gpus = []
    for line in result.stdout.strip().split("\n"):
        parts = [p.strip() for p in line.split(",")]
        gpus.append(GPUInfo(
            index=int(parts[0]),
            name=parts[1],
            temperature=int(parts[2]),
            memory_used=int(parts[3]),
            memory_total=int(parts[4]),
            utilization=int(parts[5]),
            ecc_uncorrected=int(parts[6])
        ))
    return gpus

def check_gpu_health(gpus: list[GPUInfo]) -> list[dict]:
    """检查 GPU 健康状态，返回告警列表"""
    alerts = []
    for gpu in gpus:
        mem_pct = gpu.memory_used / gpu.memory_total * 100

        if gpu.utilization > 95:
            alerts.append({
                "severity": "warning",
                "gpu": gpu.index,
                "message": f"GPU {gpu.index} 利用率过高: {gpu.utilization}%"
            })

        if mem_pct > 95:
            alerts.append({
                "severity": "critical",
                "gpu": gpu.index,
                "message": f"GPU {gpu.index} 显存接近 OOM: {mem_pct:.1f}%"
            })

        if gpu.temperature > 85:
            alerts.append({
                "severity": "warning",
                "gpu": gpu.index,
                "message": f"GPU {gpu.index} 温度过高: {gpu.temperature}C"
            })

        if gpu.ecc_uncorrected > 0:
            alerts.append({
                "severity": "critical",
                "gpu": gpu.index,
                "message": f"GPU {gpu.index} 存在不可修复 ECC 错误: {gpu.ecc_uncorrected}"
            })

    return alerts

def monitor_loop(interval: int = 10):
    """持续监控循环"""
    print("GPU 监控启动...")
    while True:
        try:
            gpus = get_gpu_info()
            alerts = check_gpu_health(gpus)

            for gpu in gpus:
                mem_pct = gpu.memory_used / gpu.memory_total * 100
                print(f"[GPU {gpu.index}] 利用率: {gpu.utilization}% | "
                      f"显存: {mem_pct:.1f}% | 温度: {gpu.temperature}C")

            for alert in alerts:
                print(f"[{alert['severity'].upper()}] {alert['message']}")

        except Exception as e:
            print(f"监控异常: {e}")

        time.sleep(interval)

if __name__ == "__main__":
    monitor_loop()
```

#### 6.2 自定义健康检查实现

```python
"""
model_health_check.py
推理服务健康检查端点实现
"""

from fastapi import FastAPI, Response
from enum import Enum
import subprocess
import httpx

app = FastAPI()

class HealthStatus(str, Enum):
    HEALTHY = "healthy"
    DEGRADED = "degraded"
    UNHEALTHY = "unhealthy"

def check_gpu_health() -> dict:
    """检查 GPU 健康状态"""
    try:
        result = subprocess.run(
            ["nvidia-smi", "--query-gpu=temperature.gpu,ecc.errors.uncorrected.aggregate.total",
             "--format=csv,noheader,nounits"],
            capture_output=True, text=True, timeout=10
        )
        lines = result.stdout.strip().split("\n")
        for line in lines:
            temp, ecc = [x.strip() for x in line.split(",")]
            if int(temp) > 90:
                return {"status": "unhealthy", "reason": f"GPU 温度过高: {temp}C"}
            if int(ecc) > 0:
                return {"status": "unhealthy", "reason": f"GPU ECC 错误: {ecc}"}
        return {"status": "ok"}
    except Exception as e:
        return {"status": "unhealthy", "reason": str(e)}

def check_model_ready() -> dict:
    """检查模型是否就绪"""
    try:
        result = subprocess.run(
            ["curl", "-s", "http://localhost:8000/v1/models"],
            capture_output=True, text=True, timeout=10
        )
        if result.returncode == 0 and "model" in result.stdout:
            return {"status": "ok"}
        return {"status": "unhealthy", "reason": "模型未就绪"}
    except Exception as e:
        return {"status": "unhealthy", "reason": str(e)}

@app.get("/health")
async def health_check(response: Response):
    """综合健康检查端点"""
    gpu_health = check_gpu_health()
    model_ready = check_model_ready()

    is_healthy = (
        gpu_health["status"] != "unhealthy"
        and model_ready["status"] != "unhealthy"
    )

    status = HealthStatus.HEALTHY if is_healthy else HealthStatus.UNHEALTHY

    if not is_healthy:
        response.status_code = 503

    return {
        "status": status,
        "gpu": gpu_health,
        "model": model_ready,
    }
```

#### 6.3 熔断器模式

```python
"""
circuit_breaker.py
推理服务熔断器：当下游服务故障时快速失败
"""

import time
from enum import Enum
from dataclasses import dataclass, field

class CircuitState(str, Enum):
    CLOSED = "closed"       # 正常状态，允许请求
    OPEN = "open"           # 熔断状态，拒绝请求
    HALF_OPEN = "half_open" # 半开状态，试探恢复

@dataclass
class CircuitBreaker:
    """熔断器实现"""
    failure_threshold: int = 5          # 失败次数阈值
    recovery_timeout: float = 60.0      # 恢复超时（秒）
    half_open_max_calls: int = 3        # 半开状态最大尝试次数

    state: CircuitState = CircuitState.CLOSED
    failure_count: int = 0
    last_failure_time: float = 0.0
    half_open_calls: int = 0
    half_open_successes: int = 0

    def can_execute(self) -> bool:
        """判断是否允许执行请求"""
        if self.state == CircuitState.CLOSED:
            return True

        if self.state == CircuitState.OPEN:
            if time.time() - self.last_failure_time > self.recovery_timeout:
                self.state = CircuitState.HALF_OPEN
                self.half_open_calls = 0
                self.half_open_successes = 0
                return True
            return False

        if self.state == CircuitState.HALF_OPEN:
            return self.half_open_calls < self.half_open_max_calls

        return False

    def record_success(self):
        """记录成功"""
        if self.state == CircuitState.HALF_OPEN:
            self.half_open_successes += 1
            if self.half_open_successes >= self.half_open_max_calls:
                self.state = CircuitState.CLOSED
                self.failure_count = 0
        elif self.state == CircuitState.CLOSED:
            self.failure_count = max(0, self.failure_count - 1)

    def record_failure(self):
        """记录失败"""
        self.failure_count += 1
        self.last_failure_time = time.time()

        if self.state == CircuitState.HALF_OPEN:
            self.state = CircuitState.OPEN
        elif self.failure_count >= self.failure_threshold:
            self.state = CircuitState.OPEN

    def get_state_info(self) -> dict:
        """获取熔断器状态信息"""
        return {
            "state": self.state.value,
            "failure_count": self.failure_count,
            "failure_threshold": self.failure_threshold,
            "last_failure_time": self.last_failure_time,
            "recovery_timeout": self.recovery_timeout,
        }
```

### 练习 3: 故障转移演练

**目标**: 模拟节点故障，验证服务自动恢复能力。

```bash
#!/bin/bash
# failover_drill.sh - 故障转移演练

echo "=== 故障转移演练 ==="

# 1. 确认初始状态
echo "--- 初始状态 ---"
kubectl get pods -n llm-inference -l app=vllm -o wide
echo ""

# 2. 记录当前 Pod 所在节点
TARGET_POD=$(kubectl get pods -n llm-inference -l app=vllm -o jsonpath='{.items[0].metadata.name}')
TARGET_NODE=$(kubectl get pod $TARGET_POD -n llm-inference -o jsonpath='{.spec.nodeName}')
echo "目标 Pod: $TARGET_POD (节点: $TARGET_NODE)"

# 3. 验证服务可用
echo "--- 测试请求 ---"
for i in $(seq 1 5); do
  STATUS=$(curl -s -o /dev/null -w "%{http_code}" \
    http://vllm-qwen-72b:8000/v1/models)
  echo "请求 $i: HTTP $STATUS"
done
echo ""

# 4. 模拟节点故障（cordon + drain）
echo "--- 模拟节点故障 ($TARGET_NODE) ---"
kubectl cordon $TARGET_NODE
kubectl delete pod $TARGET_POD -n llm-inference --grace-period=0 --force

# 5. 观察服务中断情况
echo "--- 监控服务状态 ---"
for i in $(seq 1 30); do
  STATUS=$(curl -s -o /dev/null -w "%{http_code}" --max-time 5 \
    http://vllm-qwen-72b:8000/v1/models 2>/dev/null || echo "timeout")
  echo "$(date +%H:%M:%S) 请求: $STATUS"
  sleep 10
done

# 6. 等待新 Pod 启动
echo "--- 等待新 Pod 启动 ---"
kubectl wait --for=condition=ready pod -l app=vllm,model=qwen-72b \
  -n llm-inference --timeout=600s

# 7. 恢复节点
echo "--- 恢复节点 ---"
kubectl uncordon $TARGET_NODE

# 8. 验证恢复
echo "--- 恢复后状态 ---"
kubectl get pods -n llm-inference -l app=vllm -o wide
for i in $(seq 1 5); do
  STATUS=$(curl -s -o /dev/null -w "%{http_code}" \
    http://vllm-qwen-72b:8000/v1/models)
  echo "请求 $i: HTTP $STATUS"
done

echo ""
echo "=== 演练完成 ==="
```

## 面试题精选

### 1. 如何设计一个高可用的模型推理服务？

**参考答案**：

高可用模型推理服务需要从以下维度设计：

1. **多副本部署**：至少 2 个副本，使用 `podAntiAffinity` 确保分散到不同节点，`topologySpreadConstraints` 跨可用区分布
2. **负载均衡**：使用 Service + Ingress/Nginx 实现流量分发，推荐 Least-Connections 或 GPU-Aware 策略
3. **健康检查**：三层探针 — Startup Probe（模型加载）、Readiness Probe（就绪状态）、Liveness Probe（存活状态）
4. **自动扩缩容**：KEDA/HPA 基于 GPU 利用率、队列深度、延迟等指标自动调整副本数
5. **优雅关闭**：`preStop` hook + `terminationGracePeriodSeconds` 确保请求完成
6. **故障转移**：K8s 自动重调度 + 反亲和性确保新 Pod 到健康节点
7. **滚动更新**：`maxUnavailable: 0` 确保零停机

### 2. 为什么 LLM 推理服务需要 GPU-Aware 负载均衡？

**参考答案**：

传统负载均衡（Round-Robin/Least-Connections）不感知 GPU 状态，可能导致：
- 某些 Pod 的 GPU 已满载，新请求被分配过去导致排队
- 长上下文请求集中在某些 Pod，造成不均匀负载
- GPU 温度过高的 Pod 继续接收请求导致降频

GPU-Aware 负载均衡通过采集 GPU 利用率、队列深度、温度等指标，将请求分配到负载最低的实例，提升整体吞吐和响应速度。

### 3. K8s 的 Startup Probe、Readiness Probe 和 Liveness Probe 在 LLM 服务中分别起什么作用？

**参考答案**：

| 探针 | 作用 | LLM 服务特点 |
|------|------|-------------|
| Startup Probe | 确认启动完成 | 模型加载需 5-15 分钟，需要大 `failureThreshold` |
| Readiness Probe | 确认可接受请求 | GPU 健康、队列未满时才就绪 |
| Liveness Probe | 确认进程存活 | 检测死锁、OOM 等 |

关键区别：
- Startup Probe 通过前，其他两个探针不会执行
- Readiness Probe 失败 → 从 Endpoint 移除（不重启）
- Liveness Probe 失败 → 重启 Pod

### 4. 如何实现推理服务的蓝绿部署和金丝雀部署？

**参考答案**：

**蓝绿部署**：
- 部署新版本（Green）到独立的 Deployment
- 通过修改 Service selector 切换流量（100% 切换）
- 快速回滚：切回旧版本 selector
- 缺点：需要双倍 GPU 资源

**金丝雀部署**：
- 使用 Istio VirtualService 配置 `weight` 分割流量
- 阶段性推进：5% → 20% → 50% → 100%
- 监控新版本的 TTFT、TPS、错误率
- 异常时立即回滚流量权重

### 5. 解释推理服务的熔断器模式，什么时候需要使用？

**参考答案**：

熔断器（Circuit Breaker）在以下场景使用：
- 下游推理服务故障时，快速失败而非等待超时
- 防止级联故障（一个 Pod 故障导致所有请求堆积）
- 保护 GPU 资源（避免向故障 Pod 发送请求浪费资源）

三种状态：
- **CLOSED（正常）**：请求正常转发
- **OPEN（熔断）**：请求直接返回错误，不再转发
- **HALF_OPEN（半开）**：定期试探性发送请求，成功则恢复

### 6. HPA 和 KEDA 在模型服务扩缩容中有什么区别？

**参考答案**：

| 对比项 | HPA | KEDA |
|--------|-----|------|
| 指标来源 | K8s Metrics API | 多种（Prometheus、队列、Cron 等） |
| 配置方式 | K8s 原生 | CRD (ScaledObject) |
| 定时扩缩 | 不支持 | 支持 Cron 触发器 |
| 缩容到 0 | 不支持 | 支持 |
| 复杂度 | 低 | 中 |
| 推荐场景 | 简单扩缩容 | 生产环境推荐 |

KEDA 优势：支持 Prometheus 指标直接查询、Cron 定时扩缩、多触发器组合。

### 7. 如何在不中断服务的情况下对模型进行版本升级？

**参考答案**：

1. **滚动更新**：`maxUnavailable: 0, maxSurge: 1`，新 Pod 就绪后才替换旧 Pod
2. **蓝绿部署**：部署新版本 Deployment，切换 Service selector
3. **金丝雀部署**：Istio 流量分割，逐步将流量切到新版本
4. **关键配置**：
   - `terminationGracePeriodSeconds: 120` 等待长请求完成
   - `preStop: sleep 30` 确保从 Endpoint 移除后再关闭
   - Readiness Probe 确保新版本就绪后才接收流量

### 8. 描述一次完整的推理服务故障排查过程。

**参考答案**：

场景：用户反馈 API 响应变慢。

1. **确认范围**：检查 Grafana Dashboard，确认 TTFT P95 升高、队列深度增加
2. **检查 Pod**：`kubectl get pods` 确认所有 Pod Running，`kubectl top pod` 检查资源
3. **检查 GPU**：`nvidia-smi` 确认利用率、温度、ECC
4. **检查端点**：`kubectl get endpoints` 确认 Service 后端数量
5. **检查日志**：`kubectl logs` 查看 vLLM 日志中的错误
6. **检查网络**：`kubectl exec -- curl localhost:8000/health` 本地连通性
7. **根因定位**：某节点 GPU 温度过高导致降频 → 隔离节点 → 新 Pod 调度到其他节点
