#### 题目 1：什么是 SRE？SRE 和传统运维有什么区别？

**难度**：⭐⭐⭐

**详细解析**：

```
SRE（Site Reliability Engineering）站点可靠性工程，由 Google 提出。

SRE 的核心理念：
1. 用软件工程的方法解决运维问题
2. 用自动化替代手动操作
3. 接受"适度的不可靠"（错误预算）
4. 持续改进系统可靠性

SRE vs 传统运维：

+------------------+-------------------+-------------------+
| 维度              | 传统运维           | SRE               |
+------------------+-------------------+-------------------+
| 工作方式          | 手动操作           | 自动化优先         |
| 故障处理          | 救火式响应         | 系统性根因分析     |
| 可靠性目标        | "越多 9 越好"      | SLO + 错误预算     |
| 与开发的关系      | 独立团队           | 深度协作           |
| 变更管理          | 害怕变更           | 拥抱变更           |
| 监控方式          | 告警驱动           | 可观测性驱动       |
| 技能要求          | 运维技能           | 编程 + 运维        |
+------------------+-------------------+-------------------+

SRE 的核心实践：
1. SLI/SLO/SLA 体系
2. 错误预算管理
3. 自动化运维（Toil 消除）
4. On-Call 值班制度
5. 事后复盘（Postmortem）
6. 容量规划
7. 变更管理
8. 混沌工程

SRE 的"50% 规则"：
Google SRE 团队要求工程师至少 50% 的时间用于工程工作（编码），
而非手动运维。如果运维工作超过 50%，需要招聘更多 SRE 或改进自动化。
```

#### 题目 2：解释 SLI、SLO 和 SLA 的关系

**难度**：⭐⭐⭐⭐

**详细解析**：

```
SLI（Service Level Indicator）服务级别指标：
- 衡量服务质量的具体指标
- 必须是可度量的、可量化的
- 常见 SLI：
  - 可用性：成功请求的比例
  - 延迟：请求响应时间（P50/P95/P99）
  - 吞吐量：每秒请求数
  - 错误率：失败请求的比例
  - 持久性：数据不丢失的概率

SLO（Service Level Objective）服务级别目标：
- SLI 的目标值
- 内部承诺，用于指导工程决策
- 示例：
  - 可用性 SLO：99.95%（月度）
  - 延迟 SLO：P99 < 200ms
  - 错误率 SLO：< 0.1%

SLA（Service Level Agreement）服务级别协议：
- 对外的合同承诺
- 包含违约赔偿条款
- 通常比 SLO 更宽松（留有余量）
- 示例：SLA 承诺 99.9%，内部 SLO 目标 99.95%

三者关系：
SLI（指标） -> SLO（目标） -> SLA（合同）

+--------+     +--------+     +--------+
|  SLI   | --> |  SLO   | --> |  SLA   |
| 可度量  |     | 内部目标 |     | 外部承诺|
+--------+     +--------+     +--------+
  P99 延迟      P99 < 200ms    P99 < 500ms
  可用性        99.95%         99.9%
  错误率        < 0.1%         < 1%

错误预算（Error Budget）：
错误预算 = 1 - SLO
例如：SLO = 99.95%，错误预算 = 0.05%

月度错误预算：
0.05% * 30天 * 24小时 * 60分钟 = 21.6 分钟

错误预算的用途：
- 预算充足：可以发布新功能、做变更
- 预算紧张：冻结变更，专注稳定性
- 预算耗尽：停止所有非关键变更
```

#### 题目 3：什么是 Toil？如何消除 Toil？

**难度**：⭐⭐⭐

**详细解析**：

```
Toil 是 Google SRE 定义的"手动、重复、可自动化、没有持久价值的工作"。

Toil 的特征：
1. 手动的：需要人工干预
2. 重复的：频繁执行相同操作
3. 可自动化的：可以用脚本或工具替代
4. 没有持久价值：完成后不会改善系统
5. O(n) 增长：随着服务规模增长而增长

常见的 Toil：
- 手动扩容缩容
- 手动重启服务
- 手动执行数据库迁移
- 手动更新 SSL 证书
- 手动清理日志
- 手动处理告警
- 手动部署应用

消除 Toil 的方法：

1. 自动化
   # 手动扩容 -> HPA 自动伸缩
   # 手动部署 -> CI/CD Pipeline
   # 手动清理 -> CronJob

2. 平台化
   # 将操作封装为自助平台
   # 开发者自助完成部署、配置等操作

3. 工具化
   # 编写工具脚本替代手动操作
   # 使用现有工具（Ansible、Terraform）

4. 流程优化
   # 简化审批流程
   # 消除不必要的步骤

量化 Toil：
- 记录每周在 Toil 上花费的时间
- 计算 Toil 占总工作时间的比例
- 目标：Toil < 50%（Google 标准）

Toil 消除优先级：
1. 高频 + 高耗时 -> 最高优先级
2. 高频 + 低耗时 -> 次优先级
3. 低频 + 高耗时 -> 再次
4. 低频 + 低耗时 -> 最后
```

#### 题目 4：请描述一个完整的事故响应流程

**难度**：⭐⭐⭐⭐

**详细解析**：

```
事故响应流程（Incident Response）：

Phase 1：检测（Detection）
- 监控系统自动告警
- 用户报告问题
- On-Call 工程师收到通知

Phase 2：响应（Response）
1. 确认事故：验证告警是否真实
2. 评估影响：影响范围、用户数量、业务损失
3. 定级：P0（全站不可用）、P1（核心功能受损）、P2（非核心功能受损）
4. 通知：通知相关团队和管理层
5. 指定 Incident Commander（IC）

Phase 3：缓解（Mitigation）
- 目标：尽快恢复服务
- 常见手段：
  - 回滚最近的变更
  - 重启服务
  - 扩容
  - 切换到备用系统
  - 降级非核心功能

Phase 4：根因分析（Root Cause Analysis）
- 5 Why 方法
- 时间线重建
- 确定根本原因

Phase 5：事后复盘（Postmortem）
- 无指责文化（Blameless）
- 记录事故时间线
- 分析根本原因
- 制定改进措施（Action Items）
- 跟踪改进措施的执行

Postmortem 模板：
## 事故概要
- 日期：
- 持续时间：
- 影响范围：
- 严重等级：

## 时间线
- HH:MM：发现问题
- HH:MM：开始排查
- HH:MM：定位根因
- HH:MM：实施修复
- HH:MM：服务恢复

## 根本原因
[详细描述根因]

## 影响
[量化影响：受影响用户数、持续时间、业务损失]

## 改进措施
| 措施 | 负责人 | 截止日期 | 状态 |
|------|--------|---------|------|
| xxx  | xxx    | xxx     | TODO |
```

#### 题目 5：什么是混沌工程？如何实施？

**难度**：⭐⭐⭐⭐

**详细解析**：

```
混沌工程（Chaos Engineering）是通过主动注入故障来发现系统弱点的实践。

混沌工程原则：
1. 建立稳态假设（Steady State Hypothesis）
2. 引入真实世界的事件（故障注入）
3. 在生产环境运行实验
4. 自动化持续运行
5. 最小化爆炸半径

实施步骤：

Step 1：定义稳态行为
- 确定关键指标（SLI）
- 建立基线（正常状态）
- 例如：请求成功率 > 99.9%，P99 延迟 < 200ms

Step 2：假设系统能维持稳态
- "即使某个服务实例宕机，系统仍能正常工作"

Step 3：设计实验
- 故障类型：网络延迟、丢包、服务宕机、磁盘满
- 爆炸半径：从小范围开始
- 回滚机制：自动或手动停止实验

Step 4：执行实验
- 在生产环境或预生产环境执行
- 持续监控关键指标
- 准备随时停止实验

Step 5：分析结果
- 系统是否维持了稳态？
- 发现了哪些弱点？
- 制定改进措施

常用工具：
- ChaosBlade（阿里开源）
- Chaos Monkey（Netflix）
- Litmus（Kubernetes 原生）
- Chaos Mesh（PingCAP）
- AWS Fault Injection Simulator

故障注入场景：
1. 网络故障：延迟、丢包、DNS 故障
2. 计算故障：CPU 满载、内存不足
3. 存储故障：磁盘满、IO 延迟
4. 应用故障：进程崩溃、OOM
5. 依赖故障：数据库不可用、第三方服务故障
```

#### 题目 6：如何进行容量规划？

**难度**：⭐⭐⭐⭐

**详细解析**：

```
容量规划（Capacity Planning）是预测和准备系统资源的过程。

容量规划的三个维度：

1. 资源维度
   - CPU：核心数、使用率
   - 内存：总量、使用率
   - 存储：容量、IOPS
   - 网络：带宽、连接数

2. 时间维度
   - 短期（1-3 个月）：应对业务增长
   - 中期（3-12 个月）：年度规划
   - 长期（1-3 年）：架构演进

3. 事件维度
   - 大促活动（双十一、黑五）
   - 新功能上线
   - 用户增长预期

容量规划流程：

Step 1：建立基线
- 收集历史资源使用数据
- 分析资源使用趋势
- 识别峰值和谷值

Step 2：预测需求
# 线性增长预测
未来资源 = 当前资源 * (1 + 增长率)^月数

# 考虑峰值
峰值资源 = 平均资源 * 峰值系数（通常 2-3 倍）

Step 3：制定方案
- 确定资源缓冲（通常 20-30%）
- 规划扩缩容策略
- 评估成本

Step 4：实施和监控
- 执行扩容计划
- 持续监控资源使用
- 定期调整计划

Kubernetes 容量规划：
# 查看集群资源使用
$ kubectl top nodes
$ kubectl top pods -A

# 查看资源请求总量
$ kubectl describe nodes | grep -A 5 "Allocated resources"

# HPA 自动扩容
# VPA 自动调整资源请求
# Cluster Autoscaler 自动扩缩节点

成本优化：
- 合理设置 resource requests
- 使用 Spot/抢占式实例
- 使用自动伸缩
- 清理未使用的资源
- 选择合适的实例类型
```

#### 题目 7：什么是可观测性（Observability）？和监控有什么区别？

**难度**：⭐⭐⭐⭐

**详细解析**：

```
可观测性是通过系统的外部输出来理解系统内部状态的能力。

可观测性三支柱：

1. Metrics（指标）
   - 数值型时间序列数据
   - 工具：Prometheus、Grafana、Datadog
   - 用途：趋势分析、告警、容量规划

2. Logs（日志）
   - 事件记录
   - 工具：ELK、Loki、Splunk
   - 用途：问题排查、审计、安全分析

3. Traces（链路追踪）
   - 请求在分布式系统中的完整路径
   - 工具：Jaeger、Zipkin、OpenTelemetry
   - 用途：性能分析、依赖关系、瓶颈定位

可观测性 vs 监控：

+------------------+-------------------+-------------------+
| 维度              | 监控              | 可观测性           |
+------------------+-------------------+-------------------+
| 关注点            | 已知问题          | 未知问题           |
| 数据类型          | 预定义指标        | 多维度数据         |
| 分析方式          | 阈值告警          | 关联分析           |
| 问题类型          | "什么坏了？"      | "为什么坏了？"     |
+------------------+-------------------+-------------------+

OpenTelemetry：
- 统一的可观测性框架
- 支持 Metrics、Logs、Traces
- 厂商无关的标准化
- 自动化埋点

可观测性最佳实践：
1. 结构化日志（JSON 格式）
2. 统一的 Trace ID（跨服务传递）
3. 丰富的标签/维度
4. 关联三支柱数据
5. 自动化告警和仪表盘
```

#### 题目 8：On-Call 值班制度应该如何设计？

**难度**：⭐⭐⭐

**详细解析**：

```
On-Call 值班制度设计要点：

1. 值班人员要求
   - 至少 2 人同时值班（主 + 备）
   - 值班人员必须熟悉系统架构
   - 值班人员必须有故障处理经验
   - 新人需要跟班培训

2. 值班轮换
   - 每轮值班时间：1 周（推荐）
   - 避免连续值班超过 2 周
   - 值班间隔：至少 2 周
   - 节假日值班需要额外补偿

3. 告警管理
   - 告警分级：
     P0：全站不可用，5 分钟响应
     P1：核心功能受损，15 分钟响应
     P2：非核心功能受损，1 小时响应
     P3：低优先级，24 小时响应
   - 告警必须可操作（Actionable）
   - 消除告警风暴（告警聚合）

4. 升级机制
   - Level 1：On-Call 工程师
   - Level 2：团队 Lead
   - Level 3：技术总监
   - Level 4：CTO/VP Engineering

5. 工具支持
   - 告警派单：PagerDuty、OpsGenie、飞书
   - 通讯工具：Slack、钉钉、飞书
   - Runbook：故障处理手册
   - 仪表盘：Grafana

6. 健康保障
   - 值班后安排调休
   - 避免深夜非关键告警
   - 设置告警静默时间
   - 定期评估告警质量

Runbook 示例：
## 告警：Pod CrashLoopBackOff

### 症状
Pod 反复崩溃重启

### 影响
该服务的请求会失败

### 排查步骤
1. kubectl logs <pod> --previous
2. kubectl describe pod <pod>
3. 检查资源限制是否合理
4. 检查依赖服务是否可用

### 修复步骤
1. 如果是代码 bug -> 回滚
2. 如果是资源不足 -> 扩容
3. 如果是配置错误 -> 修复配置
```

#### 题目 9：什么是错误预算？如何管理错误预算？

**难度**：⭐⭐⭐⭐

**详细解析**：

```
错误预算是 SRE 的核心概念，平衡可靠性和迭代速度。

错误预算计算：
错误预算 = 1 - SLO

示例：
SLO = 99.95%（月度）
错误预算 = 0.05%
月度允许不可用时间 = 30 * 24 * 60 * 0.05% = 21.6 分钟

错误预算管理策略：

1. 预算充足（> 50%）
   - 可以正常发布新功能
   - 可以执行变更
   - 可以做混沌工程实验

2. 预算中等（20-50%）
   - 谨慎发布
   - 增加测试和审查
   - 准备回滚方案

3. 预算紧张（< 20%）
   - 冻结非关键变更
   - 专注稳定性改进
   - 增加监控和告警

4. 预算耗尽（0%）
   - 停止所有变更
   - 全力恢复服务
   - 启动事后复盘

错误预算策略文档（Error Budget Policy）：
# 错误预算策略

## 预算计算
- SLO：99.95%
- 月度预算：21.6 分钟

## 预算状态与行动

| 预算状态 | 剩余比例 | 行动                     |
|---------|---------|-------------------------|
| 健康     | > 50%   | 正常发布和变更            |
| 警告     | 20-50%  | 增加审查，准备回滚方案    |
| 危险     | < 20%   | 冻结非关键变更            |
| 耗尽     | 0%      | 停止所有变更，全力修复    |

## 预算耗尽后的恢复
1. 完成事后复盘
2. 制定并执行改进措施
3. 预算恢复到 50% 后解除冻结

错误预算的常见误区：
- 不是越多 9 越好（99.999% 可能成本过高）
- 不是用来"花"的（不是故意用掉的）
- 是用来指导工程决策的
```

#### 题目 10：什么是事后复盘（Postmortem）？如何写好 Postmortem？

**难度**：⭐⭐⭐

**详细解析**：

```
Postmortem 是事故后的系统性分析和改进过程。

无指责文化（Blameless Culture）：
- 不追究个人责任
- 关注系统和流程的改进
- 鼓励透明和诚实
- 承认"人都会犯错"

Postmortem 触发条件：
- P0/P1 事故
- 影响用户超过一定数量
- 持续时间超过一定阈值
- 重复发生的事故

Postmortem 模板：

# 事故复盘报告

## 事故概要
- 事故名称：[简要描述]
- 日期时间：YYYY-MM-DD HH:MM - HH:MM
- 持续时间：X 分钟/小时
- 影响范围：[受影响的服务/用户]
- 严重等级：P0/P1/P2
- Incident Commander：[姓名]

## 影响评估
- 受影响用户数：X 万
- 请求数：X 万次失败
- 收入影响：约 X 万元
- SLA 影响：可用性从 X% 降至 Y%

## 时间线
| 时间 | 事件 |
|------|------|
| HH:MM | 告警触发：XXX |
| HH:MM | On-Call 工程师确认故障 |
| HH:MM | 开始排查 |
| HH:MM | 定位根因：XXX |
| HH:MM | 执行修复：XXX |
| HH:MM | 服务恢复 |
| HH:MM | 确认恢复 |

## 根本原因
[详细的技术原因分析]

## 5 Why 分析
1. Why：为什么服务不可用？-> 因为数据库连接耗尽
```

#### 题目 22：如何处理数据库主从延迟？

**难度**：⭐⭐⭐⭐

```

1. 从库硬件性能差
2. 从库负载过高
3. 大事务
4. 网络延迟
5. 并行复制未开启

排查方法：
# 查看从库延迟
$ SHOW SLAVE STATUS\G
# 关注 Seconds_Behind_Master

# 查看从库线程状态

1. 开启并行复制
   slave_parallel_type = LOGICAL_CLOCK
   slave_parallel_workers = 8

   - 实时读：主库
   - 非实时读：从库

   gtid_mode = ON
```

#### 题目 23：如何设计一个限流方案？

**难度**：⭐⭐⭐⭐

```
常见限流算法：

1. 固定窗口计数器
   - 简单，但有窗口边界突发问题

2. 滑动窗口计数器
   - 解决窗口边界问题
   - 实现复杂度中等

3. 漏桶算法（Leaky Bucket）
   - 请求以固定速率处理
   - 平滑流量
   - 无法应对突发

4. 令牌桶算法（Token Bucket）
   - 以固定速率生成令牌
   - 请求需要消耗令牌
   - 允许突发流量
   - 最常用

Nginx 限流：
http {
    # 请求限流（漏桶）
    limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;

    # 连接限流
    limit_conn_zone $binary_remote_addr zone=conn:10m;

    server {
        location /api/ {
            # burst=20：允许突发 20 个请求
            # nodelay：不延迟处理突发请求
            limit_req zone=api burst=20 nodelay;
            limit_conn conn 10;
        }
    }
}

分布式限流（Redis）：
# 令牌桶算法 Lua 脚本
local key = KEYS[1]
local rate = tonumber(ARGV[1])     # 令牌生成速率
local capacity = tonumber(ARGV[2]) # 桶容量
local now = tonumber(ARGV[3])      # 当前时间
local requested = tonumber(ARGV[4]) # 请求的令牌数

local fill_time = capacity / rate
local ttl = math.floor(fill_time * 2)

local last_tokens = tonumber(redis.call("get", key) or capacity)
local last_refreshed = tonumber(redis.call("get", key .. ".ts") or now)

local delta = math.max(0, now - last_refreshed)
local filled_tokens = math.min(capacity, last_tokens + (delta * rate))
local allowed = filled_tokens >= requested
local new_tokens = filled_tokens
if allowed then
    new_tokens = filled_tokens - requested
end

redis.call("setex", key, ttl, new_tokens)
redis.call("setex", key .. ".ts", ttl, now)

return allowed and 1 or 0
```

#### 题目 24：如何实现服务的优雅关闭？

**难度**：⭐⭐⭐⭐

```
优雅关闭（Graceful Shutdown）的目标：
1. 停止接受新请求
2. 等待现有请求处理完成
3. 关闭数据库连接
4. 注销服务注册
5. 清理临时资源

实现方案：

1. 捕获 SIGTERM 信号
   # Go
   sigCh := make(chan os.Signal, 1)
   signal.Notify(sigCh, syscall.SIGTERM, syscall.SIGINT)
   <-sigCh

   # Python
   import signal
   def handler(signum, frame):
       # 清理操作
       pass
   signal.signal(signal.SIGTERM, handler)

2. 停止接受新连接
   # 关闭监听 socket
   server.Shutdown(ctx)

3. 等待现有请求完成
   // 设置超时
   ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
   defer cancel()
   server.Shutdown(ctx)

4. 关闭连接池
   db.Close()
   redisClient.Close()

5. 注销服务注册
   consul.Deregister(serviceID)

Kubernetes 中的优雅关闭：
spec:
  terminationGracePeriodSeconds: 60
  containers:
    - name: app
      lifecycle:
        preStop:
          exec:
            command: ["/bin/sh", "-c", "sleep 10"]
            # 等待 Endpoint 更新

注意事项：
- terminationGracePeriodSeconds 应大于应用关闭时间
- preStop hook 用于等待 Endpoint 更新
- 确保 SIGTERM 信号能传递到应用进程
```

#### 题目 25：如何处理分布式系统中的数据一致性问题？

**难度**：⭐⭐⭐⭐⭐

```
CAP 定理：
- C（Consistency）：一致性
- A（Availability）：可用性
- P（Partition Tolerance）：分区容忍
- 三者只能同时满足两个

常见一致性模型：
1. 强一致性：写入后立即可读
2. 最终一致性：写入后最终可读
3. 因果一致性：保证因果关系的一致性

解决方案：

1. 分布式事务（2PC/3PC）
   - 两阶段提交
   - 性能差，阻塞

2. Saga 模式
   - 长事务拆分为多个本地事务
   - 每个事务有补偿操作
   - 最终一致性

3. TCC（Try-Confirm-Cancel）
   - Try：预留资源
   - Confirm：确认提交
   - Cancel：取消释放

4. 事件溯源（Event Sourcing）
   - 记录所有状态变更事件
   - 通过重放事件恢复状态

5. 消息队列最终一致性
   - 本地事务 + 消息表
   - 消费者幂等处理

Saga 模式示例：
创建订单 Saga：
1. 创建订单（Order Service）
2. 扣减库存（Inventory Service）
3. 扣减余额（Payment Service）
4. 确认订单（Order Service）

补偿操作：
4. 取消订单
3. 退还余额
2. 恢复库存
1. 删除订单
```

#### 题目 26：如何设计一个蓝绿部署方案？

**难度**：⭐⭐⭐⭐

```
蓝绿部署（Blue-Green Deployment）：

原理：
- 维护两个完全相同的环境（蓝和绿）
- 一个环境对外提供服务
- 新版本部署到另一个环境
- 测试通过后切换流量
- 快速回滚：切回旧环境

Kubernetes 实现：

# Blue 环境（当前版本）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app-blue
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
      version: blue
  template:
    metadata:
      labels:
        app: my-app
        version: blue
    spec:
      containers:
        - name: app
          image: myapp:v1

---
# Green 环境（新版本）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app-green
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
      version: green
  template:
    metadata:
      labels:
        app: my-app
        version: green
    spec:
      containers:
        - name: app
          image: myapp:v2

---
# Service 切换流量
apiVersion: v1
kind: Service
metadata:
  name: my-app
spec:
  selector:
    app: my-app
    version: blue    # 切换到 green 即可
  ports:
    - port: 80
      targetPort: 8080

切换流程：
1. 部署 green 环境
2. 测试 green 环境
3. 切换 Service selector 到 green
4. 监控新版本
5. 如果有问题，切回 blue
6. 确认无问题后，删除 blue 环境
```

#### 题目 29：如何处理微服务间的依赖故障？

```
依赖故障处理策略：

1. 超时控制
   - 设置合理的超时时间
   - 连接超时 + 读超时

2. 重试机制
   - 指数退避重试
   - 设置最大重试次数
   - 幂等性保证

   - 返回缓存数据
   - 返回默认值
   - 返回友好错误

5. 限流
   - 保护下游服务
   - 防止雪崩

        maxConnections: 100

        h2UpgradePolicy: DEFAULT
        http1MaxPendingRequests: 100
        http2MaxRequests: 1000
```
