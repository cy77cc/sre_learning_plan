### 1. 混沌工程原则

#### 1.1 核心理念

```
┌─────────────────────────────────────────────────────────────────────┐
│                    混沌工程核心原则                                    │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  原则 1: 稳态假设 (Steady State Hypothesis)                  │   │
│  │                                                             │   │
│  │  定义: 定义系统的"正常"状态                                  │   │
│  │                                                             │   │
│  │  稳态指标:                                                   │   │
│  │  ├── 请求成功率 > 99.9%                                     │   │
│  │  ├── P99 延迟 < 500ms                                       │   │
│  │  ├── 错误率 < 0.1%                                          │   │
│  │  ├── CPU 使用率 < 80%                                       │   │
│  │  └── 业务指标正常（订单量、转化率）                         │   │
│  │                                                             │   │
│  │  关键: 混沌实验不是随机破坏，而是验证稳态是否被破坏          │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  原则 2: 真实世界事件 (Real-World Events)                    │   │
│  │                                                             │   │
│  │  模拟真实可能发生的故障:                                     │   │
│  │  ├── 服务器故障 (硬件故障、内核崩溃)                         │   │
│  │  ├── 网络故障 (延迟、丢包、分区)                             │   │
│  │  ├── 应用故障 (进程崩溃、内存泄漏)                           │   │
│  │  ├── 依赖故障 (数据库、缓存、第三方 API)                    │   │
│  │  ├── 资源耗尽 (CPU、内存、磁盘、连接池)                     │   │
│  │  └── 配置错误 (错误配置、证书过期)                           │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  原则 3: 生产环境运行 (Run in Production)                    │   │
│  │                                                             │   │
│  │  为什么在生产环境:                                           │   │
│  │  ├── 测试环境无法完全模拟生产                                │   │
│  │  ├── 真实流量才能暴露真实问题                                │   │
│  │  ├── 生产环境的依赖和配置不同                                │   │
│  │  └── 只有生产环境才有完整的监控和告警                        │   │
│  │                                                             │   │
│  │  渐进策略:                                                   │   │
│  │  1. 先在测试环境验证实验设计                                 │   │
│  │  2. 在生产环境小范围执行                                     │   │
│  │  3. 逐步扩大实验范围                                         │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  原则 4: 持续自动化 (Automate Continuously)                  │   │
│  │                                                             │   │
│  │  ├── 定期执行混沌实验（如每周）                              │   │
│  │  ├── 集成到 CI/CD 流水线                                     │   │
│  │  ├── 自动化结果分析                                          │   │
│  │  └── 持续改进系统韧性                                        │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  原则 5: 最小爆炸半径 (Minimize Blast Radius)                │   │
│  │                                                             │   │
│  │  ├── 从单个 Pod 开始实验                                     │   │
│  │  ├── 逐步扩大到服务级别                                      │   │
│  │  ├── 限制影响范围（命名空间、标签）                          │   │
│  │  ├── 准备好回滚/停止机制                                     │   │
│  │  └── 设置超时自动终止                                        │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 3.2 Litmus ChaosExperiment

```yaml
# pod-delete-experiment.yaml
apiVersion: litmuschaos.io/v1alpha1
kind: ChaosEngine
metadata:
  name: pod-delete-chaos
  namespace: production
spec:
  # 目标应用
  appinfo:
    appns: production
    applabel: app=myapp
    appkind: deployment

  # 混沌实验
  experiments:
    - name: pod-delete
      spec:
        components:
          env:
            # 目标 Pod 数量
            - name: TOTAL_CHAOS_DURATION
              value: "30"
            # 混沌持续时间（秒）
            - name: CHAOS_INTERVAL
              value: "10"
            # 每次删除间隔
            - name: FORCE
              value: "false"
            # 是否强制删除
        probe:
          # 稳态探针
          - name: "check-app-health"
            type: "httpProbe"
            mode: "Continuous"
            httpProbe/inputs:
              url: "http://myapp.production.svc/healthz
              method:
                get:
                  criteria: "=="
                  responseCode: "200"
              insecureSkipVerify: false
            runProperties:
              probeTimeout: 5s
              interval: 2s
              retry: 3
              probePollingInterval: 2s

  # 执行状态
  engineStatus: "active"
  chaosServiceAccount: litmus-admin
```

#### 4.2 Chaos Mesh CRD 配置

```yaml
# PodChaos - 随机杀死 Pod
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: pod-kill-example
  namespace: chaos-testing
spec:
  action: pod-kill
  mode: one
  # one: 随机选择一个 Pod
  # all: 所有匹配的 Pod
  # fixed: 固定数量
  # fixed-percent: 固定百分比
  # random-max-percent: 最大百分比
  selector:
    namespaces:
      - production
    labelSelectors:
      app: myapp
  duration: "30s"
  scheduler:
    cron: "@every 1h"
    # 每小时执行一次

---
# NetworkChaos - 网络延迟
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: network-delay-example
  namespace: chaos-testing
spec:
  action: delay
  mode: all
  selector:
    namespaces:
      - production
    labelSelectors:
      app: myapp
  delay:
    latency: "200ms"
    jitter: "50ms"
    correlation: "50"
  duration: "60s"
  direction: to
  target:
    selector:
      namespaces:
        - production
      labelSelectors:
        app: payment-service
    mode: all

---
# NetworkChaos - 网络丢包
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: network-loss-example
  namespace: chaos-testing

  action: loss
  mode: all
  selector:
    namespaces:
      - production
    labelSelectors:
      app: myapp
  loss:
    loss: "30"
    correlation: "50"
  duration: "60s"

---

  action: latency
  mode: all

      - production

  volumePath: /var/data

### 5. 实验设计方法论

#### 5.1 混沌实验设计流程

```
┌─────────────────────────────────────────────────────────────────────┐
│                    混沌实验设计流程                                    │
│                                                                     │
│  Step 1: 定义稳态假设                                               │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  "在正常情况下，系统的 SLI 应该满足 SLO"                     │   │
│  │                                                             │   │
│  │  SLI 定义:                                                   │   │
│  │  ├── 请求成功率 > 99.9%                                     │   │
│  │  ├── P99 延迟 < 500ms                                       │   │
│  │  └── 订单创建成功率 > 99.5%                                 │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  Step 2: 设计实验假设                                               │

### 练习 1: 安装 Chaos Mesh 并执行 Pod 杀死实验

**目标:** 安装 Chaos Mesh，执行 Pod 杀死实验，验证系统自动恢复。

```bash
# 步骤 1: 安装 Chaos Mesh
curl -sSL https://mirrors.chaos-mesh.org/latest/install.sh | bash

# 步骤 2: 验证安装
kubectl get pods -n chaos-testing

# 步骤 3: 部署测试应用
kubectl create namespace chaos-demo
kubectl apply -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-app
  namespace: chaos-demo
spec:
  replicas: 3
  selector:
    matchLabels:
      app: demo-app
  template:
    metadata:
      labels:
        app: demo-app
    spec:
      containers:
        - name: demo-app
          image: nginx:1.24
          ports:
            - containerPort: 80
EOF

# 步骤 4: 创建 Pod 杀死实验
cat <<EOF | kubectl apply -f -
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: pod-kill-demo
  namespace: chaos-demo
spec:
  action: pod-kill
  mode: one
  selector:
    namespaces:
      - chaos-demo
    labelSelectors:
      app: demo-app
  duration: "30s"
EOF

# 步骤 5: 观察实验
kubectl get pods -n chaos-demo -w
# 观察 Pod 被杀死后自动恢复

# 步骤 6: 查看实验结果
kubectl describe podchaos pod-kill-demo -n chaos-demo

# 步骤 7: 清理
kubectl delete podchaos pod-kill-demo -n chaos-demo
```

### 练习 2: 使用 Litmus 进行网络延迟实验

**目标:** 使用 Litmus Chaos 注入网络延迟，验证服务降级策略。

```bash
# 步骤 1: 安装 Litmus
helm repo add litmuschaos https://litmuschaos.github.io/litmus
helm install litmus litmuschaos/litmus --namespace litmus --create-namespace

# 步骤 2: 创建 ChaosEngine
cat <<EOF | kubectl apply -f -
apiVersion: litmuschaos.io/v1alpha1
kind: ChaosEngine
metadata:
  name: network-latency-chaos
  namespace: chaos-demo
spec:
  appinfo:
    appns: chaos-demo
    applabel: app=demo-app
    appkind: deployment
  experiments:
    - name: pod-network-latency
      spec:
        components:
          env:
            - name: NETWORK_LATENCY
              value: "200"
            - name: JITTER
              value: "50"
            - name: TOTAL_CHAOS_DURATION
              value: "60"
  engineStatus: active
  chaosServiceAccount: litmus-admin
EOF

# 步骤 3: 观察延迟注入效果
# 在另一个终端持续请求服务
while true; do
  curl -w "time_total: %{time_total}s\n" -o /dev/null -s http://demo-app.chaos-demo.svc
  sleep 1
done

# 步骤 4: 清理
kubectl delete chaosengine network-latency-chaos -n chaos-demo
```

## 面试题精选

### 1. 什么是混沌工程？它的核心原则是什么？

**参考答案：**

混沌工程是一种通过在系统中主动注入故障来发现隐藏问题、验证系统韧性的实践。

核心原则：
1. **稳态假设**：定义系统的"正常"状态
2. **真实世界事件**：模拟真实可能发生的故障
3. **生产环境运行**：在真实环境中验证
4. **持续自动化**：定期自动执行实验
5. **最小爆炸半径**：控制实验影响范围

### 2. Chaos Mesh 和 Litmus 有什么区别？

**参考答案：**

| 特性 | Chaos Mesh | Litmus |
|------|------------|--------|
| 来源 | PingCAP | CNCF |
| 安装复杂度 | 简单 | 中等 |
| CRD 数量 | 少而精 | 多而全 |
| UI | Dashboard | ChaosCenter |
| 实验类型 | Pod/Network/IO/Stress/DNS/Time | 丰富（含 AWS/Azure） |
| 学习曲线 | 简单 | 中等 |
| 适合场景 | K8s 原生实验 | 多云/混合云 |

选择：K8s 环境用 Chaos Mesh，多云环境用 Litmus。

### 3. 如何控制混沌实验的爆炸半径？

**参考答案：**

控制策略：
1. **模式选择**：one（单个）/ fixed-percent（固定百分比）/ all（全部）
2. **标签选择**：通过 labelSelectors 限制影响的 Pod
3. **命名空间隔离**：只在特定命名空间执行
4. **持续时间**：设置 duration 自动终止
5. **手动终止**：保留随时停止的能力
6. **监控触发**：SLO 违约时自动终止

### 4. 什么是 GameDay？如何组织？

**参考答案：**

GameDay 是一种有组织的混沌工程实践，团队一起执行故障注入实验。

组织流程：
1. **准备**：确定参与者、选择实验、评估风险、通知相关方
2. **执行**：按计划执行实验，实时观察系统行为
3. **复盘**：讨论发现、制定改进项、更新 Runbook

关键要素：有组织、有计划、有观察、有复盘。

### 5. 如何验证混沌实验是否成功？

**参考答案：**

验证维度：
1. **稳态保持**：SLO 指标是否在阈值内
2. **自动恢复**：系统是否自动恢复（MTTR）
3. **告警有效性**：告警是否及时触发（MTTD）
4. **用户影响**：实际用户影响范围
5. **发现价值**：是否发现新的故障模式

成功标准：系统按预期行为工作，或发现了有价值的改进点。

### 6. 混沌工程与传统测试有什么区别？

**参考答案：**

| 维度 | 传统测试 | 混沌工程 |
|------|----------|----------|
| 环境 | 测试环境 | 生产环境 |
| 目标 | 验证功能 | 验证韧性 |
| 方法 | 预定义场景 | 探索性实验 |
| 范围 | 单组件 | 整个系统 |
| 持续性 | 一次性 | 持续进行 |
| 价值 | 发现 Bug | 发现架构问题 |

### 7. 如何在组织中推广混沌工程？

**参考答案：**

推广路径：
1. **获得支持**：向管理层展示混沌工程的价值
2. **从小开始**：从测试环境、非关键服务开始
3. **建立信心**：通过成功案例建立团队信心
4. **逐步扩展**：从测试到生产，从单服务到多服务
5. **自动化**：将混沌实验集成到 CI/CD
6. **文化建设**：将混沌工程融入团队文化

### 8. 混沌实验中如何保证安全？

**参考答案：**

安全措施：
1. **爆炸半径控制**：从最小范围开始
2. **自动终止**：设置 duration 和终止条件
3. **监控告警**：SLO 违约时自动终止
4. **回滚准备**：随时可以手动终止和回滚
5. **人员值守**：执行时必须有人观察
6. **业务保护**：避免在高峰期执行
7. **逐步扩大**：先测试后生产

### 9. 如何衡量混沌工程的投资回报率（ROI）？

**参考答案：**

衡量维度：
1. **MTTR 改善**：故障恢复时间缩短
2. **MTTD 改善**：故障检测时间缩短
3. **故障减少**：生产事故数量减少
4. **SLO 达成**：SLO 达成率提升
5. **知识积累**：团队对系统的理解加深
6. **信心提升**：团队对变更的信心增强

### 10. 混沌工程如何与 SRE 实践结合？

**参考答案：**

结合点：
1. **SLO 驱动**：用 SLO 定义稳态假设
2. **Error Budget**：Error Budget 充足时执行混沌实验
3. **GameDay**：定期组织 GameDay
4. **持续改进**：实验发现的改进项纳入 Sprint
5. **Runbook 验证**：用混沌实验验证 Runbook 有效性
6. **监控验证**：用混沌实验验证监控覆盖度
